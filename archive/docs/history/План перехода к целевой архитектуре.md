# План перехода к целевой архитектуре ACE

Дата: 22.11.2026.

Статус: **план миграции**, не изменение кода. Документ задаёт порядок,
границы и критерии готовности каждого этапа.

Цель плана — не «переписать приложение», а **постепенно заменить
неустойчивые границы устойчивыми**, сохраняя работоспособность на каждом
шаге.

Связанные документы:

- `docs/Целевая архитектура приложения.md` — куда идём;
- `docs/Целевая архитектура модулей.md` — контракт расширений;
- `docs/Обнаруженые проблемы.md` — что уже известно;
- `docs/Проблема одной секции.txt` — границы доверия к Resolver4.

## 0. Правила миграции

1. **Никакого big bang.** Каждый этап оставляет приложение рабочим.
2. **Тесты — ворота.** Этап не начинается, пока предыдущий не проходит
   архитектурные тесты и не имеет зелёного baseline.
3. **Сначала границы, потом перенос кода.** Нельзя «оптимизировать» код,
   пока не описано, кому он принадлежит.
4. **Один контракт сразу.** Пока приложение не в релизе, публичная
   обратная совместимость не поддерживается. Старые имена, shim'ы и
   deprecation-обёртки не создаются. Внутренний transitional-адаптер
   допустим только внутри одного этапа и удаляется в его конце.
5. **Запись патчей заморожена до этапа 5.** До этапа 5 — только
   предпросмотр. После этапа 5 запись остаётся экспериментальной до
   release gate этапа 8.
6. **Один снимок — одна операция.** Любая миграция кэшей и проектов должна
   сохранять это правило.
7. **Никаких «тихих» fallback'ов.** Если новый контракт не найден — это
   ошибка или `SKIPPED`, а не вызов «первого попавшегося метода».
8. **Каждое отступление — ADR.** Причина, срок, план устранения.
9. **Данные пользователя не теряются.** Проекты мигрируют one-time с
   backup. Кэш не мигрирует: версия меняется, старый кэш удаляется.
   Форматы игры (LTX/XML/DLTX/DXML) сохраняют полную совместимость.
10. **Изменения обратимы.** Для рискованных этапов — feature flag и
    возможность отключить новый путь без отката данных.
11. **Обратная совместимость — не цель.** Новая версия не обязана читать
    данные старого формата, кроме явной one-time миграции проекта.

### 0.1. Политика совместимости до первого релиза

| Что | Позиция |
|---|---|
| Код приложения | **Ломать свободно.** Один контракт, одно имя, один путь |
| API SDK для встроенных модулей | **Ломать.** `base` и `ogg_editor` обновляются в том же изменении |
| Внешние модули | Сейчас отсутствуют. Если появятся — политика пересматривается отдельно |
| `project.json`, drafts, resolved, assets | **One-time forward migration + backup.** Обратное чтение не поддерживается |
| `tabs.json`, `project_roots.json` | Можно сбросить или мигрировать тривиально |
| `generated/` — кэш резолва, иконки, XML | **Не мигрировать.** Сменить версию и удалить/пересобрать |
| Патч-моды на диске | Не читаются как источник истины; совместимость не нужна |
| `tests/main_unit_test_*` | **Сохранить.** Это контракт поведения, а не поддержка старых версий |
| Форматы игры: LTX, XML, DLTX, DXML, кодировки | **Полная совместимость и паритет.** Ломать нельзя |
| `sdk_min` и версия SDK | **Сохранить.** До 1.0 — 0.x с правом ломать; после 1.0 — semver |
| Политика deprecation | **Не нужна до 1.0.** Вместо неё — удаление старого API |

Почему так:

- каждый публичный shim — это вторая ветка поведения, лишние тесты и
  скрытая связность;
- пока нет внешних модулей, поддерживать старый SDK-контракт не для кого;
- кэш — regenerable-данные, его миграция бессмысленна;
- проект — пользовательский труд, поэтому one-time миграция дешевле
  потери черновиков;
- форматы игры — не «версия приложения», а свойство движка; здесь
  компромиссов нет.

Если реальных проектов с ценными черновиками ещё нет, допускается явный
сброс с предупреждением. Молчаливое удаление данных запрещено.

### 0.2. Данные проекта

Проект — единственная категория данных, где one-time migration обязательна.

Правила:

1. **Только вперёд.** Новая версия читает старый проект и переводит его в
   новый формат. Обратное чтение нового формата старой версией не
   поддерживается.
2. **Backup до миграции.** Перед изменением создаётся копия
   `project.json`, черновиков и resolved/assets в каталоге проекта
   (`.migration_backup_<timestamp>`) или рядом с ним.
3. **Атомарность.** Миграция пишет во временный каталог/файл и
   переименовывает только после успешной проверки.
4. **Идемпотентность.** Повторный запуск миграции не портит уже
   мигрированный проект.
5. **Диагностика.** Ошибка миграции видна пользователю; проект остаётся в
   исходном состоянии.
6. **Одноразовость.** После успешной миграции старый код чтения удаляется;
   он не живёт как постоянная ветка совместимости.
7. **Тесты.** Старый fixture → новый формат; проверка черновиков,
   resolved, assets, настроек и `tabs.json`.
8. **Сброс допустим только явно.** Если проект не нужен, пользователь
   видит предупреждение и подтверждает сброс.

| Мёртвый код | `src/old/*`, отдельные методы | Поддерживаемость |

### 1.3. Главный риск

Главный риск — не размер кода, а **неявные контракты**:

- UI знает, как собрать патч;
- модуль знает, как устроен `core`;
- кэш знает «текущую папку», а не снимок;
- окно не знает владельца;
- SDK знает предметы.

Поэтому миграция начинается не с рефакторинга файлов, а с **фиксации
контрактов и тестов**, которые не дадут этим связям вернуться.

**Размер:** S. **Риск:** низкий. **Блокирует:** всё.

### Цель

Зафиксировать текущее поведение и сделать архитектурные нарушения
видимыми до того, как начнётся перенос кода.

К началу этапа `AGENTS.md`, `docs/Текущий режим.md` и
`docs/Миграционные исключения.md` уже существуют и обязательны для
исполнения.

### Шаги

1. Зафиксировать baseline:
   - сохранить текущее рабочее состояние (коммит/тег или резервная копия,
     включая незакоммиченные изменения);
   - прогнать `pytest`, `compileall`, `git diff --check`;
   - сохранить число тестов и известные skip;
   - сохранить эталонный набор секций/файлов для сравнения.

2. Зафиксировать политику совместимости из §0.1:
   - публичных shim'ов и deprecation-обёрток нет;
   - старые API удаляются в том же изменении;
   - проекты — one-time migration;
   - кэш — version bump + удаление;
   - форматы игры — полная совместимость.

3. Расширить `tests/test_architecture.py`:
   - матрица импортов (см. `docs/Целевая архитектура приложения.md`, §3.3);

     модули;
   - `sdk` не импортирует `core`, `app`, `platform`, `ui`, `modules`;
   - `core` не импортирует `sdk`, `app`, `platform`, `ui`, `modules`;
   - `app` не импортирует `ui`, `platform`, `modules`;
   - `ui` не импортирует `core` напрямую (после Этапа 3 — жёстко);
   - импорт пакета `modules` разрешён только в `ModuleLoader`;
   - `PyQt5.QtWidgets` только в `ui` и `modules`;
   - `dispatch` не вызывается из фонового потока (runtime-тест);
   - запрет `getattr(... "method", None)` в адаптерах (после Этапа 1).

   Базовая проверка должна запускаться одной командой:

   ```text
   python -m pytest -q
   python -m compileall -q src
   git diff --check
   ```

4. Ввести allowlist публичных имён:
   - `sdk.__all__`;
   - `core.__all__`;
   - список модулей-исключений на время миграции.

5. Ввести feature flag `patch_write_experimental`:
   - по умолчанию выключен;
   - включает запись только после Этапов 5 и 8;
   - UI показывает статус.

6. Ввести обязательный ADR-шаблон:
   - контекст;
   - решение;
   - альтернативы;
   - последствия;
   - срок/план устранения.

7. Зафиксировать «правила поля»:
   - новые фичи не добавляются в patch path;
   - новые модули не используют старые доменные API;
   - новые кэши не создаются вне `CacheService` (после Этапа 2);
   - эталонные тесты `tests/main_unit_test_*` не создаются и не меняются
     без явного одобрения оператора (см. `docs/main_unit_tests.md`).

8. Зафиксировать baseline производительности:
   - построение дерева;
   - открытие resolved-корня (память/диск);
   - запрос секции;
   - предпросмотр патча;
   - память процесса;
   - время отклика UI при фоновой предсборке.

   Эти числа — не догма, а точка сравнения. После каждого этапа
   допускается отклонение не более 10% без объяснения.

### Критерии готовности

- baseline воспроизводится одной командой;
- политика совместимости §0.1 зафиксирована в ADR;
- архитектурные тесты падают на искусственном нарушении;
- performance baseline зафиксирован;
- feature flag существует и выключен;
- ADR-шаблон и первые ADR добавлены;
- все текущие тесты зелёные.

### Что не делаем

- не меняем поведение;
- не переносим файлы;
- не добавляем публичные shim'ы и deprecation-обёртки;
- не «чиним» проблемы, которые ещё не имеют контракта.

## 4. Этап 1. SDK: чистый контракт

**Размер:** M. **Риск:** средний. **Зависит от:** Этап 0.

### Цель

Сделать SDK стабильным и маленьким, убрать доменные понятия из корня,
ввести capabilities и типизированный контекст. Старые имена удаляются
сразу: shim'ов и deprecation до `1.0` нет.

### Шаги

1. Разделить SDK:

```text
sdk/
  __init__.py          # тонкий фасад для модулей
  contracts/           # DTO, ID, ошибки, имена событий
  kernel/              # ModuleBase, ModuleContext, регистрация, задачи
  ui/                  # протоколы UI
  features/items/      # ItemCatalog, ItemEntry, ItemSection, ...
  features/audio/      # Ogg-контракты, если нужны другим
  features/documents/  # общие документные DTO
```

2. Вынести реализации адаптеров:
   - `src/sdk/adapters.py` → `src/platform/sdk_bridge/` (или
     `src/ui/platform/sdk_bridge/` на переходном этапе);
   - в `sdk` оставить только протоколы;
   - старые импорты удаляются, а `base_module`, `ogg_editor` и тесты
     обновляются в том же изменении. Публичных shim'ов нет.

3. Ввести capability registry:
   - `ctx.capabilities.require(name, min_version)`;
   - `ctx.capabilities.optional(name)`;
   - `ctx.capabilities.provide(name, version, obj)`;
   - версия и владелец;
   - проверка при загрузке модуля.

4. Ввести `DocumentApi` и `PatchApi`:
   - `ctx.documents.open/read/apply/subscribe`;
   - `ctx.patches.propose(intent)`;
   - фиксация патча модулю недоступна;
   - item/resolved-методы уходят в `sdk.features.items` и
     `sdk.features.documents` или удаляются из корня.

5. Ввести уровни API:
   - stable/experimental/internal;
   - `deprecated` не используется до 1.0: старое удаляется, а не живёт
     параллельно;
   - маркировка в docstring и в реестре;
   - проверка `sdk.max`.

6. Обновить `ModuleContext`:
   - `ctx.module_id`;
   - `ctx.kernel`, `ctx.services`, `ctx.documents`, `ctx.patches`,
     `ctx.ui`, `ctx.tasks`, `ctx.events`, `ctx.commands`,
     `ctx.capabilities`, `ctx.projects`, `ctx.paths`;
   - никаких необъявленных полей.

7. Ломка старого контракта:
   - старые имена удаляются из `sdk/__init__.py` без shim;
   - `base_module` и `ogg_editor` переводятся в том же изменении;
   - тесты и примеры обновляются вместе с кодом;
   - публичная совместимость не сохраняется.

8. Ввести порты ядра:
   - `core/api/vfs.py`, `documents.py`, `resolve.py`, `graph.py`,
     `patches.py`;
   - `CoreServices` становится композиционным адаптером, а не публичным
     богом-фасадом;
   - `app` зависит от портов, а не от конкретных классов.

9. Удалить мёртвый legacy-код, который не участвует в сборке:
   - `src/old/*`;
   - очевидные старые реализации, которые не импортируются;
   - это уменьшает пространство для случайной «совместимости».

### Критерии готовности

- `sdk` не импортирует внутренние слои;
- корень SDK не содержит `ItemCatalog`, `ItemEntry`, `apply_resolved_field_edit`
  и подобных доменных имён — без legacy-алиасов;
- модуль-образец использует только `sdk` и capability;
- `CoreApiAdapter`/`UiApiAdapter` не ищут методы по именам;
- тесты импортов и версии проходят.

### Риски и смягчение

| Риск | Смягчение |
|---|---|
| Встроенные модули сломаются | обновить `base`, `ogg_editor` и тесты в том же изменении |
| Доменные API нужны base | `sdk.features.items` + capability |
| Capability registry станет service locator'ом | типизированные протоколы, явные `needs` |
| Адаптеры переедут не полностью | transitional-адаптер только внутри этапа, не публичный |

## 5. Этап 2. Снимок и кэш

**Размер:** L. **Риск:** средний/высокий. **Зависит от:** Этап 1.

### Цель

Сделать так, чтобы ни один кэш не мог вернуть данные из другого состояния
VFS, а инвалидация была точечной и объяснимой.

### Шаги

1. Ввести `SnapshotService` в `app/workspace`:
   - `SnapshotToken`;
   - компоненты: scan dir, profile, mod order, file stamps, overlay,
     engine versions, rules version;
   - `snapshot_id`;
   - событие `SnapshotChanged`;
   - `WorkspaceSession` — единственный владелец.

2. Ввести `CacheService`:
   - пространства имён: `tree`, `resolve.text`, `resolve.semantic`, `xml`,
     `graph`, `query`, `icons`, `patch.preview`;
   - `get_or_compute(namespace, key, compute, deps)`;
   - memory LRU + disk backend;
   - single-flight;
   - статистика;
   - инвалидация по snapshot/deps;
   - `ResolvedCache` становится backend'ом, а не отдельным центром.

3. Привязать дерево к снимку:
   - ключ `tree_builder` включает `snapshot_id`;
   - внешнее изменение файла создаёт новый снимок;
   - `TREE_READY` несёт `snapshot_id`;
   - `Forest.cache_id` = `snapshot_id`.

4. Убрать дублирование path identity:
   - канонический `path_key`/`same_path` — в `core.tools.paths`;
   - модули используют `ctx.paths.key(path)`/`ctx.paths.same(a, b)`;
   - `sdk.path_key`/`sdk.paths.path_key` удаляются, а встроенные модули
     и тесты переводятся сразу;
   - `normcase` везде;
   - тесты на регистр, `..`, junction/symlink.

5. Исправить `ProjectOverlay.revision`:
   - `ProjectService` передаёт дешёвый `revision_token` из состояния
     черновиков (id проекта + ревизии драфтов);
   - для overlay без токена — контентный хеш, включающий каждую
     `LineSource`;
   - не длина `line_sources`;
   - изменение карты источников меняет ревизию;
   - после Этапа 3 токен будет поставлять `DraftStore`.

6. Сделать предсборку прогревом кэша:
   - приоритеты;
   - отмена;
   - не является источником истины;
   - не блокирует открытие файла;
   - прогресс и статистика.

7. Добавить точечную инвалидацию:
   - `affected_roots(paths)`;
   - инвалидация только затронутых корней;
   - fallback — полная инвалидация с записью причины.

8. Отказаться от миграции кэша:
   - поднять версию формата;
   - старый `generated/resolved_cache` не читается;
   - старый каталог удаляется или пересобирается;
   - в диагностике видно, что кэш сброшен.

### Критерии готовности

- внешнее изменение файла не оставляет старое дерево;
- правка проекта не инвалидирует все корни;
- `ResolvedCache` и дерево не могут смешать снимки;
- кэш-ключ объясним (namespace + snapshot + logical key);
- старый кэш не читается после смены версии;
- тесты на инвалидацию и повторное использование проходят;
- нет регрессии времени открытия > 10% (или есть объяснение).

### Риски и смягчение

| Риск | Смягчение |
|---|---|
| Кэш станет медленнее | бенчмарки, memory LRU, disk backend |
| Снимок дорогой | ленивые подписи, кэш подписей, инкрементальные stamp |
| Старые ключи кэша | версия формата + удаление/пересборка, без миграции |
| Точечная инвалидация ошибочна | fallback на полную + диагностика |

### Риски и смягчение

| Риск | Смягчение |
|---|---|
| Большой рефакторинг | по одному use case за шаг |
| Потеря черновиков | one-time migration + backup + тесты |

## 8. Этап 5. Единый patch engine

**Размер:** L. **Риск:** высокий. **Зависит от:** 3, 4.

### Цель

Сделать один конвейер для LTX, XML, assets и новых файлов; убрать ручную
сборку и автоподтверждение; сделать запись доказуемо безопасной.

### Шаги

1. Ввести `PatchEngine`:
   - `plan(intent, snapshot)`;
   - `generate(plan)`;
   - `verify(generated)`;
   - `preview(plan)`;
   - `commit(generated, authorization)` — только через writer.

2. Реализации:
   - `LtxPatchEngine`;
   - `XmlPatchEngine`;
   - `AssetPatchEngine`;
   - `NewFilePatchEngine`;
   - общий `PatchOrchestrator`.

3. Ввести `PatchIntent` и `PatchBundle`:
   - намерение;
   - снимок;
   - план;
   - файлы;
   - проверка;
   - заметки.
   `CommitAuthorization` не входит в `PatchBundle`: это отдельный
   результат `PatchCommitService.authorize` (ADR-22), который
   выпускается после подтверждения рисков и полного round-trip.

4. Перенести ручные ветки из `src/app/projects/patch_builder.py`:
   - `_asset_preview_item`;
   - `_new_file_preview`;
   - `_merge_xml_generated`;
   - `add_item`/XML-режимы.
   В engine или в явные contributors.

5. Ввести `PatchCommitService`:
   - единственная точка записи;
   - проверка `PatchWriter`;
   - `CommitAuthorization` (plan id + snapshot id + подтверждённые риски) —
     отдельный результат `authorize`, не поле `PatchBundle`;
   - запрет автоподтверждения;
   - атомарная запись;
   - post-write verification;
   - аудит.

6. Убрать `if plan.needs_confirmation: plan = replace(plan, confirmed=True)`
   из `src/ui/platform/project_controller.py`.
   Вместо этого — отдельный диалог подтверждения и токен.

7. Полный round-trip:
   - применить патч виртуально;
   - собрать затронутый корень;
   - сравнить полный diff «до/после»;
   - проверить отсутствие дублей, потерянных ключей, `DLTX_DELETE`-
     артефактов;
   - проверить источник итогового значения.

8. UI предпросмотра:
   - показывает полный diff;
   - показывает проверку;
   - показывает риски;
   - позволяет исключить элемент;
   - не позволяет записать без проверки.

9. Фиксация без блокировки UI:
   - запись патч-мода выполняется через task service;
   - прогресс по файлам;
   - ошибка/отмена не оставляет частичный мод;
   - UI остаётся отзывчивым.

### Критерии готовности

- ни один путь не пишет без `CommitAuthorization`;
- `PatchWriter` недоступен в обход `PatchCommitService`;
- опасные планы требуют отдельного подтверждения;
- полный diff затронутого корня проверяется;
- XML/asset/new-file идут через тот же контракт;
- фиксация не блокирует UI;
- старые patch-тесты проходят;
- `tests/main_unit_test_patch.py` проходит без изменения ожидаемого
  поведения (изменения — только с одобрения оператора);
- новые тесты на безопасность и round-trip проходят.

### Риски и смягчение

| Риск | Смягчение |
|---|---|
| Потеря существующей логики | параллельный запуск old/new preview |
| Медленный полный diff | только затронутый корень, ленивый diff |
| Несовместимость планов | версия `PatchPlan`, миграция |
| Случайная запись | feature flag + авторизация + тесты |

## 9. Этап 6. Workbench и UI-платформа

**Размер:** L. **Риск:** средний. **Зависит от:** 1, 3. **Параллельно:** 4/5.

### Цель

Сделать рабочую среду расширяемой и безопасной: окна, вкладки, раскладка,
тема, маршрутизация открытия.

### Шаги

1. `WindowService`:
   - `WindowSpec`/`DockSpec`/`TabSpec`;
   - owner;
   - state key;
   - dock/floating/dialog;
   - sizes/anchors;
   - layout persistence.

2. Владение вкладками:
   - `open_tab` принимает owner;
   - `close_tab` проверяет owner;
   - `close_owner_tabs` — только свои;
   - `tab_id` больше не является единственным способом определить владельца.

3. File open router:
   - контекст `view/edit/preview/patch`;
   - предпочтения;
   - неоднозначность;
   - fallback;
   - `request_id` навигации.

4. Редактор:
   - режимы raw/resolved/draft/preview/diff;
   - явный dirty/busy;
   - «Сохранить как патч»;
   - запрет записи в оригинал;
   - никакой второй копии текста как источника истины.

5. Тема:
   - `ThemeService` с токенами;
   - убрать `PALETTE` как глобальный источник;
   - динамическая смена;
   - тест «нет жёстких цветов» в `ui`/`modules`.

6. TaskService:
   - пул потоков/процессов;
   - приоритеты;
   - отмена;
   - прогресс;
   - owner cleanup;
   - shutdown.

7. Подсказки:
   - `HintService` — платформенный сервис;
   - провайдеры и каталоги не живут в модулях;
   - модуль подключает подсказки через `attach_text_hints`;
   - собственные popup подсказок/автодополнения текста запрещены;
     стандартные `QComboBox`, диалоговые списки и domain-specific
     средства выбора значения (например, `SoundTypeCombo`) не считаются
     hint-popup.

8. Операции и зависимости:
   - `OperationRegistry` со состояниями `queued/running/done/failed/cancelled`;
   - owner, progress, cancel, зависимости;
   - стабильный `operation_key` и single-flight;
   - повторный запуск не создаёт дубль, а показывает «уже запущено»;
   - центр операций в правом нижнем углу вместо одиночного индикатора
     предсборки;
   - список идущих/завершённых операций по клику;
   - блокируются только действия, зависящие от конкретной операции;
   - ошибки и отмена видны пользователю;
   - никакого модального блокирования всей рабочей среды.

### Критерии готовности

- модуль не может закрыть чужое окно/вкладку;
- раскладка восстанавливается;
- отсутствующий модуль не ломает восстановление;
- тема переключается без перезапуска;
- нет жёстких цветов в UI/модулях (кроме документированных исключений);
- задачи не блокируют UI и отменяются;
- очередь операций видна и открывается из индикатора;
- повторный запуск одной операции не создаёт дубль;
- при построении дерева блокируются только зависимые функции, а не всё
  приложение;
- ни одна тяжёлая операция не выполняется в UI-потоке.

### Риски и смягчение

| Риск | Смягчение |
|---|---|
| UI-регрессии | ручной smoke + скриншоты/тесты |
| Потеря раскладки | версия схемы + fallback |
| Встроенные модули используют старые окна | обновить их в том же изменении, без shim |
| Тема ломает лексеры | токены + обновление по событию |

     а не канонический VFS snapshot;
   - один `LocalizationService` для подсказок и карточек;
   - `clear_namespace` очищает память, диск сохраняется;
   - `clear_disk` и `backend_stats` покрывают item-backend'ы.

9. CACHE-5a / graph-кэш (шаг 7.9):
   - `ReferenceGraphBuilder` принимает `cache_service`;
   - `graph.file` — file stamp, `graph.section` — `forest.cache_id` +
     overlay signature;
   - production `main.py` больше не создаёт `DisabledCache`;
   - fallback/partial/read-error не кэшируются.

10. CACHE-5 / confidence связей (шаг 7.10):
    - `MatchInfo.confidence`, `GraphMatch.confidence`,
      `GraphNode.primary_confidence`;
    - правила `exact/probable/heuristic` по типу связи;
    - UI-колонка «Уверенность»;
    - SDK `0.13.0` по ADR-36.

### Критерии готовности

- `base` всегда загружается и не отключается (ADR-35);
- `base` загружается через обычный `module.json`/`ModuleLoader`, без
  привилегированного пути импорта;
- `ogg_editor` требует `base` по id;
- item browser можно не включать;
- class-manifest не используется;
- модуль-образец проходит conformance;
- отключение провайдера capability не ломает приложение;
- корень SDK не содержит предметов;
- item-кэши (`catalog`, `icons`, `localization`) идут через общий
  `CacheService` с content-addressed `snapshot_id`; `CACHE-1` закрыт;
- graph-кэш (`graph.file`, `graph.section`) идёт через `CacheService`;
  production не использует `DisabledCache`; `CACHE-5a` закрыт;
- связи графа имеют `confidence` и UI показывает его; `CACHE-5` закрыт.

### Риски и смягчение

| Риск | Смягчение |
|---|---|
| `base` слишком связан с платформой | сначала вынести workspace, потом UI |

## 11. Этап 8. Паритет и release gate

**Размер:** M. **Риск:** средний. **Зависит от:** 5, 7.

### Цель

Закрыть или задокументировать расхождение с игрой и только после этого

### Шаги

1. Автоматический дамп секций:
   - имя;

   - значения;

2. Сравнение с игрой:
   - множества секций;
   - ключи;
   - значения;
   - реестр известных отличий.

3. Разбор 19023/19024:
   - найти первую отличающуюся секцию;
   - проверить её происхождение;
   - исправить или задокументировать.

4. Эталонные наборы:
   - `system.ltx`;
   - несколько модов;
   - XML/DXML;
   - списки/удаления/создания секций.

5. Нагрузочные проверки:
   - 20k+ файлов;
   - 19k+ секций;
   - память;
   - время открытия;
   - параллельная предсборка;
   - отмена.

6. Release gate:
   - все обязательные проверки зелёные;
   - запись включается флагом;

### Критерии готовности

- запись проходит полный round-trip на эталонном наборе;
- нет известных опасных расхождений;

### Риски и смягчение

| Риск | Смягчение |
|---|---|
| Расхождение не найдено | реестр исключений + ручная проверка |
| Патч ломает редкий мод | эталонные наборы + feature flag |

## 17. Что не делать

1. **Не переписывать Resolver4.** Это baseline, а не поле рефакторинга.
2. **Не делать big-bang «новую архитектуру».** Только strangler-миграция.
3. **Не добавлять новые фичи в patch path до Этапа 5.**
4. **Не вводить plugin-host «на всякий случай».** Сначала trust level и
   контракт.
5. **Не прятать ошибки fallback'ами.** Ошибка должна быть видимой.
6. **Не делать capability registry «service locator'ом».** Только
   типизированные протоколы и явные `needs`.
7. **Не тащить предметы обратно в `core`/корень SDK.** Домен — в features.
8. **Не закрывать чужое окно/вкладку «для удобства».** Владение — закон.
9. **Не автоматически подтверждать опасные планы.** Подтверждение — только
   пользователь.
10. **Не тащить публичные shim'ы и deprecation до 1.0.** Ломать сразу,
    данные мигрировать one-time.
11. **Не поддерживать старые кэши и старые форматы проектов.** Кэш —
    пересобрать; проект — one-time migration или backup.
12. **Не ломать форматы игры.** LTX/XML/DLTX/DXML и паритет — не часть
    «версии приложения».

## 18. Definition of Done для всей миграции

Миграция завершена, когда:

1. `app`, `platform`, `ui`, `core`, `sdk`, `modules` разделены и проверены
   тестами.
2. SDK не содержит доменных понятий в корне.
3. `core` публикует только явные порты.
4. Любое значение объяснимо.
5. Любой кэш привязан к снимку.
6. Любая правка проходит через проект и патч-конвейер.
7. Любая запись требует проверки и подтверждения.
8. Любое окно/вкладка имеет владельца.
9. Любой модуль можно выгрузить без следов.
10. `base` всегда загружается и не отключается; `item_browser` можно
    отключить.
11. Нет публичных shim'ов, legacy-алиасов и deprecation-хвостов до 1.0.
12. Старые проекты проходят one-time migration; старый кэш удаляется.
13. Паритет с игрой закрыт или задокументирован.
14. Архитектурные тесты и conformance-тесты зелёные.
15. Документация соответствует коду.
16. Новые фичи можно добавлять, не меняя фундамент.

## 19. Итог

Главная задача миграции — не «сделать красиво», а **убрать страх перед
изменениями**.

Устойчивый фундамент означает:

- понятно, где чьи данные;
- понятно, кто имеет право писать;
- понятно, к какому снимку относится результат;
- понятно, как добавить модуль и не сломать других;
- понятно, как проверить патч до записи.

Когда эти пять вещей станут обычными тестами, а не договорённостями, новые
фичи перестанут быть рискованными.

Отдельно зафиксировано: код и SDK можно ломать до релиза, но данные проекта
проходят one-time migration с backup, а кэш просто пересобирается. Это
сохраняет чистоту архитектуры без потери пользовательского труда.
