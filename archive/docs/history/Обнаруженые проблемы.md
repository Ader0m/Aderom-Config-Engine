# Отчёт по оставшимся проблемам ACE

Дата: 26.11.2026.

Проверка: **1370 тестов OK, 1 skipped, 76 subtests**, `compileall` и
`git diff --check` чистые.

Документ содержит только **актуальные** проблемы и риски. История
исправлений и промежуточные состояния — в
`docs/old/История миграции ACE.md`; правила — в `AGENTS.md` и целевых
документах.

---

## 1. Открытые проблемы

### 1.1. Копии больших текстов в проекте

**ID:** `DRAFT-COPIES`. **Приоритет:** средний.

- `ProjectDraft` хранит `original_text`, `current_text`, `saved_text` —
  до трёх копий.
- Аналогично `ProjectResolvedDraft`.
- `ProjectOverlay` передаёт ссылки, но `_filter_overlay`,
  `build_preview` и патч-конвейер создают дополнительные срезы/копии.
- `ProjectPreviewBuilder` хранит `GeneratedPatch` с полными текстами
  файлов; лимит 32 млн символов ограничивает, но не устраняет пиковую
  память.

**Что делать:** перейти на компактные представления/дельты там, где
полный текст не нужен; не хранить копию текста в DTO виджета.

### 1.2. Поколенческая очистка дискового кэша

**ID:** `CACHE-GEN`. **Приоритет:** низкий/средний.

- `CacheService` привязывает записи к `snapshot_id` и зависимостям, но
  дисковый backend `ResolvedCache` ограничен объёмом.
- `_prune_disk` в `core/tools/cache.py` удаляет по LRU-mtime; лимит 1 ГБ —
  предохранитель, а не управление поколениями.
- `clear_disk()` не вызывается автоматически; ручной очистки в UI нет.
- Item-кэши (`catalog`, `icons`, `localization`) имеют дисковые backend'ы
  и вытесняются по LRU; graph-кэши (`graph.file`, `graph.section`) —
  memory-only.

**Что делать:** поколенческие каталоги/маркеры и очистка старых поколений
при старте или смене версии правил.

### 1.3. Крупные прикладные сервисы

**ID:** `APP-BOUNDARY`. **Приоритет:** средний.

- `app/projects/service.py` и `ui/platform/project_controller.py`
  остаются крупными координаторами с бизнес-логикой.
- Часть сценариев уже вынесена (`ProjectRepository`, `DraftStore`,
  `ProjectSession`, `OverlayBuilder`, preview/commit/use cases), но
  границы всё ещё не идеальны.

**Что делать:** выделять use cases по мере изменения, не смешивая
рефакторинг с новой функциональностью.

### 1.4. Дублирование «открыть сырой файл»

**ID:** `OPEN-RAW`. **Приоритет:** низкий/средний.

Пути, которые самостоятельно решают, что считать «сырым» и как показать
файл:

- `LtxFileOpener.open_raw`;
- `XmlFileOpener.open_raw`;
- `PlatformApi.request_open_file_raw`;
- `FileOpenRouter.open_default`;
- `CommonActions.open_raw`.

**Что делать:** оставить один платформенный сценарий и тонкие
обработчики, если различия действительно нужны.

### 1.5. Два пути правки предмета

**ID:** `ITEM-EDIT`. **Приоритет:** средний.

- обычное поле: `_apply_field` → resolved-документ;
- новый файл: `_new_file_for_line`/`_edit_new_item_file` → raw-черновик.

Один UI-жест меняет разные хранилища в зависимости от того, новый файл
или нет.

**Что делать:** единый intent/use case на уровне `app`, а UI — только
выбор представления.

### 1.6. Незакрытые проверки из §8.3

**ID:** `ARCH-TESTS`. **Приоритет:** низкий/средний.

По состоянию на 26.11.2026 остаются кандидатами на тесты:

- `platform → base.*` команды;
- `adapter → window.file_tree`;
- формат/размер проектных черновиков.

Проверка очистки после падения `register` уже покрыта
`tests/test_module_conformance.py`; пункт в старом отчёте устарел.

### 1.7. `getattr(..., "method", None)` вне SDK-мостов

**ID:** `ARCH-FALLBACK`. **Приоритет:** средний.

Архитектурный тест проверяет только `ui/platform/sdk_bridge`. Паттерн
«если метод есть — вызовем» остаётся, например:

- `ui/platform_api.py` (`close_owner_tabs`, `open_item_card_at_cursor`,
  `sort_by_files_desc`, `cancel_operation`);
- `ui/hints/context.py` (`local_sections`);
- `ui/editor_tabs.py` (`mark_clean`, `set_editable`, `flush_pending`,
  `goto_line`, `undo`, `redo`, `show_find`).

Это противоречит `AGENTS.md` §4.3 и антипаттернам целевой архитектуры
модулей. Нужно либо перейти на явные протоколы, либо зафиксировать
допустимые исключения ADR.

### 1.8. Нет ручной очистки backup миграции

**ID:** `GAP-6`. **Приоритет:** низкий.

- `.migration_backup_*` не удаляется автоматически — это правильно.
- Ручной очистки с подтверждением в диагностике/настройках нет.

### 1.9. Расхождение 19023/19024

**ID:** `PARITY-19023`. **Приоритет:** высокий для release gate.

- Игрового `game_sections.txt`/`game_properties.txt` нет.
- Расхождение задокументировано как открытое внешнее отличие, а не
  подтверждённый паритет.
- `PATCH_WRITE_EXPERIMENTAL=True` включает только экспериментальную
  запись; боевой статус не объявлен.

### 1.10. Прогресс модульных задач

**ID:** `TASK-PROGRESS`. **Приоритет:** низкий.

`TaskHandle.progress` существует, но модульные задачи в основном пишут
прогресс в `log`; точные `done/total` есть у предсборки и части
платформенных операций.

## 3. Остаточные риски

1. **События не поддерживают старые payload'ы.** Модули обязаны
   использовать `Events.*`; старые строки не поддерживаются.
2. **`SavedDraft.text` удалён.** Подписчику доступны `kind`, `key`, `path`,
   `revision`, `size`.
3. **Автосохранение фоновое.** Запись идёт в `TaskService` с coalescing;
   закрытие приложения откладывается только для активной записи.
4. **XML overlay учитывает raw XML-черновики.** `resolved_edits` относится
   к LTX; XML-resolved правки хранятся отдельно.
5. **Debounce 250 мс.** Между вводом и обновлением черновика есть задержка;
   сохранение/закрытие/смена проекта сбрасывают её.
6. **Лимит дискового кэша 1 ГБ.** Это предохранитель; поколенческая
   очистка — §1.2.
7. **Модули — доверенный код.** Process/FS-isolation нет; для сторонних
   модулей нужен отдельный plugin-host.
8. **`base` обязателен.** Отсутствие `base` не поддерживается; `unload`/
   `reload` обязательного модуля запрещены, кроме shutdown-пути.
