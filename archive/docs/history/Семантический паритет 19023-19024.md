## 2. Что означает 19023/19024

`docs/Проблема одной секции.txt` фиксирует результат другого прогона:
**19023 секции в Resolver4** и **19024 секции в игре**. Это не текущий
эталонный манифест (11870): другой VFS/набор модов/момент снятия
показаний. В репозитории нет `game_sections.txt` из игры, поэтому
назвать конкретную лишнюю секцию нельзя.

До получения игрового дампа расхождение считается **задокументированным
открытым отличием**, а не закрытым паритетом. Реестр известных отличий:
`docs/baseline/known-parity-differences.json` (сейчас пуст).

Вероятные причины из `docs/Проблема одной секции.txt`:

- runtime-секция, созданная скриптами после загрузки;
- пустая секция;
- секция, удалённая через `!![section]`, но посчитанная до удаления;
- override-only секция;
- разница `@[section]`/порядка DLTX-модов;
- служебный `generated/*.ltx`, попавший в VFS;
- разный момент снятия дампа.

## 3. Формат дампа

Краткий дамп (для сравнения имён и количества ключей):

```text
section<TAB>key_count
alpha<TAB>3
beta<TAB>5
```

Полный property-дамп (для разбора источника):

```text
section<TAB>key<TAB>value<TAB>file<TAB>depth<TAB>operation<TAB>confidence
```

Оба дампа сортируются по имени секции; property-дамп — по имени секции
и ключу. Поэтому повторный запуск на том же VFS даёт тот же результат.

## 4. Сравнение с игрой

Краткое сравнение (секции и количество ключей):

```powershell
.venv\Scripts\python.exe tools\semantic_parity.py `
    --configs "<configs>" `
    --compare game_sections.txt `
    --known docs\baseline\known-parity-differences.json
```

Полное property-сравнение (секции, ключи, значения, источники):

```powershell
.venv\Scripts\python.exe tools\semantic_parity.py `
    --configs "<configs>" `
    --compare-properties game_properties.txt `
    --source-root "<configs>" `
    --strict-row-order `
    --known docs\baseline\known-parity-differences.json `
    --report "$env:TEMP\parity-report.json"
```

Можно передать `--compare` и `--compare-properties` одновременно:
выполнятся оба сравнения, и результат будет успешным только если
зелёные оба. `--report` пишет JSON `ace-parity-report-v1` с хэшами
дампов, результатами `summary`/`properties`/`manifest` и состоянием
реестра (`known.ignored`, `known.unused`). Неиспользованная запись
реестра делает отчёт неуспешным. `known.unused` считается по фактически
выполненным сравнениям: для release gate запускайте одновременно
краткий и property-режим, иначе запись, видимая только на уровне
значений, может выглядеть неиспользованной.

Для release gate используйте `--release-gate`: он требует
одновременно `--compare`, `--compare-properties` и `--report`. В
отчёте есть `modes`, `complete`, `missing_modes` и
`release_gate_ready`; частичный отчёт может иметь `ok=true`, но
`complete=false` и `release_gate_ready=false`. `--manifest` остаётся
дополнительной проверкой и не заменяет игровые дампы.

`game_sections.txt` принимается в одном из форматов:

- `section<TAB>key_count`;
- по одному имени секции на строку;
- property-дамп с заголовком `section<TAB>key<TAB>...` — тогда
  сравниваются имена и количество строк на секцию.

В кратком режиме `--known` подавляет и отсутствие секции на одной
стороне, и разницу количества ключей; в property-режиме — все отличия
секции. Если отличие действительно было, секция попадает в
`known_ignored`.

`game_properties.txt` принимается в формате
`section<TAB>key<TAB>value<TAB>file<TAB>depth<TAB>operation<TAB>confidence`.
Сравниваются имена секций, ключи, значения, источники (`file`),
операции и глубина. Отсутствие `file` на одной стороне даёт
`source_missing`; `operation` и `depth` сравниваются только если
заполнены с обеих сторон. Пути нормализуются. Повторяющиеся ключи
(варианты регистра, list-операции) группируются; разное количество
строк попадает в `key_count_difference`. Секции из реестра известных
отличий не попадают в расхождения, но отмечаются в `known_ignored`,
если отличие было. Property-дамп содержит строки только для секций с
ключами; пустые секции проверяются кратким дампом или манифестом.
Инструмент печатает `only_resolver`, `only_game`, `only_resolver_key`,
`only_game_key`, `key_count_difference`, `value_difference`,
`source_difference`, `source_missing`, `operation_difference`,
`depth_difference`, `row_order_difference` и возвращает код 1 при
отличиях, кроме записей из реестра известных отличий.

Ограничения property-сравнения:

- повторяющиеся строки одного ключа по умолчанию сравниваются как
  мультимножество; порядок list-операций проверяется только с
  `--strict-row-order` и попадает в `row_order_difference`;
- `confidence` не сравнивается: это внутренняя оценка ACE, а не
  игровое значение;
- если одна сторона не содержит `file`, это попадает в
  `source_missing` и считается различием; полностью без источников
  игровой дамп не пройдёт property-сравнение;
- пути нормализуются через `normpath`/`normcase`; для относительных
  путей игрового дампа используйте `--source-root <configs>`, иначе
  относительный и абсолютный путь к одному файлу дадут
  `source_difference`;
- BOM в property-дампе и JSON-реестре поддерживается (`utf-8-sig`);
  CLI-режимы `--compare` и `--compare-properties` покрыты smoke-тестами.

## 5. Критерий закрытия

Расхождение 19023/19024 можно закрыть только после получения
поимённого игрового дампа:

1. снять `game_sections.txt` после полной загрузки игры и всех DLTX-модов;
2. запустить сравнение;
3. найти первую отличающуюся секцию;
4. проверить её происхождение в карточке секции;
5. либо исправить `Resolver4` (запрещено без отдельного решения и
   паритетных тестов), либо внести секцию в реестр известных отличий с
   причиной и сроком.

До этого пункт «19023/19024 объяснено или задокументировано» выполнен
как **задокументированное открытое отличие**, а не как подтверждённый
паритет.
