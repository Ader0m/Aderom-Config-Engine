# ADR-24. Асинхронная запись патч-мода и UI предпросмотра

Дата: 23.11.2026
Статус: accepted

## Контекст

К шагу 5.5 запись патч-мода выполнялась синхронно в UI-потоке:
`ProjectController.write_preview` вызывал use case, внутри которого
проходили авторизация, полный round-trip и запись файлов. Для большого
корня это блокировало интерфейс. TASK-2 оставался открытым.

UI предпросмотра показывал только часть проверки и не отделял явно
опасные изменения и полный diff.

## Решение

1. `ProjectController.write_preview` запускает `app.patching.commit.write_preview`
   через `TaskService` с `owner=project.id`; UI-поток только выбирает
   каталог, подтверждает риски и запускает задачу.
2. Результат и ошибка возвращаются в UI через `on_done`; запись не
   меняет виджеты из фонового потока.
3. Повторная запись во время активной задачи отклоняется локальным
   guard'ом `_patch_write_running` с сообщением «уже выполняется».
   Общий `operation_key`/реестр операций остаётся Этапом 6.
4. `write_preview` принимает `log`, `cancel_check` и
   `snapshot_provider`:
   - логирует прогресс по каждому файлу;
   - до/после `authorize` и после `commit` повторно читает актуальный
     `snapshot_id`; при смене VFS отменяет текущий элемент и откатывает
     уже записанные файлы;
   - проверяет отмену до и после `authorize`, а также после `commit`;
   - при ошибке/отмене удаляет все файлы, записанные этим вызовом,
     поэтому частичный патч-мод не остаётся.
5. UI предпросмотра:
   - в фоне запускает полный `PatchRoundTripVerifier` и прикладывает
     `VerificationResult` к `PreviewItem.roundtrip`;
   - `write_preview` передаёт этот отчёт в `PatchCommitService.authorize`
     как `roundtrip_report`, поэтому при записи round-trip не
     выполняется повторно;
   - отчёт — доверенный `RoundTripReport` с `plan_id` (fingerprint
     патча), `snapshot_id` и токеном конкретного
     `PatchRoundTripVerifier`; fingerprint включает `target.root_path`,
     `generated.text` и канонический набор `plan.changes`; поддельный
     `VerificationResult`, отчёт другого корня/текста/изменений/снимка/
     verifier отклоняются;
   - показывает текст сгенерированного патча/diff;
   - показывает важные проверки (`full_diff`, `source`,
     `dltx_artifacts`, `parents`, `roundtrip`) и все ошибки;
   - показывает опасные изменения плана;
   - по-прежнему позволяет исключить элемент;
   - не разрешает запись, если нет ни одного проверенного включённого
     элемента, включая успешный полный round-trip.
6. При активной записи диалог показывает кнопку «Отменить запись»;
   `cancel_patch_write` вызывает `TaskService.cancel_owner` для проекта.
   После завершения/ошибки диалог возвращается в обычное состояние.
7. Закрытие приложения не блокирует UI на 15 секунд и не разбирает окно
   заранее: `MainWindow.closeEvent` сначала вызывает `on_app_close`.
   Если идёт запись, она отменяется, закрытие откладывается
   (`event.ignore()`); после `_on_patch_write_done` окно закрывается
   повторно. Только затем выполняется окончательный `flush()`.
8. `PatchCommitResult` содержит `roundtrip_report`; audit-журнал пишет
   `status`/`reason` (`committed`, `rolled_back`, `cancelled`).
9. `PATCH_WRITE_EXPERIMENTAL` остаётся `False`; шаг не включает
   пользовательскую запись.
10. TASK-2 в части `write_preview` закрыт. На момент решения
    `on_app_close` синхронно делал `flush()` — это осознанное действие
    при закрытии, а не рабочий путь записи. Уточнение шага 6.9:
    окончательный `flush()` выполняется задачей `project.close:<id>`;
    `on_app_close` возвращает `False`, а окно закрывается после
    завершения задачи.

## Альтернативы

1. **Оставить синхронную запись.** Отклонено: блокирует UI и нарушает
   правило тяжёлых операций.
2. **Сделать отдельный `QThread` в контроллере.** Отклонено: задачи
   должны идти через платформенный `TaskService`.
3. **Показывать только patch-текст без проверки.** Отклонено: запись
   должна требовать проверенный `PreviewItem`.
4. **Ввести общий реестр операций сейчас.** Отклонено: это Этап 6;
   локальный guard — временная защита до реестра.

## Последствия

- UI остаётся отзывчивым во время round-trip и записи; отчёт
  предпросмотра переиспользуется при авторизации, повторный проход не
  выполняется.
- Прогресс виден в диагностическом журнале; отдельный progress bar и
  общий центр операций появятся на Этапе 6.
- Ошибка и отмена между файлами не оставляют частичный мод.
- Закрытие приложения откладывается до завершения записи без ожидания
  в UI-потоке и без частичной разборки окна.
- На момент решения `on_app_close` оставался синхронным исключением для
  окончательного `flush()`; шаг 6.9 вынес его в задачу
  `project.close:<id>`.
- UI показывает полный diff/проверку и риски, но не становится вторым
  источником истины: решение о записи остаётся за `PatchCommitService`.

## Срок и условия выхода

- Этап 6: `OperationRegistry`/task handle, общий прогресс и отмена
  заменяют локальный guard.
- Этап 8: release gate полного round-trip и записи.
- Включение `PATCH_WRITE_EXPERIMENTAL` — только отдельным решением
  оператора.
