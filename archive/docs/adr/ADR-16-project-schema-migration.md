# ADR-16. Схема проекта, `ProjectRepository` и one-time migration

Дата: 22.11.2026
Статус: accepted

## Контекст

Этап 3 начинается с данных проекта: `AGENTS.md` §4.1 запрещает терять и
перезаписывать пользовательские проекты, а план (§0.2, §6) требует
версию схемы и one-time forward migration с backup до переноса сценариев
из UI в `app`.

До изменения:

- `src/app/projects/service.py` одновременно читал/писал `project.json`,
  хранил черновики, собирал overlay и предпросмотр; это DATA-1;
- `project.json` не имел версии схемы: старый и повреждённый файл
  различались только по набору ключей;
- устаревшее имя режима (`in_place`) нормализовалось при каждом чтении,
  то есть legacy-алиас оставался постоянной веткой;
- one-time migration проекта отсутствовала (GAP-5);
- не было backup и диагностируемого отказа миграции.

Оператор подтвердил:

- работу над Этапом 3 и его первым шагом;
- добавление `schema_version` в `project.json` с one-time migration и
  backup.

## Решение

1. Ввести `src/app/projects/repository.py` — владельца раскладки
   каталога проекта и `project.json`:
   - `ProjectRepository.read_meta`, `validate_meta`, `write_meta`,
     `ensure_current`;
   - `write_json_atomic` — единственная реализация атомарной записи
     JSON через временный файл и `os.replace`;
   - константы `META_NAME`, `DRAFTS_DIR`, `RESOLVED_DIR`, `ASSETS_DIR`,
     `TABS_NAME` — единственный источник имён каталогов.
2. Ввести схему проекта:
   - `PROJECT_SCHEMA_VERSION = 2`;
   - v1 — плоский `project.json` без поля версии (до Этапа 3);
   - v2 — поле `schema_version` и нормализованный `save_mode`;
   - отсутствие поля читается как v1, нечисловая версия — тоже v1.
3. Миграция выполняется только вперёд, при загрузке проекта:
   - обязательные поля `id`, `name`, `save_mode`, `xml_patch_mode`
     проверяются до миграции: отсутствие или неверный тип даёт
     `ProjectError`, а не `KeyError`;
   - затем проверяются `save_mode` и `xml_patch_mode`; невалидный
     проект не перезаписывается;
   - затем создаётся backup `project_dir/.migration_backup_<timestamp>`
     с `project.json`, `drafts/`, `resolved/`, `assets/`, `tabs.json`;
   - `project.json` пишется атомарно; при ошибке исходный файл остаётся
     нетронутым, backup сохраняется, пользователь видит `ProjectError`;
   - повторная загрузка уже мигрированного проекта backup не создаёт.
4. Проект с версией схемы новее текущей отклоняется с `ProjectError`:
   старый код не пытается угадать чужой формат.
5. `ProjectService` остаётся сессией проекта (активный проект, overlay,
   черновики, предпросмотр) и делегирует чтение/запись
   `project.json` репозиторию. Публичное поведение и сигнатуры
   `ProjectService` не меняются.
6. `DraftStore`, single-writer, `ProjectSession`, вынос use cases из
   UI, `ResolvedDocumentSession` и асинхронное автосохранение — следующие шаги
   Этапа 3. Этот ADR их не вводит и не отменяет.

## Альтернативы

1. **Оставить `project.json` без версии, определять формат по ключам.**
   Отклонено: нельзя отличить старый проект от повреждённого и от
   проекта более новой версии; нет основания для миграции.
2. **Мигрировать лениво, только при следующей записи.** Отклонено:
   миграция была бы невидимой, без backup в предсказуемый момент; при
   ошибке пользователь узнал бы о ней позже.
3. **Хранить backup рядом с каталогом проекта.** Отклонено: `list_projects`
   сканирует корни проектов, соседний каталог попал бы в список.
   Вложенный `.migration_backup_*` список не засоряет.
4. **Оставить нормализацию `in_place` на чтении.** Отклонено: §0.2
   требует удалить постоянную ветку чтения старого формата после
   миграции.
5. **Перенести сразу весь `ProjectService` в репозиторий и `DraftStore`.**
   Отклонено на этом шаге: слишком крупное изменение; план §6 требует
   двигаться по одному use case, сохраняя зелёные тесты.

## Последствия

- `project.json` получает поле `schema_version`; старые сборки ACE
  игнорируют незнакомый ключ, но обратная совместимость формата не
  поддерживается и не гарантируется.
- Первая загрузка проекта v1 создаёт backup в каталоге проекта; backup
  не является проектом и не участвует в списке проектов.
- Ошибка чтения, проверки или миграции не закрывает активный проект:
  пользователь видит сообщение, данные остаются на месте.
- `ProjectService.load` по-прежнему синхронный: миграция и backup
  выполняются в вызывающем потоке (сейчас — UI). Это унаследованный
  путь загрузки, зафиксированный как временное исключение PROJECT-LOAD
  в `docs/Миграционные исключения.md`; срок закрытия — Этап 3.5/6,
  перенос в `ctx.tasks`. Busy-индикатор `_set_project_loading`/`repaint`
  сохраняется, чтобы ожидание было видно.
- Ручная очистка `.migration_backup_*` не реализована (GAP-6, будущая
  диагностика с подтверждением); автоматическое удаление запрещено.
- Запись `project.json` сериализуется замком репозитория; запись
  черновиков по-прежнему идёт под замком сервиса — один писатель на
  файл.
- `_write_meta` и `_write_json_atomic` удалены из сервиса: второго пути
  записи `project.json` нет.

## Срок и условия выхода

- Решение действует до появления схемы v3.
- При схеме v3 добавляется миграция v2 → v3; код v1 → v2 остаётся
  единственным путём для старых проектов и удаляется только вместе с
  поддержкой v1.
- После закрытия Этапа 3 миграция не расширяется «на будущее»: каждое
  изменение схемы — отдельный шаг с backup и тестами.
