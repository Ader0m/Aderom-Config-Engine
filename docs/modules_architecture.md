# Архитектура модулей

Документ описывает, как модуль встраивается в приложение, какие границы он
не должен нарушать и как модули сосуществуют друг с другом.

## 1. Слои и ответственность

| Слой | Отвечает за |
|---|---|
| `core` | Дерево файлов, резолвер, сборка, граф связей, файловые операции |
| `ui` | Главное окно, редактор, меню, хостинг окон модулей, задачи, шины |
| `sdk` | Единственный публичный контракт между модулями и приложением |
| `modules` | Сценарии, команды, окна и представления конкретных модулей |

Модуль зависит **только от `sdk`**. Он не импортирует `core` и внутренности
`ui`. PyQt допустим только для собственных окон и виджетов модуля.

Публичная поверхность `core` — `core/__init__.py`, `core/facade.py` и
`core/models.py`. Остальное сгруппировано по ответственности:

```text
core/tools/      файлы, пути, кэш, процессы, текст
core/tree/       дерево файлов, запросы, граф связей, include/DLTX-модели
core/resolver/   LTX-резолвер, сборка, предсборка, атрибуция
core/xml/        SLAXML, DXML, XML-резолв
core/items/      DDS, каталог предметов, иконки, локализация
core/patching/   общие модели/цели/писатель
  ltx/           DLTX: документ, diff, план, генератор, проверка, режимы
  xml/           XML/DXML: документ, diff, план, генератор, проверка, форк
```

`core/patching/ltx` и `core/patching/xml` имеют симметричный вход:
`LtxPatchService.plan(...)` и `XmlPatchService.plan(...)`, а внутри —
одинаковый маршрут `document → diff → planner → generator → verifier`.

`base_module` — обязательный модуль платформы. Он загружается всегда и задаёт
базовый пользовательский сценарий: открытие каталога, построение дерева,
просмотр `.ltx`, просмотр игровых предметов, базовые действия дерева и
редактора. При этом он использует тот же SDK, что и остальные модули, и не
имеет доступа к внутренностям UI. Окно предметов — часть базового модуля,
поэтому его нельзя выключить отдельно; модуль, которому нужен перенос
предметов, объявляет зависимость `requires=("base",)`.

В дерево попадают и `.xml`-файлы VFS. По умолчанию XML открывается
через `XmlResolver` (include-сборка + DXML). Проектный `ProjectOverlay`
учитывается и здесь: XML-черновики проекта подменяют содержимое
include-файлов, а новые XML-файлы участвуют в масках `*.xml`. Исходный
текст доступен отдельно — «Открыть исходный XML» в редакторе приложения
или «Открыть XML в Notepad++». Резолв-путь `.ltx` при этом не меняется.

Для XML также доступен `XmlResolver` (`core/xml/resolver.py`) —
Python-порт логики движка `themrdemonized/xray-monolith`:
`CXml::ParseFile` (include-сборка относительно `$game_config$`,
включая `*.xml`) и `COnXmlRead`/DXML (`dxml_core.script`,
`xml_obj`, `on_xml_read`). Штатные `modxml_*.script` портированы в
`core/xml/dxml.py`; остальные Lua-патчи не исполняются и попадают в
`XmlResolveResult.notes`. XML читается строго как `windows-1251`
(с отбрасыванием BOM), без автоопределения кодировки. Для результата
строится построчная атрибуция, как у LTX: `оригинал`, включённый файл
или `DXML: <скрипт>`; она показывается в той же панели источников.

Для XML работает тот же патч-конвейер, что и для LTX:
`xml_model` → `xml_diff` → `XmlForkService` / `PatchPlanner` →
`DxmlGenerator` → `XmlModelPatchVerifier` / `XmlResolverPatchVerifier` →
`PatchWriter`. Поддерживаются правки атрибутов, текста, добавление/удаление
элементов.

Режим «XML-файлы» (`auto`/`xml`) работает как форк ключа:

- изменённый элемент с `id`/`name` копируется в новый XML с новым ключом
  (`<old>_ace_<project>`; для блока без ключа — `ace_<project>`);
- старый ключ остаётся в исходном файле;
- ссылки на старый ключ в LTX меняются по настройке DLTX проекта
  (Root, On-file или Override);
- ссылки в XML меняются по настройке DXML проекта: DXML-Lua создаёт
  скрипт, XML/Override — полную копию XML-файла;
- ссылки в `gamedata/scripts` не патчатся и показываются предупреждением.

Режим `dxml_lua` оставлен для правки XML на месте: он генерирует
`gamedata/scripts/modxml_*.script` и не создаёт новый ключ.
On-file использует обычное планирование Root на каждый изменённый файл:
целью всегда является корень загрузки, поэтому `mod_<root>_*.ltx`
действительно загружается движком. Отдельные патч-файлы на каждый файл
собирает уровень проекта. Override (`core/patching/ltx/override.py`)
пишет полную копию победителя.
Единые входы планирования — `core/patching/ltx/service.py` и
`core/patching/xml/service.py`.
Остальные модули дополняют приложение и не должны требовать своего порядка
загрузки. Любой дополнительный модуль может быть не загружен — приложение
обязано сохранять работоспособность без него.

## 2. Что модуль получает через SDK

`ctx` — единственная точка входа. Для каждого модуля создаётся свой экземпляр
контекста; это не глобальный синглтон.

| Поле | Назначение |
|---|---|
| `ctx.services` | `CoreApi`: дерево, резолвер, сборка, граф, чтение файлов |
| `ctx.ui` | `UiApi`: меню, статус, диалоги, редактор, окна модулей |
| `ctx.tasks` | `TaskApi`: фоновые задачи |
| `ctx.events` | Шина событий: факты (`publish`) и перехватываемые UI-действия (`dispatch`) |
| `ctx.commands` | Шина команд: намерения с одним обработчиком |
| `ctx.ui.theme_color` | Цвет темы по токену, без импорта `ui.theme` |
| `ctx.paths` | Пути приложения |

`ctx.events` и `ctx.commands` — SDK-адаптеры, а не сами шины. Модуль не
видит внутренние словари подписчиков и обработчиков и не может обойти
контракт. `ModuleLoader` находится на стороне платформы (`ui.module_loader`),
а не в SDK: SDK не должен импортировать пакет модулей.

Правила:

- всё взаимодействие с ядром и платформой — только через `ctx`;
- нельзя обращаться к `MainWindow`, `file_tree`, `editor` и другим внутренностям UI;
- нельзя импортировать другой модуль и вызывать его объекты напрямую;
- общие объекты ядра (`forest` и т.п.) модуль считает read-only;
- имена команд, событий, окон и действий должны быть namespaced: `<module>.<name>`.

## 3. Lifecycle

Загрузчик находит пакеты `modules.<name>`, проверяет `manifest.sdk_min`,
зависимости `manifest.requires` и вызывает фазы жизненного цикла. Модуль с
незагруженной зависимостью пропускается с сообщением в журнале; ошибка
`init`/`register`/`activate` одного модуля логируется и не останавливает
остальные. Например, `ogg_editor` объявляет `requires=("base",)` и может
рассчитывать на обязательное окно предметов базового модуля.

```text
discover
   ↓
init        — создать состояние, подписаться на события
   ↓
register    — зарегистрировать меню, команды, обработчики, действия
   ↓
построение главного окна
   ↓
activate    — модуль может создавать окна и запускать отложенную работу
   ↓
runtime     — события, команды, фоновые задачи, окна
   ↓
deactivate  — закрыть окна, остановить свою активность
```

### `init(ctx)`

- создать внутреннее состояние модуля;
- подписаться на события;
- определить каталоги/настройки, но не выполнять тяжёлую работу;
- не создавать окна и не обращаться к ещё не созданному главному окну.

### `register(ctx)`

- зарегистрировать пункты меню и горячие клавиши;
- зарегистрировать команды `ctx.commands.register(...)`;
- зарегистрировать контекстные действия дерева;
- зарегистрировать обработчики открытия файлов;
- не создавать окна и не запускать длительные операции.

### `activate(ctx)`

- главное окно уже существует;
- можно создавать окна модуля и подготавливать представления;
- тяжёлую работу запускать через `ctx.tasks.run(...)`.

### `deactivate(ctx)`

- закрыть окна модуля;
- прекратить фоновую активность;
- не удалять чужие данные и не менять состояние других модулей.

`ctx.events.subscribe(...)` возвращает подписку с методом `unsubscribe()`.
Модуль обязан хранить подписки и отписываться в `deactivate`, иначе после
выгрузки модуля его обработчики продолжат получать события.

`publish` можно вызывать из фонового потока: подписчики получат событие в
потоке UI. `ctx.tasks.run(...)` также гарантирует, что `on_done` и `on_log`
вызываются в потоке UI.

## 4. Параллельная работа модулей

Модули работают в одном процессе, но являются независимыми возможностями.

- Поток UI один: менять виджеты можно только в главном потоке.
- Долгие операции — только через `ctx.tasks.run(...)`.
- Модули не должны полагаться на порядок загрузки друг друга.
- Дополнительный модуль может быть отключён; остальные не должны от него зависеть.
- Нельзя хранить ссылки на объекты другого модуля.
- Взаимодействие — через события и команды.
- Ошибка одного модуля не должна ломать остальные: загрузчик изолирует
  исключения `init`/`register`/`activate`, шина событий логирует ошибки
  подписчиков, задачи возвращают ошибку в `on_done`.
- Общие ресурсы (`core`-сервисы) не мутируются модулями напрямую.

`base_module` — исключение: он является обязательной частью платформы.
Дополнительные модули могут использовать его публичные команды и события,
но не его внутренние классы.

экспортируется как `sdk.DEFAULT_SEARCH_DELAY_MS`; модули используют это
значение, а не собственные интервалы, чтобы поведение поиска было
одинаковым во всех окнах.

### Двоичные ресурсы проекта

Проект изначально хранил только текстовые черновики `.ltx`/`.xml`.
Ресурсы вне `configs` (звуки, текстуры, модели) не имеют текстового
представления, поэтому для них добавлен отдельный — двоичный — черновик
`ProjectAssetDraft`:

- `ctx.ui.read_project_asset(path)` — текущие байты черновика или `None`;
- `ctx.ui.update_project_asset(path, data)` — изменить черновик в памяти;
- `ctx.ui.save_project_asset(path, data=None)` — записать в каталог проекта;
- `ctx.ui.project_asset_drafts()` — список `AssetDraftInfo`;
- `Events.PROJECT_SAVED` (`project_saved`) — черновик записан (payload —
  `SavedDraft` с `kind == "asset"`).

Двоичные черновики участвуют в обычном автосохранении, `Ctrl+S`, закрытии
приложения и попадают в патч-мод как файл `gamedata/<root>/<...>` целиком.
Каталог `Overwrite` по-прежнему запрещён. Проект не меняет оригинальные
файлы.

Конкретные расширения не зашиты в `core`/`ui`. Модуль регистрирует тип
ресурса в `register(ctx)`:

```python
from sdk import ProjectAssetType

ctx.ui.register_project_asset_type(
    ProjectAssetType(
        key="sound.ogg",
        label="Звук Ogg Vorbis",
        extensions=(".ogg",),
        vfs_root="sounds",
    )
)
```

Реестр проверяет ключ, расширения, один каталог `vfs_root` и конфликты
`(vfs_root, extension)`. На его основе проект проверяет путь, строит
элемент предпросмотра и передаёт `PatchWriter` правила
`{root: расширения}`. Модуль снимает тип в `deactivate`; при выгрузке
модуля поддержка исчезает, и проект показывает ошибку для таких
черновиков, а не пишет их вслепую.

### Настройки проекта

Модуль может добавить в окно «Настройки проекта» собственные поля.
Значения хранятся в `project.json` (`module_settings`) и доступны модулю
через SDK:

```python
from sdk import ProjectSetting, ProjectSettingChoice

MODE = ProjectSetting(
    key="example_module.mode",
    label="Режим модуля",
    kind="choice",
    default="default",
    choices=(
        ProjectSettingChoice(value="default", label="Обычный режим"),
        ProjectSettingChoice(value="advanced", label="Расширенный режим"),
    ),
)

def register(self, ctx):
    ctx.ui.register_project_setting(MODE)

def deactivate(self, ctx):
    ctx.ui.unregister_project_setting(MODE.key)

def save(self):
    mode = self.ctx.ui.project_setting(MODE.key, MODE.default)
```

Конкретные ключи и подписи задаёт модуль; SDK и UI знают только
описание настройки.

Поддерживаются типы `choice`, `bool` и `text`. Диалог сам строит виджет
по описанию настройки, поэтому UI не знает про конкретные модули.


Тип ресурса отвечает на вопрос «можно ли это записать в патч». Отдельный
вопрос — «как показать файл пользователю». Для него модуль регистрирует
`FileReader`:

```python
from sdk import FileReader, FileView

class OggCommentReader(FileReader):
    priority = 100

    def can_read(self, path, data=None):
        return path.suffix.lower() == ".ogg"

    def read(self, path, data=None):
        return FileView(
            text="...итоговый вид комментария...",
            label="Комментарии Ogg Vorbis",
            details=("X-Ray v3",),
        )

ctx.ui.register_file_reader(OggCommentReader())
```

Проект выбирает первый подходящий читатель по `priority` и `can_read`.
`read` возвращает `FileView` — ровно один итоговый вид файла. Сейчас он
используется в предпросмотре патча; тот же реестр можно использовать для
поиска по содержимому, экспорта и других сценариев.

Почему делегат, а не событие:

- чтение — чистая трансформация «путь + байты → представление», а не
  факт, на который может быть много независимых реакций;
- нужен детерминированный выбор одного читателя с приоритетом;
- предпросмотр выполняется в фоновом потоке, поэтому читатель не должен
  работать с Qt и обязан быть потокобезопасным;
- `register_file_reader` возвращает подписку с `unsubscribe()`, и модуль
  снимает читатель в `deactivate`.

Если читатель не зарегистрирован, проект показывает безопасный fallback
(«Двоичный файл: N байт»). Ошибка читателя не блокирует запись патча, но
попадает в заметки предпросмотра.

### Перенос предмета между модулями

Окно предметов базового модуля формирует `QDrag` с MIME-типом
`ITEM_SECTION_MIME`; внутри — имя секции и все её поля в формате
`encode_item_section(...)`. Принимающий модуль декодирует данные через
`decode_item_section(...)` и сам решает, что с ними делать. Это не создаёт
импорт между модулями: общий контракт живёт в `sdk.dragdrop`, а не в окне
предметов. Базовый модуль обязателен, поэтому OGG-модуль объявляет
`requires=("base",)` и может рассчитывать на наличие источника drag-and-drop.
Главное окно приложения принимает такой drop без собственной логики — только
чтобы перенос не считался неудачным; обработка остаётся модулям-получателям.

Модуль `ogg_editor` использует эту инфраструктуру для правки
Vorbis-комментариев. Важно: движок X-Ray (`SoundRender_Source_loader.cpp`)
читает **первый** Vorbis-комментарий как бинарную структуру little-endian
(`version`, `min_dist`, `max_dist`, `base_volume`, `game_type`,
`max_ai_dist`), а не как текст. Поэтому вкладка модуля показывает
человекочитаемые поля, а при сохранении пересобирает только служебные
страницы Ogg; аудиопакеты не перекодируются.

Для прослушивания `.ogg` используется `soundfile` (libsndfile): он
декодирует текущий контейнер в временный WAV, который воспроизводит
`QMediaPlayer`. Это обходит отсутствие системного Ogg/Vorbis-кодека в
Windows. Если `soundfile` недоступен, модуль пытается отдать `.ogg`
напрямую QtMultimedia.

Граф связей секции запрашивается через
`ctx.services.build_section_graph(forest, section_name, vfs_mode=False)`.
В обычном режиме поиск идёт по **итоговым файлам резолвера** (LTX-корням):
перед резолвом каждого корня ядро проверяет `ResolvedCache`, поэтому
повторные запросы графа и открытие файлов не запускают Resolver4 заново.
После `TREE_READY` ядро запускает фоновую предсборку LTX-корней и
XML-файлов; прогресс показывается панелью «Сборка x/n» в правом нижнем
углу. XML проходит include-сборку и DXML, поэтому его результаты тоже
кладутся в общий `ResolvedCache`, а поиск по XML в графе не разбирает
файлы заново.
Предсборка использует пул процессов (~75% логических CPU, минимум один
остаётся системе/UI), потому что Resolver4 и XmlResolver — Python-код и
потоки не дают ускорения из-за GIL. Дисковый кэш переживает перезапуск:
ключ LTX включает mtime/size/ctime файла и всех его
include/DLTX-зависимостей, а также подпись `Resolver4.py`; ключ XML —
include-дерево, подпись `dxml_core.script`/`modxml_*.script` и версию
логики XML-резолва. Подписи считаются по поддереву конкретного файла,
без глобального обхода всего леса. Чтобы открытие уже собранного файла
не пересчитывало подпись заново, `ResolverService` кэширует готовый ключ
на время жизни дерева, а `XmlResolver` — список include-зависимостей с
проверкой их mtime/size/ctime. Сброс — при «Чистом запуске»/`refresh()`.
В `line_sources` одинаковые источники разделяются одним объектом
`LineSource` (system.ltx даёт больше миллиона строк при ~1000 уникальных
источниках), иначе pickle-кэш на диске читается секундами.
При `vfs_mode=True` ядро обходит все текстовые файлы VFS
(`.ltx`, `.xml`, `.script`, `.lua`) без резолва — это диагностический
режим для «потерянных» связей. XML-файлы, уже найденные итоговым
графом, не попадают в потерянные: для XML сравнение идёт по файлу,
а не по строке (форматирование и номера строк могут отличаться).
Узлы графа несут флаг `resolved`:
`True` — строка относится к итоговому файлу, `False` — к исходному.
Открытие узла идёт через общую шину: `ctx.ui.open_at_line` для
резолва (обработчик сам использует кэш) и `ctx.ui.open_raw_at_line`
для сырых/VFS-узлов.
Для ссылок на ресурсы секции (`icons_texture` → `.dds`, `visual` →
`.ogf`) узел дополнительно содержит `target_path` — полный путь к
файлу от корня VFS (`textures/` или `meshes/`). Текстуры открываются
приложением Windows через `ctx.services.open_with_shell`; для запуска
используется `physical_path`: ядро разрешает VFS-путь в реальный через
`GetFinalPathNameByHandle`/`Path.resolve`, а при активном MO2/usvfs и
недоступности реального пути создаёт временную копию. Если ассоциация
не настроена, оболочка показывает диалог «Открыть с помощью…».
Визуальные модели `.ogf` обычно упакованы в игровые архивы, поэтому
открытие для них заменено заглушкой: показывается сообщение, внешняя
программа не запускается. Тип каждой связи (`declaration`,
`inheritance`, `ltx_reference`, `script_reference`, `xml_reference`,
`texture_reference`, `visual_reference`) показывается маркером в
начале строки и цветом из `ui.theme.PALETTE`; файл выводится только
именем, полный путь остаётся в tooltip и в узле.
Для наследования (`[секция]:p1,p2`) каждый родитель показывается
отдельной строкой `[Наследование]`: родители из заголовка самой
секции и связи «дочерняя секция → родитель» из других файлов. Это
касается и режима VFS: перекрытые родительские связи попадают в
`lost_children` и видны в панели потерянных связей. Двойной клик по
строке родителя открывает объявление этого родителя (файл и строку),
а не заголовок искомой секции.

Каталог предметов также собирается ядром: оно разрешает `system.ltx`
(поэтому учитываются `mod_system_*.ltx`), берёт из него предметные
секции и возвращает плоские записи с эффективными `icons_texture` и
`inv_grid_*`. Для урезанных VFS остался fallback на
`items.ltx`/`item_base.ltx`. Декодирование DDS в RGBA (`read_texture_region`) тоже
живёт в `core`; модуль получает готовые байты и только рисует иконку.
Поэтому модуль не импортирует ни `core`, ни `ui.theme`.

Каталог и иконки кэшируются по снимку VFS: каталог — память + диск
(подпись include/DLTX-поддерева), регионы иконок — LRU в памяти, а
пакет иконок — gzip+pickle на диске (подписи DDS-атласов). Для
декодирования DXT/несжатых DDS используется пул процессов, как у
предсборки LTX/XML: это Python-код, и потоки не дают ускорения из-за
GIL. Модуль лишь передаёт готовые RGBA в `QImage`.

Текст `inv_name`/`description` ядро берёт из строковых таблиц
`configs/text/<lang>/*.xml`: сначала загружается `eng`, затем `rus`
(если есть), поэтому русские строки перекрывают английские, а
отсутствующие остаются английскими. Ключ — атрибут `id` у
`<string>`, значение — текст `<text>`. Готовая строка попадает в
`ItemEntry.name_text`/`description_text`.

Правка поля в карточке меняет соответствующую строку resolved-текста
`system.ltx` в resolved-черновике проекта. Открытая resolved-вкладка
обновляется точечно (без замены всего 17-МБ текста). Без активного
проекта правка запрещена; сохранение — обычное проектное: `Ctrl+S`,
автосохранение раз в минуту и при закрытии.

Название и описание — не поля `system.ltx`, а строки
`text/<lang>/*.xml`. Поэтому они редактируются в карточке напрямую:
ядро находит XML-документ (включая `#include`-фрагмент), который дал
победивший перевод, и меняет только `<text>` нужного `<string id>`.
В обычном состоянии оба поля выглядят как часть карточки; клик по ним
включает ввод, а потеря фокуса или `Ctrl+Enter` применяет правку.
Описание при этом рисуется так же, как его показывает движок:
`CUILines` разбирает только литерал `\n` как перевод строки (реальные
CR/LF/TAB в шрифтовом атласе имеют нулевую ширину), `%c[default]` — как
цвет текста карточки, `%c[a,r,g,b]` — как ARGB, а именованные метки
берутся из `configs/ui/color_defs.xml` (с учётом overlay проекта). После
`%c[` в редакторе появляется выпадающий список цветов с фильтрацией по
вводу; список перечитывается после сохранения проекта. В режиме
правки литералы `\n` превращаются в настоящие переносы строк, а их
места помечаются призрачными значками `\n`; метки `%c[...]` остаются
видимым текстом. Под редактором справа появляется кнопка «Сохранить»
(потеря фокуса и `Ctrl+Enter` продолжают работать). Реальные CR/LF/TAB
из форматирования XML в редактор не попадают — они удаляются так же,
как их игнорирует движок. При записи XML после каждого литерала `\n`
добавляется настоящий перенос строки с таб-отступом: игра его не
видит, а файл остаётся читаемым. ПКМ по названию, описанию или
текстовому полю (`inv_name`, `inv_name_short`, `description`) даёт
«Открыть XML»: исходный XML открывается на строке объявления
`<string id="...">` через `open_raw_at_line`. Разбор вынесен в
`sdk/engine_text.py`, поэтому модуль по-прежнему не импортирует
`core`.
Новый текст сразу попадает в черновик проекта, а `LocalizationService`
читает XML вместе с overlay проекта — карточка показывает ровно то,
что будет сохранено, ещё до сборки патча. Дальше действует выбранный
режим XML-патча: `DXML-Lua` правит XML на месте, `XML` форкает ключ и
перепривязывает ссылки, `Override` делает полную копию файла. Для
новых XML-файлов проекта (например, `st_ace_<проект>.xml`) overlay
учитывается при загрузке языка, поэтому созданный предмет не остаётся
с «сырым» ключом вместо названия.

Право на правку карточка не кеширует при отрисовке: оно проверяется в
момент клика по названию/описанию и в момент открытия редактора ячейки
таблицы. Поэтому проект, созданный уже после открытия окна или вкладки
предмета, включает редактирование без пересборки этих окон. На
`project_changed` модуль возвращает удержанный resolved-документ
каталога в реестр платформы (она освобождает живые документы при смене
проекта); каталог и окно при этом не пересобираются, а без активного
проекта правка остаётся запрещённой.

Запись XML-черновика и последующая пересборка карточки выполняются в
фоне через `ctx.tasks`: на один файл одновременно работает не более
одной задачи, а повторный текст ставится в очередь. На время записи
вкладка получает «часики», карточка блокирует ввод и показывает
курсор ожидания. Тяжёлый `json.dumps`/запись файла и повторный разбор
локализации не выполняются в UI-потоке.

Окно создаёт сам модуль. Платформа предоставляет родительское окно,
показывает его, поднимает, активирует и хранит по ключу. `src/ui` не должен
знать, что именно показывает модуль.

Вкладку редактора тоже создаёт модуль: он передаёт свой `QWidget` в
`open_editor_tab`. Платформа владеет контейнером вкладок, их показом и
закрытием, а базовый редактор — зарезервированная вкладка `ui.editor`.
Повторное открытие с тем же `tab_id` заменяет содержимое вкладки.

`register_menu`, `register_shortcut` и `register_mouse_binding` принимают
необязательный `action`. Если он задан, перед вызовом callback платформа
рассылает это действие через `dispatch`: другой модуль может перехватить его
и отменить стандартное поведение. Без `action` всё равно рассылаются общие
действия `ui.shortcut` и `ui.mouse`.

Модуль не устанавливает глобальные Qt-хуки и не обходит SDK.

## 6. События и команды

- **Событие** — факт: «дерево построено», «файл открыт», «окно запрошено».
  Подписчиков может быть несколько, отменить событие нельзя.
- **Команда** — намерение: «открыть окно», «запустить сборку». У команды один
  обработчик, она может вернуть результат.
- События платформы имеют префикс `ui.`, базового модуля — `base.`,
  остальные модули используют свой префикс.
- Если нужен именно перехват с отменой или приоритетом, используется
  `FileOpenHandler` или команда, а не событие.

- **UI-действие** — запрос, который можно перехватить: «нажата клавиша»,
  «пользователь выбрал пункт меню», «клик в дереве». Рассылается через
  `EventBus.dispatch`; первый обработчик, вернувший truthy, отменяет
  стандартное поведение.

`ctx.events.subscribe(name, handler, priority=0)` возвращает подписку.
Чем выше `priority`, тем раньше вызывается обработчик; при равном приоритете
сохраняется порядок регистрации. Также доступны `ctx.events.unsubscribe(...)`
и `ctx.events.has(name)`.

```python
sub = ctx.events.subscribe(Events.UI_TAB_OPENED, self._on_tab, priority=10)
...
sub.unsubscribe()
```

`ctx.events.publish(name, payload)` — факт, вызываются все подписчики.
`ctx.events.dispatch(name, payload) -> bool` — перехватываемое действие.

События платформы:

```text
file_opened              (FileOpened)      publish
file_open_failed         (FileOpenFailed)  publish
project_saved            (SavedDraft)      publish
project_changed          (Project|None)    publish
ui.window.shown          (key)             publish
ui.window.closed         (key)             publish
ui.tab.opened            (tab_id)          publish
ui.tab.closed            (tab_id)          publish
ui.tab.changed           (tab_id | None)   publish
ui.shortcut              ({key, scope})    dispatch
ui.mouse                 ({scope, button, modifiers, event}) dispatch
```

`file_opened` публикуется UI-слоем **после** размещения виджета и
переключения на него, а не маршрутизатором в момент выбора обработчика.
Событие приходит из всех путей открытия: модульная вкладка (`open_tab`,
включая повторное использование виджета), сырой файл (`open_file`) и
дефолтная вкладка (`show_text`). Payload — путь файла (или label, если
путь неизвестен). `file_open_failed` публикуется, если открытие не
состоялось (например, ошибка фоновой сборки резолва).

Платформа хранит отложенную навигацию (поиск/переход к строке) ключом по
пути и применяет её только к событию `file_opened` с этим же путём. Не
следует привязывать навигацию к `ui.tab.changed` или читать
`currentWidget()` сразу после запроса открытия: для асинхронного резолва
`.ltx` вкладка создаётся заметно позже.

`ui.window.requested`, `ui.tab.requested` и `ui.file.open_requested` —
зарезервированные имена для запросов между модулями. Платформа
рассылает их через `dispatch`, но модульных обработчиков по умолчанию
нет: модуль сам подписывается, если умеет открывать окно/вкладку.

Чтобы перехватить UI-действие, модуль регистрирует обработчик:

```python
sub = ctx.ui.register_action_handler(
    "my_module.toggle",
    self._on_toggle,
    priority=100,
)

def _on_toggle(self, payload):
    ...
    return True  # действие перехвачено, стандартный callback не вызывается
```

Если событие платформы нужно именно **перехватить** с приоритетом или
возможностью отменить стандартное поведение, используется цепочка
обработчиков (как `FileOpenHandler` для файлов) или `dispatch`, а не
подписка на событие.

Важно не смешивать роли шин:

- запрос данных у ядра — `ctx.services`;
- намерение выполнить действие — `ctx.commands`;
- уже произошедший факт — `ctx.events.publish`;
- перехватываемое UI-действие — `ctx.ui.register_action_handler` /
  `ctx.events.dispatch`.

Модуль не устанавливает глобальные Qt-хуки и не обходит SDK.

## 7. Скелет модуля

```python
from sdk import ModuleBase, ModuleManifest
from sdk.events import Events


class MyModule(ModuleBase):
    manifest = ModuleManifest(
        name="my_module",
        version="0.1.0",
        sdk_min="0.1.0",
    )

    def init(self, ctx):
        super().init(ctx)
        self._window = None
        self._tab = None
        self._subs = []
        self._subs.append(
            ctx.events.subscribe(
                "ui.window.requested",
                self._on_window_requested,
            )
        )

    def register(self, ctx):
        ctx.ui.register_menu(
            "Мои окна",
            "Окно 1",
            self.show_window,
            "Ctrl+1",
            action="my_module.show_window",
        )
        ctx.ui.register_shortcut(
            "Ctrl+Alt+T",
            self.show_tab,
            scope="global",
            action="my_module.show_tab",
        )
        ctx.commands.register("my_module.show_window", self.show_window)

        # Перехват действия: вернуть True — значит отменить стандартный callback.
        self._subs.append(
            ctx.ui.register_action_handler(
                "my_module.show_window",
                self._on_show_window_action,
                priority=100,
            )
        )

    def activate(self, ctx):
        ctx.log("my_module активирован")

    def deactivate(self, ctx):
        for sub in self._subs:
            sub.unsubscribe()
        self._subs.clear()

        if self._tab is not None:
            ctx.ui.close_editor_tab("my_module.tab")
            self._tab = None

        if self._window is not None:
            ctx.ui.close_module_window("my_module.window")
            self._window = None

    def _on_window_requested(self, window_id):
        if window_id == "my_module.window":
            self.show_window()

    def _on_show_window_action(self, payload):
        # Условный пример: не перехватываем, пусть сработает стандартный callback.
        return False

    def show_window(self):
        if self._window is None:
            self._window = MyWindow(self.ctx.ui.open_at_line)
        self.ctx.ui.show_module_window("my_module.window", self._window)

    def show_tab(self):
        if self._tab is None:
            self._tab = MyTabWidget()
        self.ctx.ui.open_editor_tab(
            "my_module.tab",
            "Моя вкладка",
            self._tab,
        )


MODULE = MyModule()
```

## 8. Чек-лист модуля

- [ ] импортирует только `sdk` (и PyQt для своих окон);
- [ ] не знает про `MainWindow` и внутренние виджеты UI;
- [ ] все имена команд/событий/действий/окон/вкладок namespaced;
- [ ] тяжёлая работа — в `ctx.tasks`;
- [ ] окна и вкладки создаются в `activate`/по действию, а не в `init`;
- [ ] подписки сохраняются и отзываются в `deactivate`;
- [ ] при `deactivate` окна и вкладки закрываются;
- [ ] модуль не зависит от порядка загрузки других модулей;
- [ ] ошибки не выходят наружу и не ломают платформу.


## 9. Контракты после рефакторинга

- `ctx.ui.register_file_action(label, handler, predicate=None)` — действие
  в контекстном меню вкладки файла. Платформа не знает имён команд модуля.
- `ctx.ui.refresh_workspace()` — пересобрать виртуальные файлы проекта в
  текущем лесе. Модуль не вызывает `add_virtual_file` напрямую.
- `ctx.ui.workspace_forest()` / `workspace_generation()` — актуальный лес
  и номер его поколения; владелец — `WorkspaceService` платформы.
- `ctx.commands.register("module.action", fn)` проверяет namespace:
  команда должна начинаться с `<manifest.name>.`. Повторная регистрация
  чужой команды запрещена; `unregister` снимает только свою.
- `register_open_handler` передаёт модульному обработчику его
  `ModuleContext`, а не `PlatformApi`.
- `ctx.ui.request_window`, `request_tab`, `request_file_open` — стандартные
  перехватываемые запросы между модулями.
- `ctx.events.dispatch` разрешён только из UI-потока. Из фонового потока
  используйте `publish` или отложенный вызов в UI-поток.
- `PROJECT_SAVED` payload типизирован как `sdk.SavedDraft`.
- `FILE_OPENED` payload — `sdk.FileOpened`; `FILE_OPEN_FAILED` —
  `sdk.FileOpenFailed`. Старые строковые payload не поддерживаются.
- Старые resolved-черновики читаются, но при сохранении переводятся в
  компактный формат v3: уникальные `LineSource`, сжатые индексы строк и
  zlib-сжатие крупных текстовых полей. `original_text`/`saved_text` не
  дублируются, если совпадают с `current_text`.
- LTX-разбор для навигации/правок один: `core.patching.ltx.document`.
  Resolver4 остаётся сборщиком итогового текста, а не заменой парсеру.
- Прикладной слой проекта и документов — `app.projects`, `app.documents`,
  `app.workspace`; он не импортирует Qt.
