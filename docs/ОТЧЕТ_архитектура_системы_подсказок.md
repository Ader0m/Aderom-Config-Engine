# Отчёт: архитектура системы подсказок в редакторах ACE

Статус: черновик + детальный проект (версия 2, без кода)  
Область: UI-редакторы, автодополнение, подсказки по контексту  
Текущая реализация: прототип подсказки цветов в карточке предмета  
Детальный проект: часть II, разделы 13–32

> Часть I (разделы 1–12) — аудит текущего прототипа и первичные предложения.
> Часть II — уточнённый проект системы с учётом реальных границ слоёв,
> жизненного цикла окон, двух backend-ов редактора и модели данных ядра.
> Сигнатуры и структуры в части II описаны концептуально: это контракты,
> а не реализация.

## 1. Краткий вывод

Сейчас в проекте есть **рабочий прототип одной подсказки**, а не система подсказок.

Прототип:

- живёт внутри `LocalizedDescriptionEdit` в `src/modules/base_module/item_viewer.py`;
- привязан к `QPlainTextEdit`, `QTextCursor` и `QCompleter`;
- знает только один триггер — `%c[`;
- знает только один тип данных — цвета из `configs/ui/color_defs.xml`;
- сам обрабатывает клавиши, фильтрацию, позиционирование popup и вставку;
- получает готовый словарь цветов из `ItemViewerFeature`.

Переиспользуемая часть — разбор текста и данные:

- `src/sdk/engine_text.py` — разбор `%c[...]`, `\n`, цветов;
- загрузка `color_defs.xml` с учётом overlay проекта;
- каталог цветов и обновление по `PROJECT_SAVED`.

Не переиспользуется:

- UI подсказки;
- привязка к редактору;
- обработка клавиш;
- вставка;
- определение контекста;
- модель элементов подсказки.

Вывод: **для насыщения новыми триггерами текущую реализацию нужно выносить в отдельный UI-слой**. Наращивать её внутри `LocalizedDescriptionEdit` не рекомендуется.

## 2. Работает ли это в редакторе LTX без изменений

Нет.

Редактор LTX — это `QsciScintilla` в `src/ui/editor.py` (`CodeEditor`), а не `QPlainTextEdit`.

Различия, которые блокируют повторное использование:

- другая модель текста и курсора;
- другие позиции: Scintilla использует байтовые смещения UTF-8, а не позиции Python-строки;
- другое API выделения и замены;
- другая обработка клавиш и popup;
- другой undo/redo;
- другой способ получения экранных координат курсора;
- другой лексер (`LtxLexer` в `src/ui/lexers.py`) и другая информация о контексте.

Кроме того, LTX-редактору нужны другие подсказки:

- имена секций после `[`;
- ключи внутри секции;
- значения `inv_name`, `description`, `inv_name_short`;
- пути после `#include`;
- DLTX-операторы `!`, `@`, `!!`;
- возможно, ссылки на другие секции и файлы.

Текущий код ничего из этого не умеет и не имеет точки расширения.

## 3. Что именно сейчас связано неверно

| Компонент | Где сейчас | Проблема |
|---|---|---|
| Определение триггера `%c[` | `LocalizedDescriptionEdit` | Жёстко зашито в виджет |
| Popup и фильтрация | `LocalizedDescriptionEdit` | Не переиспользуется другими редакторами |
| Обработка клавиш | `LocalizedDescriptionEdit` | Смешана с логикой редактора описания |
| Вставка `%c[color]` | `LocalizedDescriptionEdit` | Знает формат конкретной подсказки |
| Список цветов | `ItemViewerFeature` | Данные проходят через модуль, а не через общий каталог |
| Обновление по `PROJECT_SAVED` | `ItemViewerFeature` | Подписка живёт в модуле, а не в UI-сервисе подсказок |
| Разбор цветов | `sdk/engine_text.py` | Эту часть можно переиспользовать |

Главная архитектурная ошибка: **UI-механика подсказок, данные и доменное знание о цветах смешаны в одном месте**.

## 4. Целевая архитектура

Предлагается разделить систему на четыре слоя.

### 4.1. UI-контроллер подсказок

Живёт в UI-слое. Не знает ни про цвета, ни про LTX, ни про локализацию.

Отвечает за:

- показ и скрытие popup;
- позиционирование относительно курсора;
- фильтрацию элементов;
- навигацию клавишами;
- вставку выбранного элемента;
- закрытие по `Esc`, потере фокуса и клику вне popup;
- единый undo-шаг;
- разрешение конфликтов клавиш с редактором;
- приоритеты провайдеров.

Контроллер работает не с конкретным виджетом, а с адаптером редактора.

### 4.2. Адаптеры редакторов

Тонкий слой для каждого backend.

Минимальный контракт адаптера:

- получить текст или фрагмент вокруг курсора;
- получить позицию курсора;
- получить текущую строку и префикс;
- получить стиль/лексему в позиции, если редактор это умеет;
- заменить диапазон текста;
- поставить курсор после вставки;
- получить экранные координаты курсора для popup;
- начать и закончить undo-группу;
- определить, доступен ли редактор для правки;
- перехватить или пропустить клавиши.

Нужны как минимум два адаптера:

- `QPlainTextEdit` / `QTextEdit` — для карточки предмета и других простых полей;
- `QsciScintilla` — для LTX/XML-редакторов.

### 4.3. Провайдеры подсказок

Провайдер отвечает за один контекст и один тип данных.

Примеры:

- `ColorTagProvider` — `%c[`;
- `LocalizationKeyProvider` — значения `inv_name`, `description`, `inv_name_short`;
- `LtxSectionProvider` — имена секций;
- `LtxKeyProvider` — ключи внутри секции;
- `IncludePathProvider` — пути после `#include`;
- `DltxProvider` — операторы и директивы DLTX.

Провайдер не рисует popup и не обрабатывает клавиши. Он отвечает на вопросы:

- есть ли в данной позиции подходящий контекст;
- какой диапазон заменять;
- какой префикс фильтрации использовать;
- какие элементы предложить;
- какой приоритет у этого контекста.

Новый триггер должен добавляться как новый провайдер, без правки контроллера и редакторов.

### 4.4. Каталоги данных

Цвета, ключи локализации, секции LTX и пути — это данные, а не UI.

Их стоит вынести в отдельные каталоги/сервисы:

- `ColorCatalog`;
- `LocalizationCatalog`;
- `LtxSectionCatalog`;
- при необходимости — каталог файлов и include-путей.

Каталоги:

- кешируются;
- обновляются по событиям проекта;
- не знают, где и как будет показана подсказка;
- отдают провайдерам нормализованные элементы.

## 5. Предлагаемые контракты

Ниже — концептуальные контракты, не код.

### Контекст подсказки

Должен содержать:

- адаптер редактора;
- путь к файлу;
- тип файла или язык;
- позицию курсора;
- текущую строку;
- текст до курсора в пределах допустимого окна;
- информацию о выделении;
- признак read-only;
- при необходимости — стиль/лексему в позиции.

### Запрос подсказки от провайдера

Провайдер возвращает:

- диапазон замены;
- префикс фильтрации;
- список элементов;
- приоритет;
- признак, нужно ли закрывать popup после вставки;
- при необходимости — дополнительное действие после вставки.

### Элемент подсказки

Должен быть единым для всех провайдеров:

- отображаемый текст;
- текст вставки;
- описание/подсказка;
- иконка или цветовой образец;
- тип элемента;
- ключ сортировки.

Это позволит цветам, секциям, ключам и путям использовать один popup.

## 6. Как должен выглядеть поток данных

1. Редактор создаёт адаптер и подключает UI-контроллер подсказок.
2. При изменении текста, перемещении курсора или нажатии клавиши контроллер собирает контекст.
3. Контроллер опрашивает зарегистрированные провайдеры.
4. Провайдеры определяют, есть ли подходящий триггер, и возвращают элементы.
5. Контроллер выбирает провайдера по приоритету.
6. Popup показывает отфильтрованные элементы.
7. При выборе контроллер просит адаптер заменить диапазон и поставить курсор.
8. Вставка оформляется как один undo-шаг.

## 7. Где что должно жить

Рекомендуемое разделение:

- UI-контроллер, popup, реестр провайдеров, адаптеры — в `src/ui/`;
- каталоги цветов, локализации и секций — в `src/core/` или `src/app/`;
- доменные провайдеры — рядом с соответствующим доменом;
- редакторы (`CodeEditor`, карточка предмета) — только подключают контроллер и не знают о конкретных подсказках.

Возможны два варианта регистрации провайдеров:

1. Регистрация в composition root приложения. Проще и предсказуемее.
2. SDK-метод для модулей, например регистрация провайдера через `ctx.ui`. Гибче, но расширяет публичный контракт SDK.

Для первого этапа рекомендуется вариант 1. Когда появится несколько модулей-поставщиков подсказок, можно добавить SDK-регистрацию.

## 8. Особенности редактора LTX

Для `QsciScintilla` нужно учесть отдельно:

- позиции Scintilla — байтовые смещения UTF-8, а не индексы Python-строки;
- для кириллицы нужен слой преобразования позиций;
- вставку лучше делать одной undo-группой;
- экранные координаты курсора получать через API Scintilla;
- учитывать стиль/лексему, чтобы не предлагать подсказки в комментариях и нежелательных строках;
- не ломать встроенные горячие клавиши редактора;
- не забирать фокус у редактора при показе popup.

У Scintilla есть встроенный autocomplete, но для полноценной системы с иконками, цветами, фильтрацией и разными диапазонами замены **предпочтителен собственный popup** с адаптером Scintilla. Встроенный autocomplete можно оставить как fallback для простых списков слов.

## 9. Этапы внедрения

### Этап 1. Зафиксировать прототип

- Не добавлять новые триггеры в `LocalizedDescriptionEdit`.
- Считать текущую реализацию референсом поведения.
- Вынести из неё только переиспользуемые части: разбор цветов и каталог.

### Этап 2. Выделить UI-контроллер и контракты

- Контракт адаптера редактора.
- Контракт провайдера.
- Контракт элемента подсказки.
- Реестр провайдеров и приоритеты.
- Popup и обработка клавиш.

### Этап 3. Перенести цветовую подсказку

- `ColorTagProvider` вместо жёсткой логики в виджете.
- `ColorCatalog` вместо словаря, передаваемого в виджет.
- Поведение должно остаться прежним: `%c[`, фильтрация, swatch, `default`, вставка `]`, обновление после сохранения проекта.

### Этап 4. Подключить `QPlainTextEdit`

- Адаптер для карточки предмета.
- Убедиться, что ghost-маркеры `\n`, сохранение и контекстное меню не конфликтуют с подсказками.

### Этап 5. Подключить `QsciScintilla`

- Адаптер для LTX/XML-редактора.
- Проверить кириллицу, undo, позиционирование popup, read-only.
- Подключить тот же контроллер подсказок.

### Этап 6. Добавить LTX-провайдеры

- Секции.
- Ключи.
- Локализационные ключи.
- Include-пути.
- DLTX-операторы.

## 10. Критерии готовности

Система считается архитектурно готовой, если:

- добавление нового триггера требует только нового провайдера и его регистрации;
- один и тот же провайдер работает в `QPlainTextEdit` и `QsciScintilla`;
- редакторы не содержат доменной логики цветов, секций или локализации;
- popup и обработка клавиш существуют в одном экземпляре;
- вставка — один undo-шаг;
- корректно работают кириллица и байтовые позиции Scintilla;
- список цветов обновляется после сохранения XML проекта;
- поведение покрыто тестами провайдеров, адаптеров и UI-smoke-тестами;
- текущая подсказка цветов продолжает работать без регрессий.

## 11. Риски и открытые вопросы

- Где должна находиться регистрация провайдеров: только в composition root или ещё и в SDK.
- Нужно ли привязывать провайдеры к типу файла/лексеру или только к контексту строки.
- Использовать собственный popup или встроенный autocomplete Scintilla для простых случаев.
- Как учитывать read-only и права проекта.
- Как поступать с несколькими провайдерами, сработавшими одновременно.
- Нужна ли поддержка multi-cursor и выделенного диапазона.
- Насколько глубоко учитывать комментарии и строковые литералы через лексер.
- Как обновлять каталоги без лишних перестроек popup во время редактирования.

## 12. Итоговая рекомендация

Текущую реализацию не расширять новыми триггерами.

Правильный путь:

1. вынести UI-механику подсказок в отдельный слой;
2. ввести контракты адаптера, провайдера и элемента;
3. перенести цвета в первый провайдер;
4. подключить оба редактора через адаптеры;
5. после этого добавлять новые триггеры как независимые провайдеры.

Так система станет расширяемой, а редактор описания и LTX-редактор будут использовать одну инфраструктуру, не дублируя popup, фильтрацию и обработку клавиш.

# Часть II. Детальный проект системы подсказок

## 13. Что уточнено против черновика

Черновик верно определил главную проблему и направление, но при проверке
по реальному коду выяснились детали, которые меняют проект:

1. **Одной регистрации в composition root недостаточно.** Карточка
   предмета создаётся базовым модулем, а модуль не имеет права
   импортировать `ui`. Значит, платформа должна уметь подключать
   подсказки к «чужому» виджету через SDK. Регистрация провайдеров —
   в composition root, а подключение контроллера к виджету — через
   `ctx.ui`.

2. **`QsciScintilla` не заставляет работать с байтами везде.** Байтовыми
   являются «сырые» позиции Scintilla (`SCI_GETCURRENTPOS`,
   `SCI_POINTXFROMPOSITION`). Обёртка QScintilla `getCursorPosition`,
   `setCursorPosition`, `positionFromLineIndex`, `lineIndexFromPosition`
   уже считает **символы**, а не байты. Это проверено экспериментально
   на кириллице. Контракт адаптера можно строить в символьных
   координатах, но внутри адаптера обязательны явные преобразования.

3. **Resolved-вкладка — это не файл.** `ResolvedView` показывает
   синтезированный текст после include/DLTX. В нём нет `#include` и
   DLTX-директив, поэтому подсказки include/DLTX должны работать только
   на «сырых» `.ltx`, а секции/ключи/значения — и на resolved-тексте.

4. **Редактируемость — это живое состояние.** У `LocalizedDescriptionEdit`
   вне режима правки стоит `read-only`, у `CodeEditor` и `ResolvedView`
   `read-only` зависит от активного проекта. Контроллер обязан проверять
   `isReadOnly()` в момент показа, а не кешировать признак.

5. **Цвета нужны не только подсказке.** Карточка рисует `%c[...]` и без
   подсказки. Поэтому каталог цветов — это данные ядра, а не внутреннее
   дело popup. Карточка должна получать палитру через SDK, а провайдер —
   из того же каталога.

6. **Полный обход VFS за секциями нельзя делать синхронно.** В проекте
   есть `system.ltx` на десятки мегабайт и resolved-текст на миллион
   строк. Каталог секций должен строиться фоном, порциями, с отменой и
   правом показать частичный результат.

7. **DLTX-операторы — это в основном префиксы синтаксиса, а не отдельный
   список подсказок.** `![`, `!![`, `@[`, `!key`, `>key`, `<key` должны
   сохраняться профильными провайдерами (секции, ключи), а не
   подменяться отдельным popup-ом.

8. **`QCompleter` и `Qt.Popup` опасны для карточки.** Popup, забирающий
   фокус, вызовет `focusOutEvent` у `LocalizedDescriptionEdit`, а тот
   завершит редактирование и вернёт текст в режим отрисовки. Нужен
   popup, который не забирает фокус, либо специальная защита жизненного
   цикла.

9. **Фильтрация должна жить в провайдере, а не в popup.** Для 50–100
   тысяч секций или ключей popup не должен материализовать все элементы.
   Провайдер сам делает prefix-выборку по индексу каталога и отдаёт уже
   отфильтрованный верхний срез.

10. **`DEFAULT_SEARCH_DELAY_MS` (180 мс) сюда не подходит.** Это задержка
    поиска/фильтра в списках. Автодополнение должно реагировать сразу;
    допустима только коалесценция нескольких сигналов в одном тике
    цикла событий, без искусственной паузы.

11. **Произвольные post-insert callback-и в контракте не нужны.** Они
    делают поведение непредсказуемым и плохо тестируемым. Вместо этого —
    декларативные `suffix`, `caret_offset`, `close_after_insert`,
    `reopen_after_insert`. Если нужно действие — это команда, а не
    подсказка.

12. **Тесты прототипа придётся переписать.** `tests/test_item_text_edit.py`
    обращается к `_completer` и `completionModel()` напрямую. После
    миграции эти проверки должны проверять результат провайдера и
    вставку через контроллер, а не внутренности Qt.

## 14. Инварианты и границы

### 14.1. Слои

| Слой | Что добавляется | Что запрещено |
|---|---|---|
| `sdk` | `sdk/hints.py` — Qt-независимые контракты; метод `UiApi.attach_text_hints`; `CoreApi.color_definitions` | импорт `core`, `ui`, `modules`, PyQt |
| `core` | `core/catalogs/*` — каталоги данных; публичные методы в `CoreServices` | импорт `ui`, `sdk`, `modules`; знание о popup и виджетах |
| `ui` | `ui/hints/*` — реестр, контроллер, popup, адаптеры, провайдеры; проводка в `PlatformApi`, `CodeEditor`, `ResolvedView`, `EditorTabs` | знание имён модулей и их внутренностей |
| `modules` | только вызов `ctx.ui.attach_text_hints(...)` в карточке предмета; при желании — чистые провайдеры позже | импорт `ui`/`core`; доступ к popup, адаптерам, реестру |
| `app` | не участвует | — |

Проверка `tests/test_architecture.py` уже запрещает модулям импортировать
`core`/`ui`, а SDK — `core`/`ui`/`modules`. Новый `sdk/hints.py` обязан
остаться без PyQt; это стоит закрепить отдельным тестом.

### 14.2. Жёсткие инварианты системы

- Подсказка всегда заменяет диапазон **внутри одной строки**. Перенос
  строки в `insert_text`/`suffix` запрещён.
- `matches()` провайдера не делает файлового I/O, не ходит в сеть, не
  парсит большие тексты и не трогает Qt. Только выборка из готового
  снимка каталога.
- Контроллер — единственное место, которое показывает popup, обрабатывает
  клавиши и вставляет текст.
- Вставка — один undo-шаг.
- Один экземпляр `HintPopup` на контроллер; один экземпляр
  `HintService` на приложение. Общего глобального singleton нет.
- В read-only подсказки не показываются (в v1 система insertion-only).
- При любой ошибке провайдера или адаптера редактор продолжает работать,
  а подсказка просто не показывается.
- Подсказки не меняют доменную модель напрямую: они вставляют текст в
  редактор, дальше действует обычный путь сохранения/патча.

### 14.3. Что не входит в v1

- Multi-cursor и несколько выделений.
- Навигационные подсказки (Ctrl+Click по ссылке) — отдельная система.
- Автоматическое создание секций/ключей/файлов из подсказки.
- XML-схема и XML-теги (проектируется отдельным этапом).
- Подсказки в read-only режиме.
- Сетевые/внешние источники данных.

## 16. Контракты

Ниже — концептуальные структуры. Это не код; имена полей фиксируют
смысл, а не реализацию.

### 16.1. `HintTargetInfo`

Описывает, **что за поверхность** перед нами. Строится обёрткой виджета
(или модулем) и может быть callable, чтобы файл/режим менялись без
пересоздания контроллера.

- `surface` — `raw` | `resolved` | `engine_text` | `plain`.
- `language` — `ltx` | `xml` | `localization_text` | `plain`.
- `path` — путь исходного файла (может быть `None`).
- `tab_id` — идентификатор resolved-вкладки (может быть пустым).
- `role` — необязательная роль: `item.description`, `item.name` и т.п.
- `default_color` — цвет текста по умолчанию `(r, g, b, a)` для
  `%c[default]`; допускается callable, чтобы палитра читалась в момент
  показа. В `HintContext` попадает уже разрешённое значение.
- `read_only` — необязательное уточнение; если не задано, адаптер
  спрашивает виджет.

`CodeEditor` отдаёт `surface="raw"`, `language` по расширению
(`.ltx` → `ltx`, `.xml` → `xml`, иначе `plain`), `path=current_file`.

`ResolvedView` отдаёт `surface="resolved"`, `language="ltx"` или
`"xml"` по `document.is_xml`, `path=root_path`, `tab_id`.

Карточка предмета отдаёт `surface="engine_text"`,
`language="localization_text"`, `role="item.description"`,
`default_color` из текущей палитры карточки.

### 16.2. `HintContext`

Снимок позиции. Всё, что нужно провайдеру, уже посчитано один раз.

- `target: HintTargetInfo`
- `adapter_kind: str` — `plain` | `scintilla`
- `line: int` — 0-based
- `column: int` — 0-based, в **символах** (не байтах и не UTF-16)
- `line_text: str` — текущая строка без `\r\n`
- `prefix: str` — `line_text[:column]`
- `suffix: str` — `line_text[column:]`
- `selected_text: str`
- `default_color: tuple[int, int, int, int] | None` — разрешённый цвет
  текста контрола (для `%c[default]`); builder вызывает callable сам.
- `editable: bool`
- `in_comment: bool`
- `in_string: bool`
- `section: str | None` — текущая секция LTX
- `section_kind: str | None` — `base` | `override` | `safe` | `delete`
- `key: str | None` — текущий ключ строки, если есть
- `value_kind: str | None` — `quoted` | `bare` | `list`
- `document_revision: int` — растёт на каждое изменение текста
- `local_sections: tuple[str, ...]` — секции, найденные в ограниченном
  окне вокруг каретки (не полный документ); адаптер может не отдавать их
  вовсе.
- `local_keys: tuple[tuple[str, str], ...]` — ключи текущей секции из
  локального текста (имя, значение), если удалось дёшево собрать

`in_comment`/`in_string`/`section`/`key` считает `context.py`:
для LTX — через чистый построчный токенизатор `core.patching.ltx.syntax`
(он не импортирует Qt; в него стоит вынести `tokenize_line` из
`ui/lexers.py`, а лексер оставить тонким маппингом токенов в стили и
цвета). Токенизатор уже покрыт `tests/test_ltx_lexer.py` и учитывает
`;`, `//`, кавычки, DLTX; для `engine_text` комментариев нет; для XML —
отдельный сканер (этап 7).

Текущая секция ищется ограниченным проходом назад по строкам до первого
заголовка (с верхней границей, например 200 строк). Это дешевле, чем
полный разбор документа, и всегда соответствует тому, что видит
пользователь, даже если resolved-документ ещё не синхронизирован.

`local_sections` — необязательная оптимизация. Её можно брать из
`ResolvedDocument.section_names()` только если spans уже построены и
документ небольшой; **нельзя** вызывать `section_names()` на каждое
нажатие для `system.ltx` на миллион строк, потому что первый вызов
разбирает весь документ. Для больших resolved-файлов список секций
берётся из глобального каталога, а текущая секция — из ограниченного
прохода назад. `local_keys` аналогично собирается только по локальному
блоку секции.

### 16.3. `HintItem`

Единый элемент для всех провайдеров.

- `label: str` — основной текст в списке.
- `insert_text: str` — что реально вставляется.
- `description: str` — вторая строка/пояснение.
- `detail: str` — короткая правая пометка (файл, значение, `#RRGGBB`).
- `kind: str` — `color` | `section` | `key` | `include` | `localization`
  | `directive` | `text`.
- `sort_key: str` — стабильная сортировка внутри провайдера.
- `swatch: tuple[int, int, int, int] | None` — RGBA для цветового образца.
- `payload: object | None` — непрозрачные данные провайдера; контроллер
  их не интерпретирует.

Никаких `QIcon`, `QColor`, `QPixmap` в SDK. Popup сам превращает
`swatch` в иконку.

### 16.4. `HintResult`

- `provider_id: str`
- `handled: bool` — провайдер «забрал» контекст; даже при пустом списке
  нижние провайдеры не опрашиваются.
- `items: tuple[HintItem, ...]` — уже отфильтрованный и ограниченный
  верхний срез.
- `total: int` — сколько всего совпадений до среза (для футера
  «показано N из M»); `0` означает «неизвестно/равно len(items)».
- `replace_before: int` — сколько символов слева от каретки заменить.
- `replace_after: int` — сколько символов справа от каретки заменить.
- `prefix: str` — префикс фильтрации (для подписи/диагностики/повторного
  использования).
- `suffix: str` — что дописать после `insert_text` (например, `]`).
- `caret_offset: int` — позиция каретки относительно конца
  `insert_text + suffix`; допускается отрицательное значение.
- `close_after_insert: bool` — по умолчанию `true`.
- `reopen_after_insert: bool` — по умолчанию `false`; нужно для навигации
  по каталогам include-путей.
- `kind: str` — тип контекста (для тестов/логов).

Инварианты результата:

- `replace_before <= len(context.prefix)`,
  `replace_after <= len(context.suffix)`.
- Диапазон замены не пересекает границу строки.
- `insert_text` и `suffix` не содержат `\n`/`\r`.
- Провайдер не возвращает больше `limit` элементов; контроллер всё равно
  делает жёсткий предел.

### 16.5. `HintProvider`

- `id: str` — `ui.color_tags`, `ui.ltx_sections`, ...
- `priority: int` — больше — раньше.
- `surfaces: frozenset[str]` — где применим; `{"*"}` — любая.
- `languages: frozenset[str]` — где применим; `{"*"}` — любой.
- `allow_in_comment: bool` — по умолчанию `false`.
- `matches(context) -> HintResult | None`
- `on_catalogs_changed()` — необязательный сброс внутренних memo.

Правила:

- `matches` возвращает `None`, если триггера нет.
- `matches` возвращает `handled=True`, если триггер есть, но элементов
  нет: это подавляет нижние провайдеры.
- `matches` не бросает исключения наружу; контроллер всё равно изолирует
  ошибки.
- Провайдер не знает о popup, клавишах, undo и виджетах.

### 16.6. `EditorAdapter`

Тонкая обёртка над backend-ом. Работает в символьных координатах.

Обязательное:

- `kind`
- `widget()` — внутренний виджет для event filter и позиционирования
- `cursor_line() -> int`
- `cursor_column() -> int`
- `line_count() -> int`
- `line_text(line) -> str`
- `line_prefix() -> str`
- `line_suffix() -> str`
- `selected_text() -> str`
- `is_editable() -> bool` — живой `not isReadOnly()`
- `default_text_color() -> tuple | None`
- `replace_range(before: int, after: int, text: str, caret_offset: int)`
- `begin_edit() / end_edit()` — одна undo-группа
- `cursor_rect_global() -> (x, y, width, height)`
- `connect_text_changed(cb)`
- `connect_cursor_moved(cb)`
- `connect_scrolled(cb)`
- `connect_destroyed(cb)`

Необязательное:

- `style_at_cursor() -> str | None` — нормализованный стиль (`comment`,
  `string`, `key`, `value`, `section`, `directive`, ...).
- `local_sections() -> tuple[str, ...] | None`
- `local_keys() -> tuple[tuple[str, str], ...] | None`
- `scroll_to_cursor()` — не требуется в v1.

Адаптер не фильтрует элементы, не показывает popup и не решает, когда
показывать подсказку.

### 16.7. `HintsHandle`

То, что получает модуль/обёртка виджета.

- `enabled: bool`
- `set_enabled(bool)`
- `refresh()` — пересчитать контекст (например, после смены файла или
  проекта)
- `close()` — скрыть popup
- `detach()` — снять event filter, закрыть popup, освободить контроллер
- `set_target(target | callable)` — если цель меняется без пересоздания
- `is_active() -> bool`

`NullHintsHandle` — безопасная заглушка для фейковых `ctx.ui` и старых
платформ: все методы ничего не делают. Модуль может вызывать
`attach_text_hints` через `getattr` и не падать в тестах.

### 16.8. Добавления в SDK

`UiApi`:

- `attach_text_hints(widget, target=None, providers=None, enabled=True)
  -> HintsHandle`
- `register_hint_provider(provider) -> Subscription` — только на этапе 7,
  с проверкой namespace `<module>.` и отпиской в `deactivate`.

`CoreApi`:

- `color_definitions(forest, overlay=None, config_dir=None) ->
  Mapping[str, tuple[int, int, int, int]]`

Оба метода — аддитивное расширение SDK: `SDK_VERSION` стоит поднять на
минорную версию, а модули продолжают работать без них (проверка через
`getattr`). `sdk_min` существующих модулей не меняется.

Метод `color_definitions` нужен карточке для отрисовки и провайдеру для
подсказки. Это единственное расширение CoreApi на первом этапе; секции,
ключи, include и локализация остаются внутренними каталогами UI-слоя,
потому что модулям они пока не нужны.

## 17. Реестр и разрешение конфликтов

### 17.1. Реестр

`HintRegistry` хранит провайдеров в порядке регистрации и умеет отдавать
снимок, отсортированный по `(-priority, order)`. Регистрация и снятие
безопасны во время работы; контроллер опрашивает снимок на каждом
refresh, поэтому новый провайдер начинает работать без перезапуска.

Приоритеты платформенных провайдеров:

| Провайдер | priority | surface | language | Триггер |
|---|---:|---|---|---|
| `ui.include_path` | 100 | `raw` | `ltx` | `#include …` |
| `ui.color_tags` | 90 | `engine_text` | `localization_text` | `%c[` |
| `ui.localization_key` | 90 | `raw`, `resolved` | `ltx` | значение `inv_name`/`inv_name_short`/`description` |
| `ui.ltx_section` | 80 | `raw`, `resolved` | `ltx` | `[`, `![`, `@[`, `!![` |
| `ui.ltx_parent` | 75 | `raw`, `resolved` | `ltx` | после `]:` |
| `ui.ltx_key` | 70 | `raw`, `resolved` | `ltx` | начало строки в теле секции |
| `ui.ltx_directive` | 60 | `raw` | `ltx` | `#` в начале строки |

Приоритеты не «магия»: они разрешают только реальные пересечения
(например, `#include` и `#`-директива). Триггеры секций/ключей/значений
разведены синтаксически.

### 17.2. Правила выбора

1. Отфильтровать провайдеров по `surface`, `language`, `editable`,
   `in_comment` (если `allow_in_comment=False`).
2. Идти сверху вниз.
3. Первый результат с `handled=True` выигрывает.
4. Результаты **не объединяются**: смешивать цвета, секции и пути в одном
   списке вредно.
5. Если провайдер вернул `handled=True` и пустой список — popup
   закрывается, нижние не опрашиваются.
6. Если провайдер упал — записать ошибку, пропустить его и продолжить.
7. После 3 подряд ошибок провайдер временно отключается до следующей
   инвалидации каталогов; в лог пишется одна запись.

### 17.3. Почему не «объединять всё»

- Разные типы заменяют разные диапазоны.
- Разные элементы требуют разного вставного поведения (`]`, кавычки,
  `/`).
- Пользователь в позиции `[` не ждёт цветов, а в `%c[` — секций.
- Объединение усложняет ранжирование и тесты без пользы.

Если когда-нибудь понадобится «мультиисточник» (например, ключи из
нескольких секций), это будет один провайдер, который сам смешивает свои
данные, а не склейка результатов разных провайдеров.

## 18. Контроллер

### 18.1. Состояние

- `Hidden` — popup скрыт, контекст не активен.
- `Open` — есть валидный результат и элементы.
- `Dismissed` — пользователь закрыл Esc; запоминается подпись контекста,
  чтобы не открывать popup на том же месте снова.
- `Suspended` — виджет read-only или контроллер выключен.

Подпись контекста: `(document_revision, line, column, provider_id,
replace_start, replace_end)`.

### 18.2. Что вызывает пересчёт

- `textChanged` адаптера;
- перемещение каретки;
- изменение выделения (в v1 только закрывает/пересчитывает);
- прокрутка (закрывает или перепозиционирует);
- `set_enabled(True)`, `refresh()`;
- смена каталогов (только если popup открыт);
- смена проекта/дерева (broadcast от `HintService`).

Программная загрузка текста (`setPlainText`, `CodeEditor.show_text`,
`ResolvedView.set_content`) не должна порождать подсказку: обёртки
временно вызывают `handle.set_enabled(False)` (или `close()`) на время
загрузки и включают обратно после. Контроллер дополнительно проверяет
`is_editable()` в момент пересчёта, поэтому даже пропущенный сигнал не
приведёт к показу в read-only.

Массовые изменения (paste, undo/redo) не открывают popup автоматически:
если popup уже был открыт и контекст сохранился, он обновляется; если
popup был скрыт — ждём следующего обычного набора или перемещения
каретки. Признак массового изменения — скачок текста строки больше чем
на один символ. Это убирает неожиданные popup-ы после вставки описания с
`%c[`.

Пересчёт коалесцируется через single-shot таймер с нулевой задержкой:
несколько сигналов в одном тике дают один проход. Искусственная задержка
не используется.

### 18.3. Алгоритм пересчёта

1. Если контроллер выключен, виджет уничтожен или `is_editable()` ложно —
   закрыть и выйти.
2. Построить `HintTargetInfo` (callable) и `HintContext`.
3. Если `in_comment` и ни один провайдер не разрешает комментарии —
   закрыть.
4. Отфильтровать провайдеров, опросить по приоритету, взять первый
   `handled`.
5. Провалидировать диапазон замены: не выходит за строку, не пересекает
   `\n`, `replace_before <= len(context.prefix)`,
   `replace_after <= len(context.suffix)`.
   При нарушении — лог и закрытие (лучше не вставить, чем испортить).
6. Дедуплицировать по `(insert_text, kind)`, ограничить (например, 200).
7. Если элементов нет — закрыть (и запомнить `Dismissed`? Нет: пустой
   результат не должен блокировать появление позже).
8. Если popup уже открыт и подпись та же — обновить элементы, сохранив
   выбранный `insert_text`, если он ещё присутствует.
9. Иначе показать/перепозиционировать popup, выбрать первый элемент.

### 18.4. Клавиши

Пока popup скрыт, контроллер не вмешивается вообще.

| Клавиша | Popup скрыт | Popup открыт |
|---|---|---|
| Up/Down | редактор | навигация по списку |
| PageUp/PageDown | редактор | страница списка |
| Enter | редактор | вставка (без модификаторов) |
| Tab | редактор | вставка (без модификаторов) |
| Esc | редактор | закрыть + `Dismissed` |
| Left/Right | редактор | пропустить; пересчёт закроет при выходе из контекста |
| Backspace | редактор | пропустить; пересчёт обновит префикс |
| Ctrl+Enter | редактор/карточка | пропустить (карточка завершает правку) |
| Ctrl+S | сохранение | сохранение |
| Ctrl+Space | ручное открытие (опция) | пропустить/переоткрыть |

Правила:

- Модификаторы (Ctrl/Alt/Meta) отменяют «коммитящие» клавиши: контроллер
  не должен перехватывать `Ctrl+Enter`, `Ctrl+Tab` и т.п.
- `event.isAutoRepeat()` для стрелок не блокируется.
- `Tab` перехватывается только при видимом popup. В остальное время он
  остаётся клавишей редактора/фокуса.
- `Esc` при скрытом popup не перехватывается: иначе сломаются диалоги и
  другие виджеты.
- Для `Enter`/`Tab`/`Esc` контроллер при необходимости обрабатывает
  `QEvent.ShortcutOverride` (принимает событие), чтобы `QShortcut` или
  внутренние команды Scintilla не сработали раньше event filter-а.

### 18.5. Вставка

1. `adapter.begin_edit()`.
2. В `try/finally`: `adapter.replace_range(before, after,
   insert_text + suffix, caret_offset)`, затем `adapter.end_edit()`.
   `end_edit` обязателен даже при ошибке, иначе undo-группа останется
   открытой.
3. Закрыть popup, если `close_after_insert`.
4. Если `reopen_after_insert` — запланировать refresh после того, как
   адаптер применит изменение.
5. Поставить защиту от повторного срабатывания на программные
   `textChanged`/`cursorPositionChanged`.

Одна undo-группа — обязательна. Для `QPlainTextEdit`/`QTextEdit` это
`beginEditBlock`/`endEditBlock`; для `QsciScintilla` —
`beginUndoAction`/`endUndoAction`.

### 18.6. Закрытие

- `Esc` — закрыть + `Dismissed`.
- Потеря фокуса редактором — закрыть.
- Клик вне popup — закрыть.
- Прокрутка/ресайз/смена вкладки — закрыть.
- `read-only` стал `true` — закрыть.
- Виджет уничтожен — `detach` без обращения к удалённым Qt-объектам.
- Каталог изменился, контекст ещё валиден — обновить, не закрывать.

### 18.7. Ошибки и жизненный цикл

- Контроллер — `QObject`, parent — внутренний виджет редактора.
- `HintService` хранит слабый набор контроллеров для broadcast-обновлений.
- При `destroyed` контроллер снимает event filter, закрывает popup,
  удаляется из набора.
- Исключения провайдеров и адаптеров логируются; текст в редакторе не
  меняется.
- В debug-режиме (`ACE_HINTS_DEBUG=1`) пишутся провайдер, префикс,
  время и причина закрытия.

## 19. Popup

### 19.1. Окно и фокус

Главное требование: **popup не забирает фокус у редактора**. Иначе
`LocalizedDescriptionEdit.focusOutEvent` завершит редактирование карточки
и popup закроется до вставки.

Предпочтительная конфигурация — **дочерний overlay-виджет окна
редактора**, а не отдельное активируемое окно:

- `HintPopup(window)` — child верхнего окна редактора (главного окна или
  диалога карточки);
- `Qt.NoFocus` у popup и списка;
- `raise_()` при показе;
- координаты считаются в системе окна, а не экрана;
- клики приходят в popup, но фокус остаётся в редакторе;
- popup автоматически уничтожается вместе с окном.

Владение при этом остаётся у контроллера: popup — child окна для
z-order, но контроллер явно удаляет его в `detach`/при `destroyed`
редактора, чтобы не оставлять висящий overlay после закрытия вкладки.

Почему так:

- клик по popup не вызывает `focusOut` у редактора и не завершает правку
  карточки;
- не нужно полагаться на поведение top-level `ToolTip`/`Popup` на Windows;
- нет проблем с модальными диалогами: overlay живёт в том же окне.

Ограничение: overlay обрезается границами окна. Поэтому позиция
выбирается «снизу или сверху от каретки» и зажимается в клиентскую
область окна; при нехватке места список становится ниже, а не выходит за
окно.

Fallback, если overlay мешает z-order/докам: top-level
`Qt.ToolTip | Qt.FramelessWindowHint` с `WA_ShowWithoutActivating` и
`NoFocus`, parent — окно редактора. `Qt.Popup` и `QCompleter` не
используются: они активируются и ломают жизненный цикл карточки.
Fallback обязательно проверяется на Windows в этапе 2.

### 19.2. Модель и отрисовка

- `HintListModel` — `QAbstractListModel`, хранит только верхний срез
  (≤ 200) и общее число совпадений.
- `HintItemDelegate` рисует:
  - цветовой образец (`swatch`) слева, если есть; `QPixmap` кэшируется
    по RGBA, чтобы не создавать его на каждый кадр;
  - `label` основной строкой;
  - `description` второй строкой muted-цветом;
  - `detail` справа (например, `#RRGGBB`, файл, значение);
  - выделение фоном `PALETTE.accent` с прозрачностью/палитрой темы.
- Высота строки — по метрикам шрифта (примерно 34–38 px), максимум 10
  видимых строк.
- Ширина — по содержимому, от 220 до 560 px; не шире экрана.
- Если совпадений больше лимита, внизу muted-строка
  «Показано 200 из N — уточните ввод».
- Пустой результат — popup скрыт (как в текущем поведении), без
  «нет совпадений», чтобы не мигал на каждом символе.

### 19.3. Позиционирование

- Для дочернего overlay координаты считаются в системе окна редактора:
  `widget.mapTo(window, point)`.
- Предпочтительно под кареткой, со смещением 2 px.
- Если снизу не хватает места — над кареткой.
- Левая граница выравнивается по каретке и зажимается в клиентскую
  область окна; для top-level fallback — в границы экрана
  (`QScreen.availableGeometry()`).
- Для `QPlainTextEdit` — `cursorRect()` (учитывает перенос строк).
- Для `QsciScintilla` — `SCI_POINTXFROMPOSITION`/`SCI_POINTYFROMPOSITION`
  по байтовой позиции, плюс ширина маргиналий/текстовой области; проверить
  на кириллице и разных DPI.
- При прокрутке/ресайзе popup либо перепозиционируется, либо закрывается;
  в v1 проще закрывать.

### 19.4. Мышь

- Hover меняет текущую строку.
- Клик/двойной клик вставляет.
- Колесо прокручивает список и не должно «проваливаться» в редактор;
  popup принимает wheel-событие, даже если список уже в конце.
- Клик вне popup закрывает.
- Клик по редактору не должен «съедаться»: редактор получает его как
  обычно, popup закрывается/пересчитывается.

Для клика вне popup достаточно временного event filter на верхнем окне
редактора: `MouseButtonPress` вне popup и вне редактора закрывает popup.
Фильтр снимается при закрытии. Для top-level fallback дополнительно
используется `QApplication.focusChanged`/деактивация окна. Это не
глобальный хук приложения: перехват ограничен окном и временем жизни
popup.

### 19.5. Тема и DPI

- Цвета — из `ui.theme.PALETTE` и `QPalette`, без hex-литералов в
  popup-коде (как и в остальном UI).
- Шрифт — из палитры редактора.
- Образцы цветов рисуются с учётом альфы поверх фона popup.
- DPI учитывается Qt автоматически; координаты — логические.

## 20. Адаптеры

### 20.1. Общая модель координат

Контракт работает в **символах Python-строки**:

- `column` — индекс в `line_text`;
- `replace_before/after` — количество символов;
- `line_text` — Python `str`.

Адаптер отвечает за преобразование в модель backend-а:

- `QPlainTextEdit`/`QTextEdit`/`QLineEdit`: `QTextCursor.position()` —
  UTF-16 code units. Для BMP (кириллица, латиница) совпадает с Python;
  для astral-символов (эмодзи) нужен пересчёт через длину UTF-16.
- `QsciScintilla`: `getCursorPosition()`/`setCursorPosition()` и
  `positionFromLineIndex()`/`lineIndexFromPosition()` уже работают в
  символах; `SCI_GETCURRENTPOS` и `SCI_*FROMPOSITION` — в байтах UTF-8.
  Смешивать их нельзя.

Обязательные тесты: кириллица в префиксе, кириллица после каретки,
astral-символ в `QPlainTextEdit`, вставка на границе.

### 20.2. `QPlainTextEdit` / `QTextEdit`

- `line_text`: `document().findBlockByNumber(line).text()`.
- `cursor_line`: `textCursor().blockNumber()`.
- `cursor_column`: `positionInBlock()` с пересчётом UTF-16 → символы.
- `line_prefix/suffix`: срез `line_text` по символьной колонке.
- `replace_range`: `QTextCursor` + `beginEditBlock/endEditBlock`;
  выделение от `caret - before` до `caret + after` (в UTF-16),
  `insertText`, затем позиция каретки с учётом `caret_offset`.
- `cursor_rect_global`: `cursorRect()` → `viewport().mapToGlobal()`.
- `is_editable`: `not isReadOnly()`.
- `connect_text_changed`: `textChanged`.
- `connect_cursor_moved`: `cursorPositionChanged`.
- `connect_scrolled`: `verticalScrollBar().valueChanged`.
- `destroyed`: сигнал `destroyed`.

`QLineEdit` можно поддержать тем же адаптером с оговоркой, что строка
одна; это пригодится для полей карточки позже.

### 20.3. `QsciScintilla`

- `line_text`: `editor.text(line)` (без `\r\n`).
- `cursor_line/column`: `getCursorPosition()`.
- `line_prefix/suffix`: срез строки.
- `replace_range`:
  - `beginUndoAction()`;
  - `setSelection(startLine, startCol, endLine, endCol)` в символах;
  - `replaceSelectedText(text)`;
  - `setCursorPosition(line, col)` с учётом `caret_offset`;
  - `endUndoAction()`.
  В `ResolvedView` undo живёт в Scintilla, а `ResolvedDocument` получает
  новый текст после паузы (`flush_pending` перед сохранением). Поэтому
  одна undo-группа Scintilla — это один шаг и для resolved-вкладки.
- `cursor_rect_global`: байтовая позиция через
  `positionFromLineIndex(line, col)`; `SCI_POINTXFROMPOSITION`,
  `SCI_POINTYFROMPOSITION`, `SCI_TEXTHEIGHT`; пересчёт в глобальные
  координаты с учётом маргиналий и позиции виджета.
- `is_editable`: `not editor.isReadOnly()`.
- `connect_text_changed`: `textChanged`.
- `connect_cursor_moved`: `cursorPositionChanged`.
- `connect_scrolled`: `verticalScrollBar().valueChanged`.
- `local_sections`: необязательный callable, который передаёт обёртка
  (`CodeEditor`/`ResolvedView`); адаптер не импортирует `ResolvedView`,
  чтобы не возникало цикла `ui.editor ↔ ui.hints`. Для больших
  resolved-файлов callable возвращает `None`.
- `style_at_cursor`: по байтовой позиции `SCI_GETSTYLEAT` и таблице
  стилей лексера; в v1 не обязателен, потому что LTX-контекст строится
  через `tokenize_line`.

### 20.4. Что адаптер не делает

- Не решает, показывать ли popup.
- Не фильтрует элементы.
- Не обрабатывает клавиши.
- Не знает о цветах, секциях и локализации.
- Не меняет `read-only` и не завершает редактирование карточки.

## 21. Каталоги

### 21.1. Общие правила

- Каталог — immutable-снимок после сборки.
- Сборка не трогает Qt и может идти в фоне.
- Снимок подменяется атомарно; провайдер видит либо старый, либо новый
  целиком.
- Ошибка сборки не роняет приложение: каталог остаётся пустым, пишется
  одна запись в лог.
- У каждого каталога есть `signature` — для диагностики и инвалидации.
- Жёсткие пределы памяти и количества элементов.
- Никакого дискового I/O в `matches`; только готовый снимок.

### 21.2. `ColorCatalog`

Источник: `<configs>/ui/color_defs.xml`, с учётом overlay проекта.

- Парсер — те же правила, что в `sdk/engine_text.py`
  (`CUIXmlInit::InitColorDefs`: `name`, `r`, `g`, `b`, `a`, имена без
  учёта регистра).
- `ColorDef`: `name`, `rgba`, `path`, `line`.
- `ColorCatalog`: `entries()`, `get(name)`, `signature`.
- Псевдоэлемент `default` не хранится в каталоге: его цвет — это цвет
  текста контрола, его подставляет провайдер из `HintTargetInfo`.
- Кэш-ключ: `(forest.cache_id, overlay.revision, file_stamp)`.
  `file_stamp` — mtime/size, чтобы внешняя правка тоже была видна.
- Сборка синхронная и дешёвая (файл маленький).
- Инвалидация: `TREE_READY`, `PROJECT_CHANGED`, `PROJECT_SAVED` с путём
  `configs/ui/color_defs.xml`.

Важно: парсер в `sdk/engine_text.py` остаётся публичным для совместимости
и тестов, но производственный путь карточки и провайдера идёт через
`core/catalogs/colors.py`. Чтобы парсеры не разъехались, нужен
параметрический тест на одном и том же `color_defs.xml`: оба должны дать
одинаковые `rgba`.

### 21.3. `SectionCatalog`

Данные:

- `SectionInfo`: `name` (каноническое, lower-case), `display`, `kind`
  (`base`/`override`/`safe`/`delete`), `path`, `line`, `parents`, `keys`
  (ограниченный набор).
- `SectionCatalog`: `names()`, `find(name)`, `keys_of(name)`,
  `parents_of(name)`, `prefix(prefix, limit)`, `signature`.

Источники:

1. «Сырые» `.ltx` файлы из `forest.files` (включая include-файлы), с
   подстановкой overlay-черновиков по пути. Виртуальные файлы проекта,
   которых нет на диске, читаются только из overlay.
2. Новые файлы проекта из overlay (`new_files`).
3. Локальный документ текущей вкладки — отдельно, в контексте, а не в
   глобальном каталоге.

Почему «сырые», а не resolved:

- Набор объявленных секций стабилен и не зависит от частых resolved-
  сохранений.
- Не нужно ждать предсборку и трогать `ResolvedCache`.
- DLTX-удаления (`!![sec]`) видны в разметке, но не отбрасываются
  безвозвратно: другой мод или другой файл может вернуть секцию.
  Поэтому по умолчанию показываем все объявленные имена, а `delete`
  помечаем как менее приоритетный вариант.
- Нет риска, что подсказка предложит секцию, которой нет в исходниках,
  но которая появилась только в синтетическом resolved-тексте.

Ограничения:

- идти по строкам, а не парсить документ целиком;
- использовать `core.patching.ltx.document.parse_section_header` и
  публичную обёртку разбора ключевой строки (её стоит добавить рядом с
  `parse_section_header`, чтобы не дублировать правила DLTX);
- хранить не более N ключей на секцию (например, 100) и общий предел
  ключей (например, 2 млн), чтобы каталог не разросся на полный
  `system.ltx`;
- хранить не более M секций (например, 50 000);
- хранить не более K родителей (например, 32);
- не хранить полный текст;
- хранить вклад каждого файла (`path -> sections`), чтобы обновление
  одного `.ltx` не пересобирало весь каталог.

Сборка:

- запускается из `HintService` через `TaskService.run(...)`: ядро не
  знает о задачах и Qt, а результат принимается в UI-потоке;
- в фоне, порциями по файлам, с бюджетом времени (например, 1–1.5 с на
  порцию) и отменой по смене поколения леса;
- публиковать частичный снимок после каждой порции;
- не блокировать первый показ: если каталог ещё строится, провайдер
  использует локальные секции текущего документа;
- при сохранении `.ltx`-файла (kind=`file`) обновлять только этот файл;
  сам пересчёт файла — тоже в фоне (в обработчике события только
  постановка в очередь, потому что `system.ltx` может быть в десятки
  мегабайт);
- при `PROJECT_CHANGED`/`TREE_READY` — полная пересборка.

Если измеренная стоимость сканирования окажется заметной для UI из-за
GIL, следующий шаг — перенести сборку индекса в пул процессов предсборки
и объединить результаты по файлам. Это оптимизация, а не необходимость v1.

### 21.4. `IncludeCatalog`

Источник:

- `forest.files` и `forest.xml_files`;
- overlay `source_files`;
- новые файлы проекта.

Правила:

- путь относительно `forest.scan_dir`, всегда с `/`;
- хранить и файлы, и каталоги (каталоги — префиксы путей);
- хранить расширение/язык, чтобы `#include` в LTX предлагал только
  `.ltx`, а будущий XML-include — только `.xml`;
- сортировка: каталоги раньше файлов на одном уровне, затем по имени;
- `prefix(prefix, limit)` — поиск по пути; если префикс содержит `/`,
  фильтр идёт по последнему сегменту, но с учётом каталога;
- ограничение — верхний срез, не весь список.

Сборка дешёвая, можно синхронно при первом запросе; инвалидация — по
`TREE_READY`, `PROJECT_CHANGED`, `PROJECT_SAVED` (file/resolved — новые
пути).

### 21.5. `LocalizationIndex`

Источник: `CoreServices.localization.load(forest, config_dir, overlay)`.

- `keys()` — отсортированные ключи;
- `prefix(prefix, limit)` — точный prefix по ключам; при пустом результате
  — регистронезависимый fallback;
- `text(key)` — перевод для второй строки;
- `entry(key)` — путь/строка объявления (для detail);
- `signature`.

Кэш и загрузка уже есть в `LocalizationService`; каталог лишь строит
сортированный индекс и не дублирует парсинг XML. Обновление — после
сохранения любого файла под `configs/text/**` и при смене проекта.
Пересборка идёт в фоне; до готовности нового снимка используется старый,
чтобы ввод не ждал.

Для превью перевода использовать `sdk.engine_text.engine_text_lines`
(или эквивалент): убрать `%c[...]`, заменить литерал `\n` пробелом,
ограничить длину.

### 21.6. Матрица инвалидации

| Событие | Colors | Sections | Includes | Localization |
|---|---|---|---|---|
| `TREE_READY` | пересобрать | пересобрать (фон) | пересобрать | пересобрать (фон) |
| `PROJECT_CHANGED` | пересобрать | пересобрать | пересобрать | пересобрать |
| `PROJECT_SAVED` kind=`file`, `.ltx` | — | обновить файл | обновить пути | — |
| `PROJECT_SAVED` kind=`file`, `configs/text/**` | — | — | — | пересобрать |
| `PROJECT_SAVED` kind=`file`, `ui/color_defs.xml` | пересобрать | — | — | — |
| `PROJECT_SAVED` kind=`resolved` | — | — | — | — |
| `PROJECT_SAVED` kind=`asset` | — | — | — | — |
| `RESOLVED_DOCUMENT_CHANGED` | — | — | — | — |
| смена активной вкладки | — | — | — | — |
| `UI_TAB_CLOSED` | — | — | — | — |

Порядок подписчиков не должен влиять на корректность: каталоги
пересобираются лениво по требованию, а не «в момент события». Событие
лишь помечает снимок устаревшим.

## 22. Провайдеры

### 22.1. Общие правила

- Провайдер сам детектирует триггер по `context.prefix/suffix`.
- Провайдер сам фильтрует и ранжирует элементы (prefix/contains).
- Провайдер возвращает только верхний срез (`≤ 100–200`).
- Провайдер сохраняет синтаксис вокруг замены (DLTX-оператор, кавычки,
  скобки).
- Провайдер не предлагает вставку, если она сделает синтаксис
  невалидным.
- Провайдер не работает в read-only и в комментариях (если не разрешено
  явно).

### 22.2. `ColorTagProvider`

- surface: `engine_text`; language: `localization_text`.
- Триггер: `%c[` без учёта регистра; между `[` и кареткой нет `]` и
  переноса.
- Префикс: содержимое после `%c[`.
- Замена: содержимое тега; если справа есть `]` до конца строки —
  включить его в `replace_after`.
- Вставка: `insert_text = name`, `suffix = "]"`, каретка после `]`.
- Элементы: `default` + именованные цвета; `default` первым при пустом
  префиксе; swatch для `default` — цвет текста контрола.
- Фильтрация: `contains`, без учёта регистра; при равенстве — по позиции
  совпадения и имени (сохраняет привычное поведение прототипа).
- Описание: `#RRGGBB`/ARGB для цвета, «цвет текста контрола» для
  `default`.
- Не работает в LTX-комментариях (в LTX вообще не включён).

### 22.3. `SectionProvider`

- surface: `raw`, `resolved`; language: `ltx`.
- Триггер: начало строки после отступа и необязательного DLTX-префикса
  (`!`, `@`, `!!`), затем `[`; каретка после `[`; `]` ещё нет.
- Замена: только имя секции; отступ, оператор и `[` сохраняются.
- Вставка: `name`, `suffix = "]"`; если справа уже есть `]`, он
  поглощается `replace_after`.
- Элементы: локальные секции в ограниченном окне вокруг каретки +
  глобальный каталог; дедупликация по имени; локальные — первыми.
- Описание: «в этом файле» или имя файла/строка из каталога.
- `!![удалённые]` не исключать полностью: помечать в описании и
  сортировать ниже обычных, потому что другой мод может вернуть секцию.
- Фильтрация: prefix, без учёта регистра.
- Приоритет 80.

### 22.4. `ParentProvider`

- surface: `raw`, `resolved`; language: `ltx`.
- Триггер: каретка после `]:` в строке заголовка; текущий токен — часть
  списка родителей.
- Замена: только текущий токен родителя (от `:` или последней `,` до
  каретки/запятой).
- Вставка: имя родителя; без суффикса.
- Элементы: секции из локального документа + каталога; исключить уже
  перечисленных в строке.
- Поддержать DLTX-удаление `!parent`: если пользователь уже ввёл `!`,
  сохранить его и предложить имя.
- Приоритет 75.

### 22.5. `KeyProvider`

- surface: `raw`, `resolved`; language: `ltx`.
- Триггер: тело секции, начало строки после отступа, нет `=`, нет
  заголовка/директивы.
- Замена: только имя ключа; DLTX-оператор (`!`, `>`, `<`) сохраняется.
- Вставка: имя ключа; без суффикса (пользователь сам ставит `=`).
- Элементы: ключи текущей секции из локального текста (в порядке
  появления) + ключи из каталога для этой секции + ключи родителей
  (транзитивно, с ограничением глубины); остальные — по алфавиту.
- Описание: значение из текущей секции (`= value`), «унаследован от X»,
  либо пусто.
- Если текущая секция не определена — не показывать (глобальный список
  ключей без секции бесполезен).
- Приоритет 70.

### 22.6. `IncludePathProvider`

- surface: только `raw`; language: `ltx`.
- Триггер: строка начинается с `#include` (без учёта регистра), каретка
  в аргументе — в кавычках или без них (резолвер поддерживает оба
  варианта).
- Замена: аргумент целиком — содержимое кавычек либо токен до пробела/
  комментария/конца строки. Кавычки, если они были, сохраняются.
- Вставка: относительный путь с `/`; для каталога — `dir/` и
  `reopen_after_insert = true`, чтобы сразу продолжить выбор.
- Элементы: каталоги и файлы; каталоги первыми; `prefix` по последнему
  сегменту; только `.ltx` в LTX-редакторе; ограничение сверху.
- Описание: `файл`/`каталог`, при наличии — размер.
- Не работает в `resolved` (там include уже раскрыт).
- Приоритет 100.

### 22.7. `DirectiveProvider`

- surface: только `raw`; language: `ltx`.
- Триггер: `#` в начале строки (после отступа), каретка сразу после
  неполного имени директивы.
- Элементы: `include` (в v1 — единственная поддерживаемая директива;
  список расширяется по мере поддержки резолвером).
- Вставка: `include`, `suffix = " "`, без `#`.
- Приоритет 60; ниже include, чтобы не мешать.

### 22.8. `LocalizationKeyProvider`

- surface: `raw`, `resolved`; language: `ltx`.
- Триггер: строка `key = value`, где `key` — один из
  `inv_name`, `inv_name_short`, `description`; каретка в значении;
  `value_kind` — `quoted` или `bare` (не список).
- Замена: всё значение (с кавычками или без) — чтобы не смешивать
  старый и новый ключ.
- Вставка: ключ локализации; кавычки сохраняются, если были.
- Элементы: `LocalizationIndex.prefix(...)`; label — ключ, description —
  переведённый текст, detail — файл/строка объявления.
- Фильтрация: prefix по ключу; fallback без учёта регистра.
- Приоритет 90.
- В `engine_text` карточки не включается: там текст, а не ключ.

### 22.9. DLTX

Отдельного «списка операторов» в v1 нет:

- `![`, `!![`, `@[` распознаёт `SectionProvider` и сохраняет при
  вставке;
- `!key`, `>key`, `<key` распознаёт `KeyProvider` и сохраняет оператор;
- `!parent` распознаёт `ParentProvider`.

Это лучше, чем отдельный popup: пользователь не выбирает оператор из
списка, а продолжает печатать синтаксис, получая имена.

Если позже понадобится «шпаргалка» по операторам, это будет отдельный
низкоприоритетный провайдер с невставляемыми информационными элементами;
для этого в контракт придётся добавить `kind="info"` и запрет вставки.
В v1 такого нет.

### 22.10. XML (этап 7, эскиз)

- `XmlTagProvider` — после `<` в позиции тега; элементы — теги текущего
  документа и каталога DXML/XML.
- `XmlAttributeProvider` — внутри тега после пробела; атрибуты,
  встречающиеся у этого тега.
- `XmlValueProvider` — значения `id`/`name`/ссылок; отдельный каталог.
- Контекст XML лучше строить небольшим построчным сканером, а не
  полагаться на стили встроенного лексера: стили зависят от текущей
  разметки и могут отставать.

## 23. Потоки данных

### 23.1. Цвет в карточке предмета

1. Пользователь кликает по описанию → `LocalizedDescriptionEdit` входит
   в режим правки (`isReadOnly = false`).
2. Печатает `%c[`.
3. `textChanged` → контроллер строит контекст (`surface=engine_text`,
   `in_comment=false`).
4. `ColorTagProvider` находит триггер, берёт снимок `ColorCatalog`,
   фильтрует по префиксу, возвращает элементы.
5. Popup показывает `default` и цвета со swatch.
6. Enter/клик → контроллер одной undo-группой заменяет содержимое тега
   на `name]`.
7. `raw_text()` при завершении правки превращает реальные переносы в
   `\n`; дальше обычное сохранение карточки.

### 23.2. Секция в сыром LTX

1. Пользователь вводит `[` в начале строки.
2. Контроллер строит контекст `surface=raw`, `language=ltx`,
   `section=None`, `in_comment=false`.
3. `SectionProvider` отдаёт локальные секции + каталог.
4. Вставка заменяет имя и добавляет `]`.
5. `CodeEditor` помечает вкладку dirty; сохранение идёт обычным путём
   (проектный черновик → патч).

### 23.3. Include-путь

1. Ввод `#include "`.
2. `IncludePathProvider` (только `raw`) показывает каталоги и файлы.
3. Выбор каталога вставляет `dir/` и переоткрывает popup.
4. Выбор файла вставляет путь; кавычки остаются на месте.
5. В `resolved`-вкладке провайдер не срабатывает.

### 23.4. Локализационный ключ

1. Ввод `inv_name = `.
2. `LocalizationKeyProvider` определяет ключ и диапазон значения.
3. Показывает ключи с переводами.
4. Вставка заменяет значение целиком, сохраняя кавычки.

### 23.5. Сохранение `color_defs.xml`

1. Проект сохраняет черновик → `PROJECT_SAVED` с путём файла.
2. `HintService` помечает `ColorCatalog` устаревшим.
3. Карточка при следующем обновлении/подсказке получает новый снимок
   через `ctx.services.color_definitions`.
4. Открытый popup при следующем refresh видит новые имена; если текущий
   выбранный элемент исчез — выбирается первый.

### 23.6. Смена вкладки и read-only

1. `EditorTabs.close_tab` вызывает `deleteLater` → контроллер ловит
   `destroyed` и делает `detach`.
2. Переключение на read-only вкладку: `is_editable() = false` →
   контроллер закрывает popup и не показывает новые.
3. Закрытие проекта: `PROJECT_CHANGED` → `HintService.refresh_all()` →
   все контроллеры пересчитывают editability и закрываются.

### 23.7. Большой resolved-файл

1. Контекст читает только текущую строку и ограниченное окно назад для
   секции.
2. `section_names()` у `ResolvedDocument` не вызывается на каждое
   нажатие: первый вызов строит spans по всему тексту. Для больших
   файлов список секций берётся из глобального каталога, локальные
   секции — только из текущего ограниченного окна.
3. Каталог секций — из сырых файлов; resolved-текст не сканируется.
4. popup материализует только верхний срез.

## 24. Интеграция в приложение

### 24.1. Composition root

В `src/main.py` после создания `CoreServices`, шин и `PlatformApi`:

- создать `HintService` с зависимостями: `services`, `events`, `tasks`,
  `forest_getter=lambda: api.workspace.forest` (либо добавить
  `PlatformApi.workspace_forest()`, который уже обещан в `UiApi`),
  `overlay_getter=api.project_overlay`, `log=api.log`;
- зарегистрировать платформенные провайдеры в фиксированном порядке;
- передать сервис в `PlatformApi` (`api.bind_hints(hints)` или параметр
  конструктора).

`main.py` — единственное место, которое знает конкретные классы
провайдеров. Это соответствует рекомендации черновика: регистрация в
composition root.

### 24.2. `PlatformApi` и SDK

- `PlatformApi.attach_text_hints(widget, target=None, providers=None,
  enabled=True)` делегирует в `HintService`.
- Если `HintService` не создан (тесты, минимальная конфигурация),
  возвращается `NullHintsHandle`.
- `UiApiAdapter.attach_text_hints` просто пробрасывает вызов.
- В `UiApi` метод документируется как необязательная возможность: модуль
  должен проверять наличие через `getattr`.

### 24.3. `CodeEditor`

- В конструктор добавляется необязательный `hint_attach` (фабрика).
- После `_init_ui` контроллер подключается к **внутреннему**
  `self.editor` (QsciScintilla), а не к `CodeEditor`.
- Target — callable: `path=self.current_file`, `surface="raw"`,
  `language` по расширению.
- `open_file`/`show_text` не пересоздают контроллер; target читает
  актуальный путь.
- `set_editable` не требует ручного уведомления: `isReadOnly` — живой.
- `CodeEditor` не знает о цветах, секциях и локализации.

### 24.4. `ResolvedView`

- Аналогично: подключение к `self.editor`.
- Target — callable: `surface="resolved"`, `language="xml"`/`"ltx"` по
  `document.is_xml`, `path=root_path`, `tab_id`.
- `local_sections` — только если spans уже построены (небольшой
  документ); иначе `None`, и список секций идёт из глобального каталога.
- Провайдеры include/DLTX сами отфильтруются по `surface`.
- `set_content`/`bind_document` не пересоздают контроллер; target callable
  читает актуальный документ.

### 24.5. Карточка предмета

- `ItemViewerFeature` передаёт в `ItemViewerWindow`/`ItemCardView`
  колбэк `attach_hints` (из `ctx.ui`), как уже передаёт `theme_color` и
  `color_defs`.
- `ItemCardView` в `__init__` подключает `description_label` с target:
  `surface="engine_text"`, `language="localization_text"`,
  `role="item.description"`, `path=description_source_path`,
  `default_color` — callable из текущей палитры.
- `editing_changed` не требует `set_enabled`: вне правки виджет
  read-only, и контроллер сам молчит.
- При закрытии окна/вкладки карточка вызывает `detach` (или полагается на
  `destroyed`).
- `set_color_suggestions`, `_color_model`, `_completer` и обработка
  клавиш popup удаляются из `LocalizedDescriptionEdit`. Остаются
  `Ctrl+Enter`, отрисовка `%c[...]`, ghost-маркеры `\n`, контекстное меню.
- `refresh_color_suggestions` больше не нужен для подсказки; если нужно
  перекрасить уже показанный текст после изменения `color_defs.xml`,
  добавляется отдельный `refresh_engine_colors`, но это не часть
  подсказок.

### 24.6. `EditorTabs`

- `MainWindow` передаёт `api.attach_text_hints` в `EditorTabs`.
- `EditorTabs._ensure_default_tab` передаёт фабрику в `CodeEditor`.
- `EditorTabs` не знает о провайдерах; только транспорт.

### 24.7. Жизненный цикл

- Контроллер живёт ровно столько, сколько виджет.
- `HintService` не хранит ссылок на виджеты, только weak-набор
  контроллеров.
- При `deactivate` модуля его окно закрывается → контроллеры умирают
  вместе с виджетами; отдельной отписки не требуется.
- При горячей перезагрузке провайдеров (этап 7) подписки снимаются в
  `deactivate` модуля.
- На `PROJECT_CHANGED` сервис не пытается обновить контроллеры внутри
  обработчика события: платформа ещё может менять `read-only` вкладок.
  Вместо этого `refresh_all()` планируется на следующий тик цикла
  событий. Дополнительно `EditorTabs.set_editable` может вызывать
  `refresh()` у виджетов, если у них есть такой метод.

## 25. Обновление данных и события

Событийная модель остаётся такой, как в архитектуре приложения:

- `TREE_READY` — новый лес; каталоги помечаются устаревшими.
- `PROJECT_CHANGED` — новый/удалённый проект; полная инвалидация.
- `PROJECT_SAVED` — точечная инвалидация по `kind` и `path`.
- `PROJECT_SETTINGS_CHANGED` — не влияет (если позже не появятся
  настройки подсказок).
- `RESOLVED_DOCUMENT_CHANGED` — не влияет на каталоги (это правки
  resolved-текста, а не сырых секций); локальные подсказки и так читают
  текущий документ.
- `UI_TAB_CHANGED` — не влияет; контроллеры закрываются по фокусу.

`HintService` подписывается на эти события и только помечает снимки
устаревшими/запускает фоновую пересборку. Providers не подписываются на
шину напрямую: они получают данные из `HintCatalogs`.

Порядок доставки не важен, потому что:

- providers читают текущий снимок;
- инвалидация — идемпотентная;
- пересборка ленивая/фоновая;
- открытый popup обновляется на следующем refresh.

## 26. Производительность и большие файлы

Бюджеты (ориентиры для этапа 5):

- сборка контекста (строка + токенизация + ограниченный проход назад) —
  до 1 мс на типичной строке;
- `matches` провайдера с prefix-индексом — до 5 мс на 100 тысяч
  элементов;
- обновление popup и отрисовка — в пределах кадра (≤ 16 мс);
- полная сборка `SectionCatalog` — фоном, порциями, без блокировки UI.

Приёмы:

- только текущая строка, никакого `toPlainText()`/`editor.text()` целиком
  на каждое нажатие;
- prefix-индекс через `bisect` по отсортированному массиву;
- верхний срез в провайдере, жёсткий предел в контроллере;
- `QAbstractListModel` вместо `QStandardItemModel` на десятки тысяч
  элементов;
- каталоги — immutable-снимки, подмена атомарная;
- фоновая сборка секций с бюджетом и отменой;
- отсутствие хеширования overlay в `matches`;
- отсутствие дискового I/O в `matches`;
- при необходимости — перенос сканирования секций в пул процессов
  предсборки (как уже сделано для резолвера), а не в UI-поток.

Отдельно: `system.ltx` может быть десятки мегабайт, а resolved-текст —
миллион строк. Поэтому нельзя:

- читать весь текст на каждое нажатие;
- парсить документ целиком в `matches`;
- строить `QStandardItem` на каждый элемент каталога;
- синхронно сканировать VFS при первом `[`.

## 27. Надёжность и диагностика

- Все вызовы провайдеров и адаптеров — в `try/except`; ошибка не
  всплывает в Qt-слот (иначе PyQt5 может уронить процесс через
  `qFatal`).
- Валидация диапазона замены до вставки; при нарушении — лог и отказ.
- Запрет многострочной вставки.
- Запрет вставки в read-only (двойная проверка: controller + adapter).
- Ограничение частоты логов ошибок провайдера.
- `ACE_HINTS_DEBUG=1` — подробный лог: провайдер, префикс, позиция,
  решение, время.
- Каталоги при ошибке остаются пустыми; подсказки просто не появляются.
- При отсутствии дерева/проекта/каталога — тихая деградация.

## 31. Риски и открытые вопросы

### 31.1. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Popup забирает фокус и карточка выходит из правки | средняя | дочерний `NoFocus` overlay; smoke-тест в модальном диалоге; top-level `ToolTip` только как fallback |
| Скан секций тормозит UI из-за GIL | средняя | фон, порции, бюджет, отмена; при необходимости — пул процессов |
| Устаревшие каталоги после правок | средняя | инкрементальное обновление по `PROJECT_SAVED`, ленивая пересборка, локальные секции |
| Ложные срабатывания в комментариях/строках | низкая | `tokenize_line`, `in_comment`/`in_string`, тесты |
| Конфликт клавиш с редактором/карточкой | средняя | перехват только при видимом popup; Ctrl+Enter/Ctrl+S проходят |
| Потеря производительности на больших списках | средняя | prefix-индекс, лимиты, `QAbstractListModel` |
| Расхождение парсеров цветов (sdk vs core) | низкая | паритетный тест |
| Разрастание SDK | средняя | только `attach_text_hints` и `color_definitions` в v1; регистрация провайдеров — позже |
| Сложность тестов из-за Qt | средняя | offscreen, фейковые адаптеры, чистые триггеры |

### 31.2. Решения, принятые в этом проекте

- Регистрация провайдеров — composition root; подключение к виджету —
  через SDK.
- Popup — собственный, не `QCompleter` и не встроенный autocomplete
  Scintilla.
- Фильтрация — в провайдере; popup только рисует.
- Контракт — символьные диапазоны в пределах одной строки.
- Никаких post-insert callback-ов; только декларативные поля.
- Include/DLTX — только raw LTX.
- Read-only — без подсказок.
- Провайдеры не объединяются; побеждает первый `handled`.
- Каталоги — immutable-снимки, обновляемые событиями и лениво.
- Цвета — через `core`, не через модуль.

- Показывать ли подсказки в read-only для навигации (не вставки)?

- Должен ли `Tab` в LTX всегда коммитить при открытом popup, или в

- Ограничивать ли локализационные ключи тремя полями предмета или

- Нужны ли XML-провайдеры в ближайшем релизе или после стабилизации LTX?

## 32. Итог

Проект сохраняет главную идею черновика — разделение UI-механики,
адаптеров, провайдеров и каталогов, — но уточняет её под реальную
архитектуру ACE:

- **UI** владеет popup, клавишами, undo и позиционированием;
- **адаптеры** скрывают разницу между `QPlainTextEdit` и
  `QsciScintilla`, работая в символьных координатах;
- **провайдеры** знают только контекст и данные, сами фильтруют и
  сохраняют синтаксис;
- **каталоги** живут в `core`, кэшируются, обновляются событиями и не
  знают о UI;
- **модули** подключают подсказки к своим виджетам одной SDK-операцией и
  не импортируют `ui`.

Главные исправления против черновика: SDK-подключение к «чужому»
виджету, фоновая сборка секций, разделение raw/resolved, сохранение
DLTX-синтаксиса профильными провайдерами, неактивирующий popup и
фильтрация на стороне провайдера.

# Приложение A. Журнал решений

| Решение | Альтернатива | Почему так |
|---|---|---|
| `attach_text_hints` в SDK | заставить модуль импортировать `ui` | модуль не имеет права импортировать `ui`; SDK — единственный контракт |
| Регистрация провайдеров в `main.py` | SDK-регистрация сразу | проще, предсказуемее; SDK-регистрация — когда появятся модули-поставщики |
| Собственный popup | `QCompleter` / autocomplete Scintilla | нужны swatch, описания, разные диапазоны, один undo, неактивирующий popup |
| Фильтрация в провайдере | фильтрация в модели popup | десятки тысяч элементов; провайдер знает индекс |
| Символьные диапазоны | байтовые/UTF-16 | переносимо между backend-ами; преобразования — в адаптере |
| Только одна строка | многострочные замены | все планируемые подсказки однострочные; проще валидация |
| Include/DLTX только в raw | и в resolved | в resolved этих конструкций уже нет |
| Нет read-only подсказок | показывать только просмотр | v1 insertion-only; навигация — отдельно |
| Нет post-insert callback | произвольные действия | предсказуемость, тестируемость, безопасность |
| Каталоги в `core` | каталоги в `ui`/модуле | данные — не UI; несколько потребителей; кэш и overlay |
| Цвета через `CoreApi.color_definitions` | оставить чтение XML в модуле | единый источник, обновление, паритет с провайдером |
