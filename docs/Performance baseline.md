## Spot-check Этапа 2

Второй, «тёплый» прогон после Этапа 2 (тот же `tools/perf_baseline.py`,
`--skip-ui`), уже через production-композицию
`CacheService + SnapshotService`:

| Операция | Время, мс | Отклонение |
|---|---:|---:|
| Построение дерева + снимок | 1709 | +10.1% |
| — только дерево (`tree_build_raw`) | 1590 | +2.4% |
| — снимок (`snapshot_observe`) | 119 | — |
| Проход Resolver4 | 1165 | +6.7% |
| Сборка resolved-текста | 1634 | +2.2% |
| Дисковый кэш, холодно | 1757 | +2.4% |
| Дисковый кэш, тепло | 1.8 | +0.1% |
| Разбор resolved-текста | 2987 | −1.3% |
| Предпросмотр патча | 1278 | −0.6% |

Повторные одиночные прогоны дают `tree_build` 1694–1718 мс
(+9.1…+10.6%). Верхняя граница чуть выше 10%: `tree_build` теперь
включает явное построение снимка (~115–120 мс), а `tree_build_raw`
остаётся в пределах ~+2–3%. Открытие файла снимок не пересчитывает;
метрики открытия/resolved-текста в пределах 10%. Разброс объясняется
нагрузкой на диск/CPU, а не кэшем дерева: harness намеренно строит
дерево с `use_cache=False`.

## Память

Рабочий набор процесса (RSS) и пик RSS.

| Точка | RSS, МБ | Пик RSS, МБ |
|---|---:|---:|
| Старт | 22.0 | 22.0 |
| После дерева | 34.3 | 35.0 |
| После Resolver4 | 52.8 | 91.9 |
| После сборки resolved-текста | 130.8 | 227.4 |
| После дискового кэша | 136.6 | 292.6 |
| После разбора секции | 400.2 | 404.4 |
| После предпросмотра патча | 405.9 | 436.2 |

Пик памяти определяется разбором resolved-текста и секциями, а не
предпросмотром. Это ожидаемо для текущей модели «текст + документ» и
должно уменьшаться на Этапе 4 за счёт ленивой семантической модели.

Шаг 4.1: полная семантическая модель не создаёт вторую копию текста.
Если `resolve.text` уже содержит корень, модель переиспользует ту же
строку; если нет — записывает результат в `resolve.text`. На эталонном
VFS полный проход — ~1.84 с, большая секция
`reduce_lod_texture_list` (4024 ключа) — ~0.12 с.

Шаг 4.2: `assemble_resolved` получает текст и `line_sources` из общей
проекции `render_sections` без snapshot-хранилища provenance. На
эталонном VFS это ~1.64–1.66 с против ~1.55–1.56 с у прежнего рендера
(+5…+6%, в пределах 10%). Полная модель строится только для карточки,
через `TaskService`; её ~1.8 с не блокируют UI-поток, а таблица
показывает по 200 строк с догрузкой.

тяжёлой части из GIL). Замер использует offscreen-Qt и не заменяет
ручной smoke-тест.

## Spot-check Этапа 8.5: синтетический нагрузочный VFS

Дата: 25.11.2026. Команда:

```powershell
.venv\Scripts\python.exe tools\load_check.py `
  --sections 19000 --files 20000 --workers 4 --timeout 180
```

Синтетический VFS: `system.ltx` включает `big.ltx`, который включает
19000 файлов с секциями; ещё 998 standalone-корней нужны для
параллельной предсборки. Всего 20000 LTX-файлов, 19002 секции в
resolved-тексте `system.ltx`, 999 корней дерева.

| Метрика | Значение |
|---|---:|
| Построение дерева | 25799.8 мс |
| Resolved-текст `system.ltx` | 5009.0 мс |
| Параллельная предсборка (`workers=4`), 999/999 | 35535.1 мс |
| Отмена предсборки | 1577.6 мс, `done=0/999`, state `idle` |
| RSS после дерева | 101.2 МБ |
| RSS после resolved | 129.9 МБ |
| Пик RSS | 158.4 МБ |

Проверка считается успешной только при `files >= 20000`,
`resolved_sections >= 19000`, `roots >= 999`, завершённой предсборке
`done == total` без ошибок и реально остановленной отмене
(`stopped=true`, `error=null`, `done < total`). Это нагрузочный
smoke-check на синтетике, а не сравнение с `stage0.json`; числа зависят
от диска/CPU. Используются `FileCacheSystem`/`ResolvedCache` напрямую,
без полной production-композиции `SnapshotService`/`TaskService`, поэтому
это не заменяет production-профиль. Оригиналы игры, `Overwrite` и VFS не
изменяются.
