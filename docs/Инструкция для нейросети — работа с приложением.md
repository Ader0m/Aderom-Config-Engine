# Инструкция для нейросети: работа с приложением

## 1.1. Перед изменением

1. Прочитай `docs/README.md`, `docs/Целевая архитектура приложения.md`,
   `docs/Целевая архитектура модулей.md` и `AGENTS.md`.
2. Определи слой и владельца изменения: `core`, `app`, `platform`
   (`ui/platform`), `ui`, `sdk`, `modules` или composition root.
3. Сформулируй план и проверь, не требует ли изменение
   нового публичного API, зависимости, миграции данных или записи.
4. Если требует — остановись и спроси оператора.
5. Не начинай со «временного обхода», «быстрого fallback'а» или
   дублирования существующего механизма.

## 1.2. Слои и импорты

- `core` не импортирует `sdk`, `app`, `platform`, `ui`, `modules`.
- `sdk` не импортирует внутренние слои и не содержит реализаций.
- `app` не импортирует `ui`, `platform`, `modules`; `core` — только через
  `core.api.*`.
- `ui` не импортирует `core` напрямую; данные приходят через `app`/
  `platform`.
- `modules` импортируют только `sdk`, PyQt для своих виджетов и свои
  third-party зависимости. Импорт другого модуля запрещён.
- Импорт пакета `modules` разрешён только `ModuleLoader`.
- Публичные контракты — `sdk.__all__` и `core.api.*`; корень `core` пуст.
- Не добавляй shim, legacy-алиас, deprecation-обёртку или второе имя для
  одного действия. До `1.0` старое удаляется сразу.
- Новое публичное API — только с ADR и версией.

## 1.3. Ответственность слоёв

| Слой | Отвечает за | Не делает |
|---|---|---|
| `core` | объективные данные, VFS, резолв, семантику, граф, patch engine | UI, проекты, модули, Qt |
| `app` | сценарии проекта, черновики, документы, overlay, preview/commit | виджеты, меню, шины |
| `platform` | шины, задачи, окна, вкладки, загрузчик, реестры | бизнес-правила движка |
| `ui` | Qt-виджеты и рабочую среду | доменные правила, запись файлов |
| `sdk` | контракты и модели для модулей | реализации |
| `modules` | свои сценарии, окна и возможности | импорт внутренностей, чужие окна |

Состояние: `core` — неизменяемые данные и кэш по снимку; `app` — состояние
сессии; `platform` — runtime; `ui` — представление; `modules` — только
своё.

## 1.4. Тяжёлые операции

- Любая операция дольше ~50 мс, I/O, резолв, XML/DXML, DDS, граф,
  предпросмотр или патч — вне UI-потока.
- Используй `TaskService`/`ctx.tasks`: состояния `queued/running/done/
  failed/cancelled`, owner, progress (если измерим), кооперативную отмену,
  `operation_key` и single-flight.
- Для измеримого прогресса вызывай `ctx.tasks.progress(done, total,
  message)` внутри `fn(log)`. Кнопка операций показывает первый запущенный
  процесс и заполняется по его прогрессу; открывать панель не обязательно.
- Повторный запуск той же операции не создаёт дубль; UI показывает «уже
  запущено».
- Не создавай `QThread`/`multiprocessing.Pool` в модулях.
- Не блокируй всё приложение модальным progress; блокируй только
  зависящую функцию.
- Не используй `processEvents`, `sleep`, `thread.wait()` в UI-потоке.
- У каждой задачи должны быть явные `operation_key` и `title`; fallback
  `<platform>:task-N` без имени запрещён.
- Операции видны в общем `OperationCenter`, а не в самодельном popup.

## 1.5. Снимок и кэш

- Любой кэш — только через `CacheService`.
- Кэш-ключ обязан включать `snapshot_id` и версию правил; нельзя
  возвращать данные, посчитанные для другого снимка.
- Не создавай второй кэш или второй источник истины.
- Смена overlay создаёт новую ревизию снимка; дорогие компоненты
  переиспользуются по подписям, а не пересчитываются вслепую.
- `generated/` не мигрируется: смена версии — удаление/пересборка.

## 1.6. Проект и патчи

- Оригиналы модов, `Overwrite` и VFS игры — только чтение.
- Любая правка — сначала черновик проекта, затем overlay, preview,
  проверка, подтверждение, commit.
- Писать патч можно только через `PatchCommitService` и
  `CommitAuthorization`.
- Не создавай `PatchPlan`/`GeneratedPatch`/`VerificationResult` вручную в
  `app`/`ui`; их создают движки.
- Не создавай `CommitAuthorization` вручную и не ставь `confirmed=True`
  без подтверждения пользователя.
- Не обходи `PatchWriter` и не импортируй его в `app`/`ui`.
- Полный round-trip обязателен до авторизации; ошибка/отмена не оставляет
  частичный патч-мод.
- `ProjectService.active` меняется только через `ProjectSession`.

## 1.7. UI, окна и события

- У окна, вкладки, задачи, подписки и регистрации есть owner.
- Модуль не закрывает чужие окна/вкладки и не меняет чужие регистрации.
- `dispatch` — только из UI-потока; `publish` можно из фона.
- Не создавай собственный hint-popup; используй `attach_text_hints`.
- Цвета — только через `ThemeService`/`ctx.ui.theme_color`; жёсткие цвета
  вне `ui/platform/theme.py` запрещены.
- Не создавай второй центр операций и второй реестр операций.

## 1.8. Модули и загрузчик

- Единственный манифест — `module.json`; class-manifest запрещён.
- Манифест читается и валидируется до импорта кода.
- Не импортируй модуль до проверки `module.json`, зависимостей и
  capability.
- `trust` из манифеста — не разрешение; доверенные id задаёт платформа.
- `base` обязателен и не отключается (ADR-35).
- Не заменяй активного провайдера capability при runtime enable/reload.
- Runtime-состояния загрузчика не сохраняются в `config/modules.json`.

## 1.9. Тесты и документация

- Добавляй/обновляй тест на каждое изменение поведения.
- Не ослабляй тест и не удаляй архитектурный тест, который мешает.
- `tests/main_unit_test_*` меняются только по явному указанию оператора.
- Перед завершением: `python -m pytest -q`,
  `python -m compileall -q src`, `git diff --check`.
- Обновляй целевые документы, а не только код.
- Не накапливай историю в README: история — в `archive/docs/`.
- Не копируй legacy-паттерн из архива.

## 1.10. Когда остановиться

Остановись и спроси оператора, если нужно:

- изменить публичный контракт или версию SDK;
- изменить `tests/main_unit_test_*`;
- ослабить/удалить тест;
- добавить зависимость;
- изменить `Resolver4` или семантику игры;
- изменить схему проекта или формат данных;
- обойти `PatchWriter`/`CommitAuthorization`;
- нарушить инвариант целевой архитектуры;
- выбрать между противоречащими документами;
- объяснить падение производительности больше чем на 10%;
- сделать «быстрое решение», противоречащее правилам.

Не маскируй проблему `except Exception` и не добавляй fallback «если метод
есть — вызовем».

## 1.11. Запрет «срезать путь»

- Не обходи слой, сервис или публичный порт только потому, что так короче.
- Не копируй логику ядра в `app`, UI или модуль.
- Не отключай проверку, round-trip, авторизацию, прогресс, отмену или
  тест ради «упрощения».
- Не заменяй существующий механизм упрощённой копией.
- Не добавляй «временный» fallback без ADR, срока и записи в legacy-раздел.
- Не считай успешный запуск доказательством корректности: нужны тесты и
  проверки инвариантов.
- Если правильное решение требует нового контракта — остановись и
  предложи ADR, а не обходи архитектуру.
