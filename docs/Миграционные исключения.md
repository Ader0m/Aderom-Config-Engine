# Миграционные исключения

Этот документ — временный legacy-карантин. Он перечисляет существующие
нарушения, которые **пока** остаются в коде, но не должны расширяться.
Постоянные правила — в `AGENTS.md`.

Правила:

1. Исключение действует только для указанного пути/паттерна.
2. Нельзя добавлять новое исключение без оператора.
3. Нельзя копировать паттерн из исключения в новый код.
4. Если файл из карантина меняется, новые нарушения в нём запрещены.
5. Исключение удаляется на указанном этапе.
6. Если нарушения нет в списке — считай его запрещённым.

---

## 1. Критические исключения

Эти нарушения особенно опасны. Их нельзя расширять ни при каких условиях.

| ID | Путь | Нарушение | Почему ещё здесь | Закрыть на |
|---|---|---|---|---|
| CR-7 | `src/core/items/*` | предметный домен живёт в `core` | до выноса features | Этап 7 |

Примечание: на Этапе 0 пользовательская запись патчей выключена флагом
`PATCH_WRITE_EXPERIMENTAL=False`. CR-1/CR-2 закрыты на шаге 5.3:
автоподтверждение удалено, запись идёт только через
`PatchCommitService` с `CommitAuthorization`; UI подтверждает опасные
изменения отдельно. Use case по-прежнему требует `allow_write=True`,
который UI передаёт только при включённом флаге. Флаг остаётся `False`
и не разрешает расширять write path. CR-3/CR-4 (синхронное
автосохранение) закрыты на шаге 3.6: запись идёт в `TaskService`, с
coalescing и привязкой к активному проекту.

Этап 5 начат (шаг 5.1, ADR-20): введены `PatchIntent`, `PatchSnapshot`,
`PatchBundle`, `PatchEngine` и `PatchOrchestrator`; SDK-запрос
переименован в `PatchRequest`. Путь записи не менялся,
`PATCH_WRITE_EXPERIMENTAL` остаётся `False`. Шаг 5.2 (ADR-21) закрыл
CR-5 и DATA-5: asset/new-file собираются движками, XML-слияние вынесено
в `core.patching.xml.merge`. Возврат ручной сборки ловится статтестом
`AppPatchConstructionBoundaryTest` в `tests/test_architecture.py`.
Шаг 5.3 (ADR-22) закрыл CR-1/CR-2: `PatchCommitService` —
единственная точка записи, `CommitAuthorization` связывает план, снимок
и подтверждённые риски; запись требует обязательный
`expected_snapshot_id`, сверяет текущий снимок VFS, отклоняет план с
ошибками/без снимка и откатывает частичный набор файлов. Успешные
записи пишутся в `generated/patch-audit-<session>.log` (новый файл на
сессию). `PatchWriter` и
`confirmed=True` в app/UI запрещены статтестом. Шаг 5.4 (ADR-23)
добавил полный round-trip затронутого корня перед авторизацией. Шаг
5.5 (ADR-24) закрыл TASK-2 в части `write_preview`: запись идёт через
`TaskService`, с прогрессом и отменой между файлами; снимок VFS
перепроверяется до/после authorize и после commit. Доверенный
`RoundTripReport` из фонового предпросмотра переиспользуется в
authorize; отчёт привязан к fingerprint (включая корень, текст патча и
изменения), снимку и verifier. При активной
записи закрытие приложения откладывается, а не блокирует UI; после
завершения окно закрывается повторно. Аудит пишет статусы
`committed`/`rolled_back`/`cancelled`. Шаг 6.9 убрал синхронный
`flush()` из `on_app_close`: сохранение перед закрытием идёт задачей
`project.close:<id>`, а окно закрывается после её завершения.
Новых исключений шаги 5.2–5.5 не добавили.

## 2. Legacy-исключения по слоям

### 2.1. UI → core

Все исключения UI-1…UI-5 закрыты. UI-3/UI-4 закрыты на шаге 6.7:
контекст подсказок получает готовое описание LTX-строки из
`app.hints`, разбор ядра идёт через `core.api.hints`. UI-2 закрыт там
же: `ui/lexers.py` использует `app.lexing` → `core.api.syntax`.
`UI_CORE_IMPORT_ALLOWLIST` пуст; прямые импорты `core` из UI запрещены.

UI-1/UI-5 закрыты при завершении Этапа 3: редактор получает текст через
переданный платформенный `text_reader`, а `ProjectController.document_text`
использует `services.read_text`/`read_xml_text` без прямого импорта `core`
и без `getattr`-fallback.

Правило: новые импорты `ui → core` запрещены. При изменении этих файлов
не добавлять новые.

Allowlist этих путей зафиксирован в
`tests/architecture_allowlist.py`. Добавление нового пути или нового
импорта — только по решению оператора и с ADR.

### 2.4. Окна, вкладки, владение

OWN-1/OWN-2/OWN-3 закрыты на шаге 6.1: владелец вкладки/окна хранится
явно, `close`/`close_owner` проверяют его, а `tab_id` больше не является
способом вычисления владельца. Платформенные мосты передают owner,
привязанный к модулю. Default-вкладка `ui.editor` принадлежит платформе;
resolved-правки, undo/redo, retain/release и update/sync также проверяют
владельца. `<platform>` — доверенный owner: платформа может управлять
любой вкладкой/окном, модуль — только своим.

## 4. Как закрывать исключения

1. На этапе, указанном в таблице, исключение должно быть исправлено.
2. Если этап изменился — обновить таблицу, а не срок «на потом».
3. После исправления удалить строку.
4. Если исключение больше не нужно — удалить сразу.
5. Новое исключение добавляет только оператор.
6. Allowlist в `tests/architecture_allowlist.py` должен уменьшаться по
   мере закрытия этапов; расширение допускается только оператором.
7. Архитектурный тест, упавший на новом нарушении, не ослабляется и не
   удаляется — исправляется код или принимается решение оператора.

## 5. Проверка перед изменением

Перед правкой файла из этого списка:

- убедись, что твоё изменение не расширяет нарушение;
- если можно уменьшить нарушение без большого рефакторинга — уменьши;
- если изменение требует нового исключения — остановись и спроси
  оператора;
- не копируй паттерн в соседний файл.
