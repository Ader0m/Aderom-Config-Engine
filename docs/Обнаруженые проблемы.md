# Отчёт по оставшимся проблемам ACE

Дата: 21.11.2026.

Проверка: **715 тестов OK, 1 skipped**, `compileall` и `git diff --check` чистые.

Ниже — состояние после закрытия пунктов 2.1, 2.2, 3.1, 3.2, 3.5 и 3.6. Полностью закрытые пункты вынесены в раздел 1; в разделах 2–9 остались только актуальные проблемы.

## 1. Что уже закрыто

### 1.1. Регистрации модулей (бывший 2.1)

- Каждая регистрация возвращает `sdk.RegistrationHandle`.
- `ModuleContext` собирает все регистрации модуля в `RegistrationScope`.
- Загрузчик вызывает `scope.dispose()` после `deactivate` и при откате упавшего `init/register`.
- Владелец проверяется для типов ресурсов, настроек проекта и contributor'ов графа.
- Снимаются меню, действия, обработчики открытия, горячие клавиши, мышиные привязки, команды, события, настройки, asset-типы и file readers.

### 1.2. Загрузчик модулей (бывший 2.2)

- `ModuleManifest` поддерживает `requires`, `optional_requires`, `provides`, `needs`, `optional_needs`; у зависимостей есть `min_version`.
- Резолвер проверяет версии, capability-провайдеров, optional-зависимости и циклы; причины пропуска лежат в `loader.skipped`.
- Добавлены явные состояния `ModuleState` и `ModuleRecord`.
- Падение `init/register/activate` переводит модуль в `FAILED`, снимает регистрации, закрывает окна/вкладки, ожидает задачи и выгружает пакет.
- Зависимые от упавшего модуля не активируются.
- Добавлены `unload`/`reload`, очистка `sys.modules`, закрытие ресурсов владельца и `force`-выгрузка зависимых.
- `TaskService`, `ModuleWindowManager` и `EditorTabs` получили owner-scoped очистку.
- Модули считаются доверенным кодом: process/FS-isolation не реализуется (см. раздел 9).

### 1.3. Владение и namespace событий (бывшие 3.1, 3.2)

- `EventBus` хранит owner подписки и умеет снимать только подписки указанного владельца.
- `ctx.events.unsubscribe(name)` снимает только подписки текущего модуля.
- Все имена `Events` переведены на `<owner>.<name>`: `app.*`, `ui.*`, `base.*`, `<module>.*`.
- `TREE_READY` и `FILE_OPEN_FAILED` публикует платформа, а не модуль.
- `EventApiAdapter.publish` предупреждает о публикации в чужой модульный namespace.
- Перехват реакций сохранён: `dispatch` не фильтруется по owner, а `register_action_handler` с более высоким `priority` заменяет реакцию.

### 1.4. Тяжёлые события и backpressure (бывший 3.5)

- `TREE_READY` передаёт `sdk.TreeReady` (`cache_id`, `generation`, сводка), а не `LtxForest`; лес читается через `ctx.ui.workspace_forest()`.
- `PROJECT_CHANGED` передаёт `sdk.ProjectChanged`, а не объект `Project`.
- `SavedDraft` больше не содержит `text`.
- Фоновая публикация использует общую ограниченную очередь (`EventBus.max_pending`) и один queued-сигнал на пачку.
- При переполнении отбрасываются старые события, ведётся `dropped_events`.

### 1.5. Изоляция ошибок (бывший 3.6)

- `PlatformApi.trigger_action` ловит исключения callback'ов меню, горячих клавиш и мыши, логирует traceback и возвращает `False`.
- `TaskService` изолирует исключения `on_log`, `on_done` и cleanup.
- `TaskService` умеет `cancel_owner`/`wait_owner`/`shutdown`; `main.py` логирует незавершённые задачи.

### 1.6. Прочее

- `_write_meta` теперь выполняется под `_write_lock`.
- XML-открыватель при отсутствии дерева/конфигов публикует `FILE_OPEN_FAILED` через платформу.
- `ModuleWindowManager.close_all` снова используется при закрытии приложения.
- Документация по событиям, жизненному циклу модулей и backpressure обновлена.

## 2. Оставшиеся проблемы жизненного цикла модулей

### 2.3. `requires=("base",)` у `ogg_editor` — фантомная зависимость

**Приоритет: средний. Пропущено по решению.**

`OggEditorModule` (`modules/ogg_editor/module.py`) объявляет `requires=("base",)`, но не вызывает команды или публичный API базового модуля. Реально ему нужны:

- формат drag-and-drop `ITEM_SECTION_MIME`;
- точка расширения `SectionGraphContribution`;
- платформенные `ctx.services`/`ctx.ui`.

Зависимость заявлена по имени модуля, а не по возможности. Загрузчик уже поддерживает capabilities; исправление — объявить у `base` `provides=("item.section.dragdrop",)`, а у `ogg_editor` — `needs=("item.section.dragdrop",)`.

## 3. EventBus и межмодульные коммуникации

### 3.3. `FILE_OPENED`/навигация всё ещё имеют щели

**Приоритет: высокий.**

- `request_id` в `FileOpened`/`FileOpenFailed` по-прежнему не заполняется и не используется; отложенная навигация хранится по пути (`PlatformApi._pending_file_actions`).
- Два запроса на один путь перетирают друг друга.
- `EditorTabs.open_file` публикует `FILE_OPENED` для существующего файла даже если редактор не смог показать его по другой причине. Для отсутствующего файла публикации уже нет — прежний пример из отчёта неактуален.
- `XmlFileOpener._on_resolved` при ошибке резолва не публикует `FILE_OPEN_FAILED`; при отсутствии дерева/конфигов публикация уже есть.
- `FileOpenRouter` не обнаруживает конфликты: два обработчика с одинаковым `priority` и `can_open` — первый молча побеждает.

### 3.4. Reserved-запросы между модулями без обработчиков

**Приоритет: средний.**

`request_window`, `request_tab`, `request_file_open` рассылают `UI_WINDOW_REQUESTED`, `UI_TAB_REQUESTED`, `UI_FILE_OPEN_REQUESTED`, но ни один модуль на них не подписан. Для окон/вкладок это фактически мёртвый API; работает только fallback `request_file_open`.

## 4. SDK: границы всё ещё размыты

### 4.1. SDK знает домен базового модуля

**Приоритет: высокий.**

- `CoreApi` содержит `item_catalog_root`, `build_item_catalog`, `build_item_entry`, `read_texture_region`, `load_item_icons`.
- `UiApi` содержит `item_entry`, `open_item_card_at_cursor`, `apply_resolved_field_edit`, `rename_resolved_field`, `retain_resolved_document`, `open_xml_resolved_tab` и т.д.
- `sdk.__init__` экспортирует `ItemCatalog`, `ItemEntry`, `ItemIcon`, `ItemSection`, `ItemCardRequest`, `ResolvedDocumentChange`, `LocalizationString`.

Модулю, которому нужен только логгер или меню, приходится зависеть от доменных понятий предметов и resolved-документов.

### 4.2. SDK отдаёт изменяемые внутренние объекты

**Приоритет: высокий.**

- `SectionGraphRequest.forest: object`, `overlay: object` — модуль получает сырой `LtxForest` и `ProjectOverlay`.
- `UiApi.workspace_forest()` возвращает тот же изменяемый лес.
- `SectionGraphContribution.edge_styles/openers` — изменяемые dict.
- `ctx.paths` — общий `SimpleNamespace`; модуль может изменить `projects_dir`/`generated_dir` для всех.

`ProjectOverlay` уже неизменяем, но сырой лес — нет; документация говорит «read-only», но это не обеспечено.

### 4.3. Адаптеры всё ещё полны fallback'ов

**Приоритет: средний.**

- `resolve_scan_dir` реализован только в `CoreApiAdapter`, не в ядре.
- `patch_target` считает родителя вручную по `include_parents`, не используя `core.patching.targets` и DLTX-привязки.
- `game_root` продублирован в `CoreServices.forest_game_root`, `CoreApiAdapter.game_root` и `ProjectPreviewMixin._asset_relative_path`.
- `run_resolver`, `assemble_text`, `open_external_editor`, `open_with_shell`, `read_text`, `read_xml_text` ищут методы по нескольким именам.
- `_call_with_overlay` через `inspect.signature` решает, передавать ли overlay; при переименовании параметра overlay молча не передастся.
- `CoreApiAdapter._shared_contributors` вешает реестр contributor'ов на `CoreServices` через `setattr`; при провайдере, не допускающем атрибуты, регистрации теряются.

## 5. Хранилище, кэш и производительность

### 5.1. Автосохранение всё ещё синхронное в UI-потоке

**Приоритет: средний.**

Per-keystroke проблема закрыта, но `ProjectController.autosave_project` по-прежнему вызывает `ProjectService.autosave()` синхронно раз в минуту. Для resolved-файла это сериализация, сжатие и запись десятков мегабайт в UI-потоке.

### 5.2. Копии больших текстов остаются в памяти

**Приоритет: средний.**

- В грязном состоянии `ProjectResolvedDraft` держит `original_text`, `current_text`, `saved_text` — до трёх копий.
- `ProjectDraft` аналогично.
- `ProjectOverlay` передаёт ссылки, но `_filter_overlay`, `build_preview` и патч-конвейер создают дополнительные срезы/копии.
- `ProjectPreviewMixin` хранит `GeneratedPatch` с полными текстами файлов; лимит 32 млн символов ограничивает, но не устраняет пиковую память.

### 5.3. Очистка кэша всё ещё не поколенческая

**Приоритет: низкий/средний.**

- 1 ГБ по байтам — предохранитель, а не управление поколениями.
- Старые ключи от прошлых overlays/mtime/`Resolver4.py` остаются до превышения лимита.
- `_prune_disk` запускается раз в 32 записи и удаляет по LRU-mtime; при резком росте каталог может временно превысить лимит.
- `clear_disk()` нигде не вызывается автоматически; ручной очистки в UI нет.
- `generated` и `projects` лежат рядом с исходниками/установкой, а не в пользовательском каталоге данных.

### 5.4. XML-цели патча читают диск, а не XML-черновики

**Приоритет: средний.**

Индексы `_ace_patch_target_index`/`_ace_xml_patch_target_index` сбрасываются при добавлении/удалении виртуальных файлов, но `_xml_target_index` читает XML через `read_xml_text(path)` с диска и не учитывает содержимое XML-черновиков проекта. Если правка XML меняет `#include`-структуру, цель патча может остаться вычисленной по диску.

### 5.5. `ProjectOverlay.revision` учитывает `line_sources` только по длине

**Приоритет: низкий.**

Для скорости в revision входит `len(line_sources)`, а не хэш содержимого. Если карта источников изменится при том же тексте и той же длине, ключ кэша может не измениться.

### 5.6. `ProjectService` защищён не полностью

**Приоритет: средний.**

`_write_meta` теперь под `_write_lock`, но:

- `ProjectService.active` меняется без общей блокировки;
- `_save_project_roots`, часть `status_text`/`list_projects` не защищены;
- `build_preview` делает снимок черновиков атомарно, но `ProjectController` в разных местах продолжает читать `self.project.active` без фиксации;
- фоновое автосохранение и `build_preview` могут пересекаться по времени.

## 6. Слойность и дублирование

### 6.1. `app`-слой появился, но границы описаны не полностью

**Приоритет: средний.**

- Таблица слоёв в `docs/modules_architecture.md` его не включает.
- `ui` импортирует `app` и `core`.
- `app` импортирует `core` напрямую; `test_architecture.py` проверяет только «app не импортирует ui/modules».
- `app/projects/service.py` и `ui/platform/project_controller.py` остаются крупными прикладными сервисами с бизнес-логикой.

### 6.2. Публичная поверхность `core` — это почти весь `core`

**Приоритет: средний.**

`core/__init__.py` экспортирует **165** имён из всех внутренних пакетов: патч-модели, парсеры, verifier’ы, resolver, XML, items, graph. `app/projects/service.py` импортирует из `core` **13** имён, UI импортирует `core` для чтения файлов и парсинга.

### 6.3. Патч-конвейер всё ещё частично собран в `app`

**Приоритет: средний.**

- `_asset_preview_item` вручную собирает `PatchPlan`, `GeneratedPatch`, `VerificationResult`.
- `_new_file_preview` делает то же для новых файлов.
- `_merge_xml_generated` вручную сливает XML-планы, файлы и verification.
- `add_item` вручную переводит `xml_override`/`xml`/`dxml_lua` в режимы ядра.
- `ProjectController.write_preview` сам собирает имя мод-каталога и обходит часть политик `PatchWriter`.

### 6.4. `write_preview` автоматически подтверждает опасные планы

**Приоритет: высокий по риску, низкий по объёму.**

`if plan.needs_confirmation: plan = replace(plan, confirmed=True)` — пользователь видит общий предпросмотр, но отдельного подтверждения для `needs_confirmation` нет. Для Override это потенциально опасно.

### 6.5. Дублирование path-key и нормализации

**Приоритет: средний.**

- `core/tools/cache.path_key` и `sdk/paths.path_key` — две реализации.
- `core/tools/fs.normalize_path` делает `normpath+abspath` без `normcase`.
- `app/workspace.py` сравнивает `Path` точным равенством.
- `TreeBuilder.add_virtual_file` использует `path.relative_to(scan_dir)` без нормализации регистра.

На Windows один и тот же путь с другим регистром может считаться разным в одном месте и тем же — в другом.

### 6.6. Дублирование «открыть сырой файл»

**Приоритет: низкий/средний.**

- `LtxFileOpener.open_raw`;
- `XmlFileOpener.open_raw`;
- `PlatformApi.open_raw`/`request_open_file_raw`;
- `FileOpenRouter.open_default`;
- `TreeActions.open_raw`.

Каждый путь сам решает, что считать «сырым», где взять текст и как показать.

### 6.7. Тема всё ещё не единый источник

**Приоритет: низкий.**

Остались жёсткие цвета:

- `ui/file_tree.py` — `HL_COLOR`;
- `ui/prebuild_panel.py` — `GREEN`;
- `ui/project_dialogs.py` — fallback `#F14C4C`, `#FFFFFF`;

Плюс `theme_color` читает глобальный `PALETTE`, а `apply_theme(app, palette)`/`apply_override_theme` не меняют `PALETTE`; при смене палитры модули и лексеры останутся на старой.

## 9. Остаточные риски

1. **Форматы событий изменились без обратной совместимости.** Модули обязаны использовать `Events.*`; старые строки вроде `"project_saved"` и старые payload'ы не поддерживаются.
2. **`SavedDraft.text` удалён.** Подписчику доступны `kind`, `key`, `path`, `revision`, `size`.
3. **Автосохранение осталось синхронным.** Сжатие и отсутствие лишних копий уменьшили проблему, но не убрали блокировку UI.
4. **XML overlay учитывает только raw XML-черновики.** `ProjectOverlay.resolved_edits` относится к LTX; XML-resolved правки хранятся отдельно и не подмешиваются в include-сборку.
5. **Debounce 250 мс.** Между вводом и обновлением проектного черновика есть задержка; сохранение/закрытие/смена проекта принудительно сбрасывают её.
6. **Лимит кэша 1 ГБ.** Это предохранитель, а не управление поколениями.
7. **Модули — доверенный код.** Process/FS-isolation нет; для сторонних/недоверенных модулей нужен отдельный plugin-host.
8. **`reload` отказывается работать при активных зависимых.** Для каскадной выгрузки есть `unload(..., force=True)`; автоматического восстановления зависимых после reload нет.

## 10. Приоритеты

**P1 — исправлять следующими:**

1. `FILE_OPEN_FAILED`/`request_id`/конфликты `FileOpenRouter` (§3.3).
2. Reserved-запросы между модулями (§3.4) — реализовать обработчики или удалить мёртвый API.
3. Границы SDK: убрать доменные item/resolved-интерфейсы, закрыть сырой `forest`/`overlay`, сделать `ctx.paths` read-only (§4.1, §4.2).
4. Отдельное подтверждение опасных `needs_confirmation`-планов (§6.4).

**P2 — важное, но не блокирующее:**
