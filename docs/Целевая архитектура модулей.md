# Архитектура модулей ACE — целевое (идеальное) состояние

Дата: 22.11.2026.

Статус: **целевой контракт расширений**. Документ описывает, как модуль
встраивается в приложение, что ему разрешено, чем он владеет и как
приложение остаётся устойчивым при добавлении, замене и выгрузке модулей.

Связанные документы:

- `docs/Целевая архитектура приложения.md` — слои, ядро, приложение,
  платформа и инварианты;
- `docs/План перехода к целевой архитектуре.md` — порядок миграции;
- `docs/old/modules_architecture.md` — исторический контракт (не источник
  правил).

---

## 0. Главный принцип

Модуль — **гость приложения**, а не его хозяин.

Он добавляет поведение, окна, команды, представления и доменные
возможности, но:

- не меняет ядро;
- не пишет оригиналы;
- не управляет чужими окнами и вкладками;
- не полагается на порядок загрузки;
- не импортирует внутренности приложения.

Модуль видит только **SDK**. Всё, что не описано в SDK, считается
внутренним и может измениться без предупреждения.

Модуль может использовать PyQt для собственных виджетов и собственные
third-party библиотеки для своей доменной логики (например, `soundfile` для
OGG). Но такие зависимости:

- принадлежат модулю, а не платформе;
- объявляются в README/манифесте;
- не проникают в публичный контракт других модулей;
- не блокируют UI;
- корректно обрабатывают отсутствие библиотеки.

## 1. План и факт: что принимается

| Аспект | Планировалось | Фактически | Решение |
|---|---|---|---|
| Управление окнами | Модуль управляет окнами почти полностью | Платформа показывает/закрывает окно по ключу | **Платформа владеет контейнером, модуль — содержимым и состоянием** |
| Дерево | Модуль регистрирует фильтры и сортировки | Такого API нет | **Реализовать проекции** |
| Жизненный цикл | `discover → init → register → activate` | Зависимости, версии, capabilities, rollback, unload/reload | **Оставить и расширить** |
| Связь модулей | Через события и команды | Плюс фактические зависимости по именам | **Capabilities вместо имён модулей** |
| SDK | Единый публичный контракт | В корне SDK есть предметы и resolved-поля | **Разделить на kernel/UI/features** |
| `base` | Обязательный монолит | Фактически обычный модуль, но по документам «обязательный» | **Стандартный модуль, не привилегированный загрузчиком** |
| Доверие | Не описано | Доверенный код в одном процессе | **Явные уровни доверия; песочница не обещается** |
| Выгрузка | Не описана | `unload`/`reload`, очистка регистраций | **Оставить и ужесточить владение** |
| Настройки проекта | Не описаны | `ProjectSetting` + реестр | **Оставить как точку расширения** |
| Двоичные ресурсы | Не описаны | `ProjectAssetType` + `FileReader` | **Оставить как точку расширения** |
| Граф связей | Не описан | Contributor'ы графа | **Оставить, добавить уверенность** |

Вывод: фактический загрузчик, реестры и владение регистрациями сильнее
исходного плана. Их нужно сохранить. Исправить нужно три вещи:

1. доменные понятия в корне SDK;
2. отсутствие проекций дерева;
3. неглубокое владение окнами/вкладками и зависимость по именам модулей.

## 2. Пакет модуля

### 2.1. Целевая структура

```text
modules/<module_id>/
  module.json          # манифест, читается до импорта кода
  __init__.py          # экспорт MODULE
  module.py            # класс модуля
  ui/                  # собственные окна и виджеты (PyQt)
  domain/              # собственная доменная логика модуля
  resources/           # иконки, тексты, шаблоны
  README.md            # что делает, какие capabilities нужны
```

Модуль может не иметь `ui/`, если он предоставляет только команды,
настройки, читатель файлов или capability.

### 2.2. Манифест

Целевой манифест — файл, а не только атрибут класса. Это позволяет:

- обнаруживать модуль без импорта кода;
- проверять совместимость до загрузки;
- хранить включённость/отключённость;
- показывать описание в интерфейсе;
- проверять trust level;
- не выполнять код несовместимого модуля.

Пример `module.json`:

```json
{
  "id": "ogg_editor",
  "name": "Редактор звуков OGG",
  "version": "0.2.0",
  "description": "Правка Vorbis-комментариев X-Ray и прослушивание.",
  "author": "ACE",
  "entrypoint": "module:OggEditorModule",
  "sdk": {
    "min": "0.3.0",
    "max": "1.0.0"
  },
  "requires": [],
  "optional_requires": [],
  "needs": [],
  "optional_needs": [
    "item.section.dragdrop",
    "section.graph",
    "project.assets"
  ],
  "provides": [
    "audio.ogg.editor"
  ],
  "trust": "trusted",
  "enabled_by_default": true,
  "platforms": ["windows"]
}
```

Поля:

| Поле | Назначение |
|---|---|
| `id` | Уникальное имя модуля и namespace |
| `version` | Версия модуля (semver) |
| `entrypoint` | `package.module:Class` |
| `sdk.min` / `sdk.max` | Диапазон совместимости SDK |
| `requires` | Обязательные модули, если без них нельзя |
| `optional_requires` | Необязательные модули |
| `needs` | Обязательные capabilities |
| `optional_needs` | Необязательные capabilities |
| `provides` | Capabilities, которые модуль предоставляет |
| `trust` | `core`, `trusted`, `untrusted` |
| `enabled_by_default` | Включать при первом запуске |
| `platforms` | Ограничение платформ |

Правила:

1. `id` совпадает с namespace команд, событий, окон и вкладок.
2. `requires` используется только тогда, когда нужен именно модуль, а не
   возможность. Предпочтительны `needs`.
3. `untrusted` не загружается текущим загрузчиком; для него нужен отдельный
   plugin-host.
4. Единственный манифест — `module.json`. Атрибут `manifest` в классе не
   используется.
5. Несовпадение `id` в манифесте и пакете/точке входа — ошибка загрузки.

### 2.3. Точка входа

```python
# modules/my_module/module.py
from sdk import ModuleBase
from sdk.contracts.events import Events


class MyModule(ModuleBase):
    def init(self, ctx):
        super().init(ctx)
        self._window = None

    def register(self, ctx):
        ctx.commands.register("my_module.show", self.show)

    def activate(self, ctx):
        pass

    def deactivate(self, ctx):
        if self._window is not None:
            ctx.ui.close_window("my_module.window")
            self._window = None

    def show(self):
        ...


MODULE = MyModule()
```

`__init__.py`:

```python
from .module import MODULE

__all__ = ["MODULE"]
```

## 3. Жизненный цикл

### 3.1. Фазы

```text
discover      — найти пакет и прочитать манифест
validate      — проверить SDK, зависимости, capabilities, trust
load          — импортировать точку входа
init          — создать состояние и подписки
register      — зарегистрировать вклады
workbench     — построить главное окно
activate      — создать окна и запустить отложенную работу
runtime       — события, команды, задачи, окна
deactivate    — остановить активность и закрыть своё
unload        — снять регистрации, дождаться задач, удалить пакет
```

### 3.2. Правила фаз

#### `discover`

- читается только манифест;
- код модуля не импортируется;
- дубликаты `id` фиксируются как ошибка;
- модуль может быть `disabled` без импорта.

#### `validate`

- версия SDK входит в диапазон;
- обязательные зависимости разрешены;
- capabilities доступны;
- trust level допустим;
- граф зависимостей ацикличен.

#### `load`

- импортируется `entrypoint`;
- класс наследует `ModuleBase`;
- `manifest.id` совпадает с файлом;
- ошибка импорта не роняет приложение.

#### `init`

Разрешено:

- создать внутреннее состояние;
- подписаться на события;
- прочитать свои настройки;
- определить каталоги.

Запрещено:

- создавать окна;
- запускать тяжёлую работу;
- обращаться к ещё не созданному workbench;
- менять состояние других модулей.

#### `register`

Разрешено:

- меню, команды, горячие клавиши;
- действия дерева и вкладок;
- обработчики открытия;
- типы ресурсов, настройки, читатели;
- contributor'ы графа;
- capabilities.

Запрещено:

- создавать окна;
- запускать длительные операции;
- полагаться на порядок других модулей.

`register` транзакционен: если он упал, все регистрации откатываются,
модуль переходит в `FAILED`, зависимые не активируются.

#### `activate`

- workbench уже существует;
- можно создавать окна, вкладки и панели;
- тяжёлая работа — через `ctx.tasks`;
- ошибка `activate` откатывает модуль.

#### `deactivate`

- остановить свои задачи;
- закрыть свои окна и вкладки;
- сохранить своё состояние;
- отписаться от событий (или положиться на `ctx.registrations`);
- не трогать чужие данные.

#### `unload`

- `ctx.registrations.dispose()`;
- закрытие окон/вкладок владельца;
- ожидание задач владельца;
- удаление пакета из `sys.modules`;
- очистка кэшей модуля.

### 3.3. Состояния

```text
DISCOVERED
VALIDATED
LOADED
INITIALIZED
REGISTERED
ACTIVE
FAILED
SKIPPED
DISABLED
UNLOADED
```

Правила переходов:

- `FAILED` не активируется и не оставляет регистраций;
- `SKIPPED` содержит причину (`ModuleSkip`);
- `DISABLED` сохраняется между запусками;
- `UNLOADED` удаляет пакет и регистрации;
- повторная загрузка начинает с `DISCOVERED`.

### 3.4. Включение и отключение

- Состояние включённости хранится в `<app>/config/modules.json`.
- Отключение равно `deactivate + unload`, но модуль остаётся в списке.
- Включение выполняет `load → init → register → activate`.
- Если модуль предоставляет capability, от которого зависят активные
  модули, отключение требует подтверждения и каскадной деактивации
  зависимых.
- `reload` не должен оставлять старые регистрации и окна.

### 3.5. Ошибки

- ошибка `init/register/activate` — модуль `FAILED`;
- ошибка подписчика события — лог, остальные работают;
- ошибка команды — типизированный результат, не падение;
- ошибка задачи — `on_done(result, error)`;
- ошибка модуля не ломает платформу и другие модули.

## 4. Зависимости и capabilities

### 4.1. Почему не имена модулей

`requires=("base",)` означает «мне нужен конкретный модуль». Но модулю
обычно нужна **возможность**:

- принять drag-and-drop предмета;
- получить каталог предметов;
- добавить узел в граф;
- открыть документ;
- предложить патч.

Если зависеть от имени, нельзя заменить `base` или собрать приложение без
него. Если зависеть от capability, можно.

### 4.2. Контракт capability

```text
Capability
  name: str                 # "item.section.dragdrop"
  version: str              # semver
  provider: module_id
  protocol: type/protocol   # типизированный контракт в sdk.features.*
  lifetime: module          # живёт, пока жив провайдер
```

API контекста:

```python
cap = ctx.capabilities.require("items.catalog", min_version="1.0")
cap = ctx.capabilities.optional("section.graph")
ctx.capabilities.provide("items.catalog", "1.0", service)
```

Правила:

1. Capability имеет типизированный протокол в SDK.
2. Потребитель не знает, какой модуль предоставляет capability.
3. Провайдер может быть заменён без изменения потребителя.
4. Отсутствие optional capability — не ошибка; модуль деградирует.
5. Отсутствие required capability — `SKIPPED` с причиной.
6. Версия capability проверяется при загрузке.
7. Модуль получает capability в `init`/`register` и хранит ссылку; не
   вызывает `require` на каждый кадр/строку.

### 4.3. Примеры

`base` (стандартный модуль) может предоставлять:

```text
document.viewer.ltx
document.viewer.xml
section.graph
project.standard_views
```

`item_browser` может предоставлять:

```text
items.catalog
item.section.dragdrop
```

`ogg_editor`:

```json
{
  "optional_needs": [
    "item.section.dragdrop",
    "section.graph",
    "project.assets"
  ]
}
```

Если `item.section.dragdrop` отсутствует, drag-and-drop просто не
включается, а модуль продолжает работать с файлами `.ogg`. Это важное
правило: удобная интеграция не должна превращаться в обязательную
зависимость.

### 4.4. Запрещённые зависимости

Модулю нельзя:

- импортировать другой модуль;
- хранить ссылку на объект другого модуля;
- вызывать внутренние классы другого модуля;
- рассчитывать на порядок загрузки;
- требовать необязательный модуль как обязательный.

Связь — только события, команды и capabilities.

## 5. Контекст модуля

`ctx` создаётся для каждого модуля отдельно. Это не глобальный синглтон.

| Поле | Назначение |
|---|---|
| `ctx.module_id` | Имя модуля из манифеста |
| `ctx.kernel` | Версия SDK, доступные модули, capabilities |
| `ctx.services` | Запросы к ядру: дерево, документы, резолв, граф |
| `ctx.documents` | Открытие и правка документов |
| `ctx.patches` | Предложение изменений (без фиксации) |
| `ctx.ui` | Меню, окна, вкладки, диалоги, тема |
| `ctx.tasks` | Фоновые задачи и отмена |
| `ctx.events` | Подписки и публикация фактов |
| `ctx.commands` | Регистрация и выполнение команд |
| `ctx.capabilities` | Провайдеры и потребители возможностей |
| `ctx.projects` | Настройки, asset-типы, читатели |
| `ctx.paths` | Неизменяемые пути приложения и единая идентичность путей (`key`, `same`) |
| `ctx.registrations` | Scope всех регистраций модуля |
| `ctx.log` | Диагностика |

### 5.1. Типизация

Контекст должен быть типизированным. Модуль не должен искать методы по
именам, использовать `getattr` и «если метод есть — вызовем». Такие
fallback'и скрывают несовместимость.

Правило:

> Если модуль хочет использовать возможность, он объявляет её в манифесте
> и получает типизированный протокол. Если возможности нет — получает
> `None` для optional или `SKIPPED` для required.

### 5.2. Версии API

До первого релиза действует простой режим:

- **stable** — предназначен для использования, но до `1.0` может меняться;
- **experimental** — может меняться в любой момент;
- **internal** — не входит в SDK;
- **deprecated** не используется до `1.0`: старое удаляется, а не живёт
  параллельно.

После `1.0`:

- ломающие изменения — только в мажорной версии;
- появляется политика deprecation;
- `sdk.max` рекомендуется указывать внешним модулям; отсутствие даёт
  предупреждение.

Модуль указывает `sdk.min`/`sdk.max`. Приложение проверяет совместимость
до `init`.

## 6. Точки расширения

### 6.1. Команды и действия

| Возможность | Целевой API | Владелец | Конфликт |
|---|---|---|---|
| Пункт меню | `ctx.ui.register_menu(...)` | модуль | уникальный `action` |
| Горячая клавиша | `ctx.ui.register_shortcut(...)` | модуль | уникальная комбинация в scope |
| Мышиная привязка | `ctx.ui.register_mouse_binding(...)` | модуль | уникальная комбинация |
| Команда | `ctx.commands.register("id.action", fn)` | модуль | нельзя занять чужую |
| Действие дерева | `ctx.ui.register_tree_action(...)` | модуль | порядок по приоритету |
| Действие вкладки | `ctx.ui.register_file_action(...)` | модуль | порядок по приоритету |
| Перехват UI-действия | `ctx.ui.register_action_handler(...)` | модуль | приоритет, первый truthy |

Имена:

```text
<module_id>.<name>
```

Пример:

```text
ogg_editor.window
ogg_editor.open
ogg_editor.add
```

### 6.2. UI-поверхности

| Возможность | Целевой API | Примечание |
|---|---|---|
| Собственное окно | `ctx.ui.open_window(WindowSpec, widget)` | платформа владеет контейнером |
| Вкладка | `ctx.ui.open_tab(TabSpec, widget)` | owner обязателен |
| Док/панель | `ctx.ui.open_dock(DockSpec, widget)` | раскладка у платформы |
| Диалог | `ctx.ui.show_dialog(...)` | модальность у платформы |
| Статус | `ctx.ui.set_status(...)` | не хранит бизнес-данные |
| Уведомление | `ctx.ui.notify(...)` | без блокировки |
| Тема | `ctx.ui.theme_color(token)` | без импорта `ui.theme` |
| Подсказки | `ctx.ui.attach_text_hints(...)` | без собственного popup |

### 6.3. Документы

| Возможность | Целевой API | Примечание |
|---|---|---|
| Обработчик открытия | `ctx.ui.register_open_handler(FileOpenHandler)` | приоритет и контекст |
| Просмотр файла | `ctx.ui.register_file_viewer(...)` | для своего типа |
| Читатель файла | `ctx.projects.register_file_reader(...)` | потокобезопасный |
| Открыть документ | `ctx.documents.open(DocumentRef)` | через платформу |
| Изменить документ | `ctx.documents.apply(DocumentEditIntent)` | в черновик проекта |
| Подписаться | `ctx.documents.subscribe(handle, fn)` | событие изменения |
| Предложить патч | `ctx.patches.propose(PatchRequest)` | без записи |

Модуль не пишет файл напрямую. Он создаёт `DocumentEditIntent` или
`PatchRequest`.

### 6.4. Дерево

| Возможность | Целевой API | Примечание |
|---|---|---|
| Фильтр | `ctx.tree.register_filter(TreeFilter)` | проекция, не мутация |
| Сортировка | `ctx.tree.register_sort(TreeSort)` | стабильный порядок |
| Группировка | `ctx.tree.register_grouping(...)` | представление |
| Колонка | `ctx.tree.register_column(...)` | значение из проекции |
| Контекстное действие | `ctx.ui.register_tree_action(...)` | predicate |
| Запрос среза | `ctx.tree.query(TreeQuery)` | возвращает `TreeProjection` |

Фильтр не удаляет данные из ядра. Он влияет только на проекцию.

### 6.5. Данные проекта

| Возможность | Целевой API | Примечание |
|---|---|---|
| Тип ресурса | `ctx.projects.register_asset_type(...)` | `ProjectAssetType` |
| Настройка | `ctx.projects.register_setting(...)` | `ProjectSetting` |
| Читатель | `ctx.projects.register_file_reader(...)` | `FileReader` |
| Экспорт | `ctx.projects.register_export(...)` | опционально |
| Событие сохранения | `Events.PROJECT_SAVED` | payload `SavedDraft` |

Целевой контракт — только `ctx.projects`. Старые имена
(`ctx.ui.register_project_asset_type`, `ctx.ui.register_project_setting`,
`ctx.ui.register_file_reader`) не входят в него и удаляются, а не
превращаются в shim. Встроенные модули обновляются вместе с контрактом.

### 6.6. Граф связей

| Возможность | Целевой API | Примечание |
|---|---|---|
| Дополнительные узлы | `ctx.services.register_graph_contributor(...)` | capability-зависимость |
| Стиль связи | `GraphEdgeStyle` | токен темы |
| Открытие узла | `opener` | модуль сам знает свой тип |
| Уверенность | `confidence` | `exact/probable/heuristic` |

Contributor не должен сканировать всю VFS на каждый вызов. Он получает
`SectionGraphRequest` с уже подготовленным контекстом и возвращает только
свои связи.

### 6.7. Диагностика

| Возможность | Целевой API | Примечание |
|---|---|---|
| Провайдер дампа | `ctx.diagnostics.register_dump_provider(...)` | секции, ключи, источники |
| Сравнение с игрой | `ctx.diagnostics.register_parity_check(...)` | эталонные наборы |
| Метрики | `ctx.diagnostics.metric(...)` | без блокировки |
| Отчёт | `ctx.diagnostics.register_report(...)` | экспорт |

### 6.8. Что нельзя расширять модулями

Следующие вещи остаются в ядре и не являются точками расширения:

- семантика Resolver4;
- правила include/DLTX/DXML;
- формат `PatchPlan` и проверки;
- `PatchWriter`;
- безопасность путей;
- базовые модели снимка и документа.

Модуль может **предложить** изменение, но не может подменить правила
движка.

## 7. Владение и изоляция

### 7.1. Владелец

У всего, что создаёт модуль, есть владелец:

- окно;
- вкладка;
- подписка;
- команда;
- задача;
- настройка;
- asset-тип;
- читатель;
- contributor графа;
- capability.

Владелец — `manifest.id`. Платформа проверяет его при:

- закрытии окна/вкладки;
- снятии регистрации;
- отмене задачи;
- замене настройки/типа;
- выгрузке модуля.

### 7.2. Что модуль не может

- закрыть чужое окно;
- закрыть чужую вкладку;
- снять чужую команду;
- снять чужую подписку;
- заменить чужой asset-тип;
- изменить чужую настройку;
- удалить чужого contributor'а;
- получить чужой виджет;
- изменить глобальное состояние платформы.

Попытка — ошибка с записью в диагностику, а не тихий обход.

### 7.3. Регистрации

Все регистрации возвращают `RegistrationHandle`.

```python
handle = ctx.ui.register_menu(...)
ctx.registrations.track(handle)
```

`ModuleContext` собирает регистрации в `RegistrationScope`. Загрузчик
вызывает `scope.dispose()`:

- после `deactivate`;
- при откате упавшего `init/register/activate`;
- при выгрузке.

Регистрация после выгрузки отклоняется.

### 7.4. Доверие

| Уровень | Значение | Изоляция |
|---|---|---|
| `core` | Встроенный код платформы | Нет, полный доступ |
| `trusted` | Проверенный модуль | Контракт, владение, тесты |
| `untrusted` | Сторонний код | Требует отдельного plugin-host |

Текущая архитектура — доверенный код в одном процессе. Это не песочница.
Обещать безопасность от вредоносного модуля нельзя. Можно и нужно
обеспечивать:

- предсказуемость;
- владение;
- отсутствие случайных глобальных эффектов;
- изоляцию ошибок;
- запрет записи в оригиналы.

## 8. Потоки и задачи

### 8.1. Правила

- UI-поток — только виджеты и короткие операции.
- `ctx.tasks.run(fn, on_done, on_log, owner)` — фоновая задача.
- `on_done`/`on_log` вызываются в UI-потоке.
- CPU-heavy Python — через пул процессов платформы.
- Нельзя создавать неограниченные `QThread`/`multiprocessing.Pool` в модуле.
- Отмена кооперативная: задача проверяет `handle.cancelled`.
- При `deactivate` задачи владельца отменяются и ожидаются.

### 8.2. TaskHandle

```python
handle = ctx.tasks.run(
    fn,
    on_done=...,
    on_log=...,
    priority="normal",
)
handle.cancel()
```

Требования:

- прогресс;
- отмена;
- таймаут;
- владелец;
- ошибка не выходит в Qt event loop;
- результат — типизированный объект или ошибка.

### 8.3. Запрещено

- блокировать UI-поток файловым I/O;
- вызывать `dispatch` из фона;
- трогать виджеты из фона;
- держать глобальные блокировки на время резолва;
- запускать процессы без ограничения.

### 8.4. Операции и зависимости

- Модуль не создаёт собственный загрузочный экран, очередь или popup
  ожидания.
- Долгая операция регистрируется в платформенном `OperationRegistry`.
- У операции есть owner, состояние, прогресс, отмена и зависимости.
- У операции есть стабильный `operation_key`; повторный запуск с тем же
  ключом не создаёт дубль.
- При повторе UI показывает «операция уже запущена» и поднимает
  существующую операцию.
- Если действие модуля зависит от операции, блокируется только это
  действие, а не всё приложение.
- Пользователь видит причину блокировки: «идёт сборка», «операция в
  очереди», «операция отменена».
- Ошибка или отмена операции не оставляет модуль в вечном ожидании.
- Очередь операций — общая платформенная панель, а не модульный виджет.

## 9. UI-расширения

### 9.1. Окна

Модуль создаёт `QWidget`, платформа — контейнер.

```python
spec = WindowSpec(
    key="ogg_editor.window",
    title="Редактор звуков",
    kind="dock",
    area="right",
    size=(900, 600),
    closable=True,
    state_key="ogg_editor.main",
)
ctx.ui.open_window(spec, widget)
```

Правила:

- ключ namespace'ирован;
- owner берётся из контекста, а не из ключа;
- модуль не вызывает `window.show()` напрямую для чужих окон;
- платформа применяет размер, док, плавающий режим и состояние;
- модуль сохраняет только состояние своего содержимого.

### 9.2. Вкладки

```python
spec = TabSpec(
    id="ogg_editor.tab:<path>",
    title="OGG",
    owner="ogg_editor",
    source_path=path,
    close_policy="ask_if_dirty",
)
ctx.ui.open_tab(spec, widget)
```

Правила:

- owner обязателен;
- чужую вкладку закрыть нельзя;
- `dirty`/`busy` — состояние вкладки, а не только текст заголовка;
- `source_path` связывает вкладку с файлом и навигацией;
- закрытие приложения проходит через политику вкладки.

### 9.3. Меню, клавиши, действия

- Имена действий namespace'ированы.
- `action` позволяет перехватить действие через `dispatch`.
- Без `action` платформа всё равно рассылает общие `ui.shortcut`/`ui.mouse`.
- Модуль не ставит глобальные Qt-хуки.
- Конфликт горячих клавиш диагностируется, а не «кто последний, тот прав».

### 9.4. Тема

- Модуль получает цвета через `ctx.ui.theme_color(token)`.
- Импорт `ui.theme` запрещён.
- Жёсткие цвета в модуле запрещены, кроме собственного брендинга,
  документированного как исключение.
- Смена темы обновляет и модульные окна.

### 9.5. Подсказки

- Модуль не создаёт собственный popup.
- Он подключает платформенный движок к своему текстовому полю:

```python
handle = ctx.ui.attach_text_hints(
    widget,
    target=HintTargetInfo(
        surface=SURFACE_ENGINE_TEXT,
        language=LANGUAGE_LOCALIZATION_TEXT,
        role="item.description",
    ),
)
```

- `handle.detach()` — при закрытии окна.
- Провайдеры, каталоги и правила вставки живут в платформе.

### 9.6. Drag-and-drop

- Общий MIME-контракт — в `sdk.dragdrop`.
- Модуль-источник кодирует данные.
- Модуль-получатель декодирует.
- Главное окно принимает drop, но не интерпретирует.
- Модули не импортируют окно-источник.

## 10. Данные и доменные расширения

### 10.1. Типы ресурсов проекта

Модуль регистрирует `ProjectAssetType`:

```python
ctx.projects.register_asset_type(
    ProjectAssetType(
        key="sound.ogg",
        label="Звук Ogg Vorbis",
        extensions=(".ogg",),
        vfs_root="sounds",
        save_mode_setting="ogg_editor.save_mode",
        save_modes=("override",),
    )
)
```

Правила:

- путь проверяется по `gamedata/<vfs_root>/...`;
- конфликт `(vfs_root, extension)` запрещён;
- при выгрузке модуля тип снимается;
- проект не пишет неизвестный тип «вслепую»;
- сохранение — через patch-конвейер.

### 10.2. Настройки проекта

```python
ctx.projects.register_setting(
    ProjectSetting(
        key="ogg_editor.save_mode",
        label="ogg-патч",
        kind="choice",
        default="override",
        choices=(...),
    )
)
```

Значения хранятся в `project.json` и доступны через `ctx.projects.setting`.

### 10.3. Читатели файлов

```python
class OggCommentReader(FileReader):
    priority = 100

    def can_read(self, path, data=None):
        return Path(path).suffix.lower() == ".ogg"

    def read(self, path, data=None):
        return FileView(text=..., label="Комментарии Ogg Vorbis")


ctx.projects.register_file_reader(OggCommentReader())
```

Требования:

- `read` — чистая трансформация;
- вызывается в фоне;
- не трогает Qt;
- ошибка читателя не блокирует запись, но попадает в заметки;
- выбор — первый подходящий по `priority`.

### 10.4. Доменные фичи

Домен — не модуль и не ядро в чистом виде. Целевая схема:

```text
core/formats/...          — общие форматы (DDS, кодировки)
app/features/items/       — доменный сервис каталога предметов
sdk/features/items/       — DTO и протокол capability
modules/item_browser/     — UI-модуль каталога
modules/ogg_editor/       — UI/формат-модуль звуков
```

Правила:

- ядро не знает слов «предмет», «иконка», «инвентарь»;
- корень SDK не экспортирует `ItemCatalog`;
- модуль получает каталог через capability `items.catalog`;
- если capability нет, UI-модуль не загружается или деградирует;
- доменный сервис может использовать `core` и кэш платформы;
- UI-модуль импортирует только SDK и PyQt.

### 10.5. Ограничения на данные

Модуль не должен:

- писать в `forest`/`snapshot`/`project` напрямую;
- менять чужие черновики;
- обходить `ProjectOverlay`;
- кэшировать данные без привязки к снимку;
- хранить полные тексты в событиях;
- использовать `id()` объекта как идентификатор.

### 11.1. События

- Факт, много подписчиков, отменить нельзя.

- Чужая команда не регистрируется.

### 12.2. `module.py`

```python
from sdk import ModuleBase
from sdk.contracts.events import Events


class ExampleModule(ModuleBase):
    def init(self, ctx):
        super().init(ctx)
        self._window = None
        self._sub = ctx.events.subscribe(
            Events.TREE_READY,
            self._on_tree_ready,
        )

    def register(self, ctx):
        ctx.commands.register("example_module.show", self.show)
        ctx.ui.register_menu(
            "Инструменты",
            "Пример модуля",
            self.show,
            "Ctrl+Alt+E",
            action="example_module.show",
        )
        ctx.projects.register_setting(...)
        ctx.capabilities.provide(
            "example.capability",
            "1.0",
            self._service,
        )

    def activate(self, ctx):
        ctx.log("example_module активирован")

    def deactivate(self, ctx):
        self._sub.unsubscribe()
        if self._window is not None:
            ctx.ui.close_window("example_module.window")
            self._window = None

    def _on_tree_ready(self, payload):
        pass

    def show(self):
        if self._window is None:
            self._window = ExampleWindow(self.ctx)
        self.ctx.ui.open_window(
            WindowSpec(
                key="example_module.window",
                title="Пример",
                kind="floating",
            ),
            self._window,
        )
```

## 14. Антипаттерны

| Антипаттерн | Почему плохо | Правильно |
|---|---|---|
| `import core` | Ломает границу и версионирование | `ctx.services` |
| `import ui.main_window` | Модуль зависит от экрана | `ctx.ui` |
| `from modules.other import ...` | Модули связаны напрямую | events/commands/capabilities |
| `requires=("base",)` без необходимости | Фантомная зависимость | `needs=("capability",)` |
| `window.show()` для чужого окна | Нет владельца | `ctx.ui.open_window(WindowSpec, ...)` |
| `QApplication.installEventFilter` | Глобальный хук | `ctx.ui.register_shortcut/mouse` |
| `open(path, "w")` | Обход патч-конвейера | `ctx.documents.apply`/`ctx.patches.propose` |
| `time.sleep` в UI | Блокировка | `ctx.tasks.run` |
| `dispatch` из фона | Нарушение потока | `publish` или отложенный вызов |
| `id(obj)` в ключе | Нестабильно | `SnapshotId`/`DocumentRef` |
| `confirmed=True` вручную | Обход подтверждения | `CommitAuthorization` |
| жёсткий цвет | Тема не единая | `ctx.ui.theme_color` |
| собственный popup подсказок | Дублирование движка | `attach_text_hints` |
| кэш без снимка | Устаревшие данные | `CacheService` + snapshot |
| `getattr(api, "method", None)` | Скрытая несовместимость | явный протокол/версия |

## 15. Переход без legacy

### 15.1. Текущие модули

`base_module` и `ogg_editor` обновляются вместе с контрактом. После каждого
этапа приложение остаётся рабочим, но публичной совместимости со старыми
именами нет.

Порядок:

1. Ввести новые контракты сразу, без параллельных shim'ов.
2. Обновить `base_module` и `ogg_editor` в том же изменении.
3. Обновить тесты и примеры.
4. Удалить старые имена и пути.
5. Не вводить deprecation до `1.0`.

### 15.2. `base_module`

Целевое состояние:

- `base` — стандартный модуль, но не привилегированный загрузчиком;
- workspace-бутстрап (выбор папки, построение дерева) — в платформе/`app`,
  а не в `base`;
- `base` предоставляет viewers, graph и стандартные действия;
- предметный UI и dragdrop вынесены в `item_browser`;
- `base` не является обязательной зависимостью по имени.

Если `base` отсутствует:

- приложение всё равно открывает дерево и сырой текст;
- resolved-вьюеры недоступны;
- это диагностируется, а не падает.

### 15.3. `ogg_editor`

Целевое состояние:

- `optional_needs=("item.section.dragdrop", "section.graph",
  "project.assets")`;
- не зависит от `base` по имени;
- если dragdrop нет, работает без него;
- регистрирует asset-тип, настройку и reader через `ctx.projects`;
- не импортирует `core`/`ui`.

### 15.4. Версия SDK

- До `1.0` — `0.x`: ломающие изменения разрешены, публичных shim'ов нет.
- После появления kernel/UI/features и прохождения conformance-тестов —
  `1.0`.
- После `1.0` ломающие изменения — только в мажорной версии, с политикой
  deprecation.
- Модуль без `sdk.max` считается совместимым с текущей мажорной версией,
  но получает предупреждение.

## 16. Критерии готовности модульной системы

1. Модуль-образец собирается и работает, импортируя только `sdk`.
2. Модуль-образец выгружается без окон, вкладок, задач и регистраций.
3. Модуль не может закрыть чужое окно/вкладку.
4. Ошибка `register` откатывает все регистрации.
5. Ошибка `activate` не ломает платформу.
6. Отключение провайдера capability каскадно обрабатывает зависимых.
7. `ogg_editor` не зависит от `base` по имени.
8. `base` не является обязательным для запуска приложения.
9. Корень SDK не содержит предметов и resolved-полей.
10. Фильтры/сортировки дерева регистрируются через SDK.
11. Окна/вкладки имеют явного владельца и состояние.
12. Тема едина; жёстких цветов в модулях нет.
13. Манифест читается без импорта кода.
14. Единственный манифест — `module.json`; class-manifest не используется.
15. `untrusted` явно отклоняется до появления plugin-host.
16. Нет публичных shim'ов, legacy-алиасов и deprecation до `1.0`.
17. Тяжёлые операции модуля видны в общем центре операций; зависимые
    действия блокируются точечно.
18. Повторный запуск операции модуля не создаёт дубль.
19. README и conformance-тесты описывают контракт.

## 17. Итоговая формула

> Модуль — это **набор возможностей с владельцем**, а не набор глобальных
> side-effect'ов.

Устойчивая модульная система держится на четырёх вещах:

1. **Контракт** — только SDK, версии, типы.
2. **Владение** — окна, вкладки, задачи и регистрации принадлежат модулю.
3. **Возможности** — зависимости по capabilities, а не по именам.
4. **Изоляция ошибок** — падение модуля не ломает приложение.

Если эти четыре вещи соблюдены, новый модуль можно добавить, заменить или
выгрузить, не пересобирая фундамент.
