## 3. Тяжёлые операции и зависимости: текущее состояние

Правило из `AGENTS.md` §6 реализовано в основной части на шаге 6.2.
Остались ограничения, перечисленные ниже.

### Что уже работает правильно

- `OperationRegistry` хранит состояния `queued/running/done/failed/
  cancelled`, прогресс, владельца, зависимости и счётчик повторных
  запросов; UI читает снимки, не блокируя задачи.
- `TaskService` выдаёт `TaskHandle` с `progress/cancel/wait`, поддерживает
  `operation_key`, single-flight и `depends_on`; повторный запуск
  возвращает существующую операцию, а не создаёт дубль.
- `TaskService` использует пул daemon-потоков (`max_workers`, по
  умолчанию 4), приоритетную очередь и отдельную очередь зависимостей;
  `priority` больше — раньше.
- `OperationCenter` в строке состояния показывает активные операции и
  открывает немодальный список; `PrebuildPanel` удалён.
- Предсборка `vfs.prebuild` показывается в общем центре и отменяется
  через него.
- `WorkspaceActions` (`vfs.rebuild`), `ItemViewerFeature`
  (`items.catalog`), `SectionGraphFeature` (`section.graph:*`),
  `build_patch_preview` и запись патча используют стабильные ключи;
  локальные `_running` удалены.
- `ProjectController.load_project` выполняет поиск (`project.list`) и
  `ProjectService.load` в `TaskService`, ждёт `vfs.rebuild`, если дерево
  ещё строится; busy-индикатор сохраняется.
- `ProjectController.create_project` выполняет `ProjectService.create` в
  `TaskService` с `operation_key="project.create"` и ждёт `vfs.rebuild`;
  `ItemViewerFeature` также ставит `items.catalog` в очередь до сборки VFS.
- `ProjectController._delete_project` выполняет удаление задачей
  `project.delete:<id>`; UI-поток не удаляет каталог проекта.
- `CacheService` дедуплицирует одновременное вычисление одного ключа
  (single-flight) и привязывает записи к `snapshot_id`/зависимостям.
- `SnapshotService` пересчитывает файловый индекс только при явной
  пересборке VFS; смена overlay создаёт новую ревизию без сканирования.
- `ResolverService.assemble_semantic` (4.1) — отдельный тяжёлый проход.
  Карточка секции (4.2) запускает его через `TaskService`
  (`SectionCardMixin.open_section_card`), UI-поток только создаёт
  диалог и показывает результат. Повторный запрос той же карточки
  поднимает существующую и не создаёт вторую задачу.
- `HintService` — платформенный движок подсказок: контроллер, popup,
  адаптеры, провайдеры и каталоги. Модули подключают его через
  `ctx.ui.attach_text_hints`, собственный hint-popup не создают.
  LTX-провайдеры включены; UI не импортирует `core` (граница
  `app.hints`/`app.lexing`).

### Чего не хватает

1. **Прогресс модульных задач в основном текстовый.**
   `TaskHandle.progress` существует, но модули пока передают прогресс
   через `log`; точные `done/total` есть у предсборки и платформенных
   операций.

### Что нельзя делать сейчас

- Не добавлять новый модульный «загрузочный экран» или свой popup
  ожидания.
- Не блокировать всё приложение модальным progress dialog.
- Не добавлять новый `QThread`/`ProcessPool` в модуль.
- Не строить очередь операций «на месте» в UI без платформенного реестра.
- Не добавлять локальные `_running`-флаги как замену `operation_key`.
- Не считать `OperationCenter` владельцем бизнес-логики: он только
  показывает снимки и просит отмену.

### Что будет позже

Этап 7 завершён: шаги 7.1–7.10 закрыты, включая `module.json`,
состояния загрузчика, `CapabilitiesApi`, `base`/`item_browser`,
`ogg_editor`, домен items в `app`, conformance, item-кэши, graph-кэш и
`confidence` связей. По ADR-35 `base` обязателен и загружается всегда.
Следующий этап — 8; он не начат и требует отдельного подтверждения
оператора.

## 5. Данные

- `generated/cache-v2/*` — расходуемый кэш. Старые
  `generated/resolved_cache` и `generated/item_cache` не читаются и
  удаляются при старте; миграции нет.
- `generated/assets` и `generated/theme_icons` — материализованные
  ресурсы, не кэш резолва; удаляются только вручную.
- `config/layout.json` — платформенная раскладка окон (geometry/docks/
  splitter, dock-записи, окна модулей и `state_key`-состояния
  содержимого). Не кэш и не данные проекта; повреждённый файл
  игнорируется, запись окон отсутствующих модулей не мешает старту.
- `config/file_open.json` — предпочтения обработчиков открытия по
  расширению и контексту (`view/edit/preview/patch`). Формат версии 2;
  файл несовместимой версии игнорируется целиком. Не кэш и не данные
  проекта.
- `config/modules.json` — пользовательское включение/отключение модулей
  (схема `1`, только `enabled`); не кэш и не данные проекта. `base`
  обязателен: запись `base: false` игнорируется (ADR-35). Future-схема
  не интерпретируется и защищена от записи; повреждённый файл
  переименовывается в `modules.json.broken-<timestamp>`. Игнорируется
  Git.
- `generated/patch-audit-<session>.log` — JSONL-журнал успешных
  записей патчей; новый файл на каждую сессию приложения, старые не
  удаляются автоматически; не кэш.
- `projects/` — пользовательские данные. Схема `2`
  (`schema_version` в `project.json`); миграция только вперёд, один раз,
  с backup `.migration_backup_*`; обратное чтение не поддерживается.
  Менять схему — только по ADR, с backup и тестами миграции.
  Автоматически удалять backup запрещено; ручная очистка с
  подтверждением — GAP-6, не реализована.
- `tests/main_unit_test_*` — контракт поведения, не менять без оператора.
- Форматы игры LTX/XML/DLTX/DXML — полная совместимость.
