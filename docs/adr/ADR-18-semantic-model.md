# ADR-18. Семантическая модель LTX и происхождение значений

Дата: 23.11.2026
Статус: accepted

## Контекст

`docs/План перехода к целевой архитектуре.md` §7 требует для каждой
секции и ключа отвечать: откуда значение, в каком моде, с каким
приоритетом, к какому корню относится, какая цепочка переопределений и
какая операция применена.

Текущий `LtxResolverAdapter` отдаёт только итоговый текст и построчные
`LineSource`. `Resolver4` уже вычисляет победителя, но теряет
проигравшие объявления при сортировке и слиянии. Повторный разбор
миллионов строк ради provenance запрещён планом и слишком дорог.

Дополнительно:

- в `core.patching.ltx.diff` уже есть публичный `SectionSnapshot` —
  снимок секции для создания патча; это другое понятие;
- семантическая модель ссылается на объекты `Resolver4` и не должна
  сериализоваться в дисковый кэш;
- запись патчей заморожена до Этапа 5, поэтому модель на этом шаге
  только читает данные.

## Решение

1. Модели живут в `src/core/semantic/`: `RootRef`, `SourceRef`,
   `ValueSource`, `OverrideChain`, `PropertySnapshot`,
   `SectionSnapshot`, `Diagnostics`, `ResolvedRoot`, `SectionIndex`.
2. `core.semantic.SectionSnapshot` — модель **разрешённой** секции; она
   не заменяет `core.patching.ltx.diff.SectionSnapshot`. Модели не
   добавляются в `core.__all__`, чтобы не создавать второе публичное
   имя в корне. Порт `core.api.resolve` даёт явный доступ прикладному
   слою.
3. Provenance снимается инструментированным подклассом
   `Resolver4.LtxResolver` (`SemanticProvenanceMixin`):
   - объявления записываются до `_sort_and_filter_section`;
   - фиксируются родители, CSV-операции `>`/`<`, удаления и
     предупреждения;
   - семантика сортировки, слияния и вычисления значений не меняется;
     сам `Resolver4.py` не редактируется.
4. Снимок объявления хранится как неизменяемый кортеж значений
   (`first`, `second`, `filename`, `depth`, `insertion_index`), а не как
   ссылка на `Item`: overlay может изменить `Item` после `load()`.
5. `SectionIndex` строится лениво и по секции. Полный дамп — отдельная
   диагностическая операция, а не обычный путь открытия файла.
6. `LtxResolverAdapter.assemble_semantic` — полная модель для карточки и
   запросов. `assemble_resolved` сохраняет кэш `resolve.text`, но текст и
   `line_sources` получает из общей проекции `render_sections` по итоговым
   секциям; второго рендера/источника нет. Проекция проверяется
   паритетным тестом.
7. Семантическая модель кэшируется через `CacheService` в пространстве
   имён `resolve.semantic`, с `snapshot_id` в ключе и только в памяти
   (`ObjectCache`). Дисковый кэш для неё не создаётся.
8. `CoreServices.semantic_query` — `SectionQueryService`; SDK-версия не
   меняется, версия модели — `SEMANTIC_MODEL_VERSION = 1`.
9. `line_sources` — проекция модели (`render_sections`). Редактор и
   панель источников используют её же; паритет «победитель модели ↔
   source строки» проверяется тестом. Отдельного второго источника для
   панели нет. Полная provenance-модель нужна карточке; открытие
   resolved-файла и prebuild используют ту же проекцию без тяжёлого
   snapshot-хранилища.
10. Read-only карточка секции (`ui/section_card.py`) получает только
    прикладной DTO (`app/semantic.py`), а не объекты `core` напрямую.
    Тяжёлая модель и DTO строятся через `SectionCardMixin` в
    `TaskService`; повторный запрос поднимает существующее окно.
    Таблица показывает по 200 свойств с кнопкой «Показать ещё», чтобы
    большая секция не создавала тысячи элементов в UI-потоке. Значения
    в DTO ограничены по длине. Карточка привязана к проекту, snapshot и
    ревизии overlay; при их смене закрывается, а устаревший результат
    задачи не применяется. Карточка не пишет файлы и не меняет документ.

## Альтернативы

1. **Изменить `Resolver4` и писать provenance внутри движка.** Отклонено:
   высокий риск изменить семантику и паритет; план требует не менять
   `Resolver4`.
2. **Повторно разбирать итоговый текст.** Отклонено: дорого по памяти и
   времени, теряет операции `!`, `>`, `<` и файл-победитель.
3. **Хранить модель в дисковом `ResolvedCache`.** Отклонено: модель
   ссылается на объекты движка, её сериализация хрупка и раздувает кэш.
4. **Экспортировать `SectionSnapshot` из `core.__all__`.** Отклонено:
   конфликт с diff-моделью и расширение широкого фасада до Этапа 9.
5. **Сделать UI-карточку сразу.** Отклонено: сначала нужен проверенный
   read-only источник данных и паритетные тесты.

## Последствия

- Появляется объяснимое происхождение значения: файл, секция, глубина,
  мод (если определяется), корень и цепочка.
- Обычный путь `assemble_resolved` сохраняет кэш `resolve.text` и
  получает проекцию из тех же итоговых секций; замер на эталонном VFS:
  ~1.64–1.66 с против ~1.55–1.56 с у прежнего рендера (+5…+6%, в пределах
  10%). Полный семантический проход для карточки — ~1.8 с.
- Первый запрос большой секции (`reduce_lod_texture_list`, 4024 ключа)
  занимает ~0.12 с; малые секции — миллисекунды.
- Модель не хранит полную копию текста в каждой секции; `text` — одна
  строка на `ResolvedRoot`, `line_sources` — проекция. Если
  `resolve.text` уже содержит текст корня, семантический проход
  переиспользует его; если нет — записывает результат в `resolve.text`,
  чтобы редактор не создавал вторую копию.
- `ValueSource.line` пока равен `0`: номер строки появится при ленивом
  синтаксическом дополнении. Это явно отражено в модели.
- Диагностика 4.1: удалённые секции, созданные `@[section]`,
  отсутствующие родители, override несуществующей секции, конфликты
  объявлений. Полный набор диагностик и паритет — 4.3.
- Overlay resolved-правки помечаются слоем `patch` и уверенностью
  `probable`; overlay новых файлов виден через обычные `source_files`.

## Срок и условия выхода

- Действует до завершения Этапа 4; пересматривается при появлении
  provenance в самом `Resolver4` или при переходе к Этапу 5.
- Если модель станет стабильным публичным контрактом, вопрос экспорта в
  `core.__all__` рассматривается отдельно на Этапе 9.
