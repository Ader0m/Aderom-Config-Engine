# ADR-34. Данные модулей, настройки и долги данных

Дата: 24.11.2026
Статус: accepted

## Контекст

После Этапа 6 `project.json` уже содержит `schema_version: 2` и
`module_settings`, но нет `config/modules.json`; `ProjectSetting`
описывает настройки проекта, а не глобальные настройки модуля.
`DATA-4` (смешение моделей проекта и патч-моделей) числится за Этапом
5/9, `needs_confirmation` отмечен как P1, а `config/layout.json` лежит
в рабочем дереве как локальный runtime-файл. Нужно зафиксировать
границы данных до начала Этапа 7, не добавляя новых исключений.

## Решение

### 1. Настройки модулей: только per-project

- Настройка, зарегистрированная через `ProjectSetting`, хранится **только**
  в `project.json.module_settings`.
- Ключ обязан быть namespaced: `<module_id>.<name>` (например,
  `ogg_editor.save_mode`). Регистрация одного ключа двумя владельцами
  запрещена.
- Значение — JSON-скаляр (`str`, `int`, `float`, `bool`); вложенные
  объекты и массивы не входят в Stage 7.
- `ProjectSetting.default` применяется, если ключа нет; отсутствие
  значения не переписывает `project.json`.
- При выгрузке модуля его настройка снимается из реестра, но значение в
  `project.json` **не удаляется**: повторное включение модуля снова
  видит пользовательское значение. Неизвестные ключи сохраняются.
- Схема проекта остаётся `schema_version: 2`; bump и миграция не нужны,
  потому что поле `module_settings` уже существует. Отдельного
  `module_settings_version` нет.
- Глобальных module settings в Stage 7 нет. `config/modules.json` хранит
  только включённость, а не значения настроек. Если модулю понадобится
  глобальная настройка, она оформляется отдельным ADR и отдельным
  версионированным файлом, а не копией значения из проекта.

### 2. `config/modules.json`

Формат версии 1:

```json
{
  "schema_version": 1,
  "modules": {
    "base": {"enabled": true},
    "item_browser": {"enabled": false}
  }
}
```

Правила:

- источник пользовательского намерения `enabled`/`disabled`;
- отсутствующая запись означает `manifest.enabled_by_default`;
- runtime-состояния (`FAILED`, `SKIPPED`, `UNLOADED`, `ACTIVE` и т.п.)
  не сохраняются; они вычисляются загрузчиком (ADR-31);
- запись неизвестного id сохраняется, чтобы намерение пережило временное
  отсутствие модуля;
- запись выполняется атомарно через `write_json_atomic` (временный файл
  + `os.replace`) только при явном enable/disable;
- `schema_version` выше текущего не интерпретируется: применяются
  defaults, пишется диагностика; файл становится **read-only** для
  приложения. Enable/disable блокируется с сообщением, что конфигурация
  создана более новой версией; приложение не пишет v1 поверх future-файла
  и не делает backup-даунгрейд. Пользователь должен разрешить схему
  вручную/обновить приложение;
- повреждённый JSON/схема (не future-версия): диагностика, best-effort
  переименование в `modules.json.broken-<timestamp>`, defaults в памяти.
  Если переименовать нельзя, исходный файл остаётся нетронутым; новый
  файл создаётся только при следующем явном изменении;
- `config/modules.json` не является частью `project.json` и не входит в
  backup проекта.

### 3. `config/layout.json`

`config/layout.json` — локальная раскладка рабочей среды (geometry,
docks, splitter, состояние окон), а не исходник и не данные проекта.
Он игнорируется Git и не коммитится. Это правило распространяется на
будущие локальные `config/*.json`, если они не являются поставляемыми
default-файлами; для них нужен отдельный признак/каталог defaults.

### 4. `DATA-4`: официально на Этап 9

`DATA-4` (смешение моделей проекта и патч-моделей в
`app/projects/models.py`) **не закрывается в Этапе 7** и переносится на
Этап 9. Граница на Этап 7:

- новые модульные контракты в `sdk/features/*` не импортируют
  `app.projects.models`, `core.patching.models`, `PatchPlan`,
  `GeneratedPatch`, `CommitAuthorization` и другие патч-модели;
- `items.catalog`, `item.section.dragdrop`, `section.graph`,
  `project.assets`, `audio.ogg.editor` используют только собственные
  DTO/protocol из `sdk.features.*`;
- `app/features/items` может использовать внутренние app/core-модели, но
  не отдаёт их через SDK;
- существующий `ProjectOverlay` остаётся SDK-входом overlay, а не
  патч-моделью;
- архитектурный тест проверяет отсутствие импортов смешанных моделей в
  новых feature-контрактах.

Разделение моделей проекта и патч-моделей — Этап 9, после модульной
экосистемы. До этого запрещено расширять смешанные модели новыми
модульными полями.

### 5. `needs_confirmation`

P1 `needs_confirmation` считается закрытым:

- `PatchCommitService.authorize` требует, чтобы все risk keys были
  переданы в `confirmed_risks`;
- UI показывает опасные изменения и спрашивает подтверждение, после чего
  передаёт `confirmed_risks` в запись;
- `plan.confirmed=True` выставляется только внутри
  `PatchCommitService.commit` после успешной авторизации, а не в UI и не
  в `app/patching/commit.py`.

Пункт §6.4 в `docs/Обнаруженые проблемы.md` переводится в закрытые.
При разморозке записи патчей на Этапе 8 запрещено возвращать
автоподтверждение.

### 6. 19023/19024 и прочие долги

- 19023/19024 остаются внешним отличием Resolver4 и закрываются только
  на Этапе 8 по игровому дампу. В Этапе 7 они не трогаются.
- `config/layout.json` не коммитится (см. §3).
- Поколенческая очистка кэша, производительность, мёртвый код и дубли
  патч-конвейера остаются Этапом 9 / P2–P3.

## Альтернативы

1. **Хранить настройки модулей глобально в `config/`.**
   Отклонено: настройка сохранения OGG относится к конкретному проекту;
   глобальная копия стала бы вторым источником истины.
2. **Хранить и проектные, и глобальные значения в `module_settings`.**
   Отклонено: неясно, что переживает смену проекта, а что нет.
3. **Поднять `schema_version` проекта только из-за `module_settings`.**
   Отклонено: поле уже есть в v2, миграция не даёт нового формата.
4. **Разделить модели проекта и патча прямо в Этапе 7.**
   Отклонено: это расширяет область Этапа 7 и создаёт риск для
   patch-конвейера; граница зафиксирована, разделение — Этап 9.
5. **Считать `layout.json` исходником и коммитить его.**
   Отклонено: geometry/state зависят от машины и засоряют diff.
6. **При future-схеме `config/modules.json` сделать backup и записать
   v1 после явного изменения.** Отклонено: приложение потеряет
   состояние, созданное более новой версией. Запись блокируется.
7. **Писать изменения future-версии в отдельный sidecar-файл.**
   Отклонено в Этапе 7: это второй источник истины и новая схема; сначала
   нужно решение о совместимости версий конфигурации.

## Последствия

- У модулей один источник проектных настроек — `project.json`.
- Включённость модулей отделена от их настроек и от runtime-состояний.
- Повреждённый `config/modules.json` не теряется и не перезаписывается
  молча; future-версия блокирует запись, чтобы не потерять состояние
  более новой версии.
- `DATA-4` получает явную границу и срок Этап 9; новые контракты не
  могут протащить патч-модели в SDK.
- `needs_confirmation` больше не P1; Этап 8 не должен вернуть
  автоподтверждение.
- `config/layout.json` больше не попадает в Git.

## Срок и условия выхода

Контракт данных действует до `1.0`. `DATA-4` пересматривается на Этапе 9;
19023/19024 — на Этапе 8. Глобальные настройки модулей и plugin-host —
только отдельными ADR.
