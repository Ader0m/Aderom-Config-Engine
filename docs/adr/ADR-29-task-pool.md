# ADR-29. Пул потоков TaskService и приоритеты

Дата: 24.11.2026
Статус: accepted

## Контекст

`TaskService` создавал `QThread` на каждую задачу. Реестр операций,
`TaskHandle`, отмена и зависимости уже работали, но число одновременно
выполняемых задач не ограничивалось, а порядок запуска не учитывал
важность сценария. `QThread.currentThread().isInterruptionRequested()`
привязывал отмену к объекту конкретного `QThread`, что мешает общему пулу.

## Решение

`TaskService` получает пул daemon-потоков:

- `max_workers` (по умолчанию 4) ограничивает параллелизм;
- готовая задача попадает в `PriorityQueue`;
- `run(..., priority=0)` задаёт приоритет: большее значение запускается
  раньше;
- при равенстве приоритетов сохраняется порядок постановки;
- задачи с зависимостями остаются в отдельной очереди `pending` и
  попадают в пул после завершения зависимостей;
- `TaskHandle` больше не владеет `QThread`; отмена — это
  `threading.Event`, а `wait()` ждёт завершения работы;
- `_TaskRelay` (QObject в UI-потоке) доставляет `on_log` и `on_done`
  из рабочего потока в UI-поток;
- `current_task()` возвращает `TaskHandle`, выполняемый в текущем
  рабочем потоке; внутренние сценарии используют его вместо
  `QThread.currentThread().isInterruptionRequested()`;
- `shutdown()` останавливает приём задач, отменяет активные, ждёт
  завершения и гасит потоки пула.

В `sdk.api.TaskApi.run` добавлен `priority: int = 0`. Версия SDK
повышается до `0.10.0`.

## Альтернативы

1. `concurrent.futures.ThreadPoolExecutor`. Отклонено: нет приоритетов и
   общей очереди с зависимостями; пришлось бы строить второй слой
   управления.
2. Пул `QThread` с повторным использованием. Отклонено: флаг
   interruption у `QThread` общий на поток, его нельзя надёжно сбросить
   между задачами.
3. Оставить `QThread` на задачу и только добавить счётчик. Отклонено:
   это не пул, а ограничение числа одновременно созданных потоков.

## Последствия

- Проверка зависимостей, постановка в `pending` и scheduling выполняются
  под одним lock; `_pump_pending` возвращает отложенные задачи в очередь
  до освобождения lock, поэтому завершение зависимости не теряет
  пробуждение.
- `depends_on` может быть callable; он вычисляется под тем же lock при
  постановке задачи, поэтому старт `vfs.rebuild` между UI-проверкой и
  очередью не теряется. `create_project` и `load_project` используют
  общий dependency-провайдер.
- `wait_owner`, `wait_all` и `shutdown` считают один deadline и передают
  каждой задаче/потоку только остаток времени. Общий вызов не может
  растянуться на `timeout × количество задач`.
- `TaskHandle.wait` ждёт финальное состояние и `on_done`, а не только
  завершение рабочего потока. `wait_owner`/`wait_all` используют этот
  контракт; `module_loader.deactivate` не вызывает `wait_owner` из
  UI-потока, а только отменяет задачи владельца.
- `_PumpRelay` доставляет пробуждение зависимых задач в UI-поток даже
  если `OperationRegistry.upsert_external` вызван из рабочего потока.
  `on_done` всегда выполняется в UI-потоке.
- `shutdown` использует отдельный ожидатель рабочего потока и
  синхронно завершает уже готовые задачи до остановки event loop.
- UI и модули не создают собственные потоки; параллелизм ограничен.
- Приоритет виден в `TaskApi.run`, но не является частью снимка
  операции: UI показывает прогресс и состояние.
- Отмена остаётся кооперативной: задача должна проверять
  `TaskHandle.is_cancelled` или `current_task().is_cancelled`.
- Старые вызовы `run` без `priority` работают как раньше.
- `shutdown` может вернуть `False`, если задача игнорирует отмену и не
  завершилась за отведённое время.

## Срок и условия выхода

Контракт действует до `1.0`. После `1.0` изменения — по semver.
