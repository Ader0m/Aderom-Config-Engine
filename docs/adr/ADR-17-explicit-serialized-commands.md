# ADR-17. Явные сериализованные команды как single-writer на Этапе 3

Дата: 23.11.2026
Статус: accepted

## Контекст

`docs/План перехода к целевой архитектуре.md` §6 шаг 2 требует
«single-writer queue»: все мутации проекта — через очередь команд,
чтение — по неизменяемому снимку.

`docs/Целевая архитектура приложения.md` §5.2 формулирует требование
шире: мутации идут через одного писателя **или** сериализуются явной
командой.

Фактическое состояние после шагов 3.1–3.8:

- `ProjectSession.write` — mutex: команда выполняется в вызывающем
  потоке, порядок определяется захватом замка, а не FIFO;
- черновики и overlay сериализуются `DraftStore`/`ProjectService` и
  `OverlayBuilder` под общим `_state_lock`;
- автосохранение имеет epoch и выполняется фоновой задачей;
- UI вызывает методы `ProjectService` (app-слой), а не мутирует
  `project.drafts`/`active` напрямую;
- UI читает `active` для отображения, закрепления фоновой операции и
  stale-проверок по идентичности/id.

Настоящая очередь с отложенным исполнением и futures конфликтует с
синхронным контрактом UI (`update_draft` сразу возвращает
`ProjectDraft`, `save_draft` — `bool`). Очередь с task handles,
прогрессом и отменой — предмет Этапа 6 (`OperationRegistry`,
`TaskService`).

## Решение

1. Для Этапа 3 требование single-writer считается выполненным **явными
   сериализованными командами**:
   - `ProjectSession` — `active`, режимы, настройки модулей;
   - `DraftStore`/`ProjectService` — текстовые, resolved и бинарные
     черновики под `_write_lock` + `_state_lock`;
   - `OverlayBuilder` — overlay под тем же `_state_lock`;
   - `ProjectService._autosave_epoch` — порядок фоновой записи и
     запрет stale-записи.
2. `ProjectSession.write` остаётся mutex, а не очередью. Порядок команд
   определяется захватом замка; FIFO и отложенные результаты не
   обещаются.
3. UI не мутирует структуры проекта в обход `ProjectService`. Вызовы
   его методов считаются явными командами; прямые изменения
   `project.active`, `project.drafts`, `resolved_drafts`, `assets` из UI
   запрещены.
4. UI может читать `active` для отображения, закрепления фоновой
   операции и stale-проверок по идентичности/id. Чтение мутабельного
   состояния для принятия решения о записи не допускается.
5. Очередь команд с futures, прогрессом, отменой и общим реестром
   вводится на Этапе 6. До этого решение действует для синхронного
   слоя.

## Альтернативы

1. **Реализовать очередь немедленно.** Отклонено: синхронный UI
   потребует inline-drain (тот же mutex с накладными расходами), а
   настоящая польза — отложенные результаты, прогресс, отмена и
   приоритеты — появляется только вместе с task handles Этапа 6.
2. **Оставить как есть без ADR.** Отклонено: план и фактическая
   реализация расходятся, критерии Этапа 3 становятся неоднозначными.
3. **Гибрид: use-case-обёртки над сервисом сейчас.** Отклонено: даёт
   вторые имена для тех же действий и не решает вопрос очереди.

## Последствия

- Этап 3 можно закрыть: все структуры имеют одного писателя, stale-
  запись запрещена epoch/identity-проверками.
- Нет FIFO-порядка команд и отложенных результатов; при необходимости
  они появятся на Этапе 6.
- Прямые UI-мутаторы `ProjectService` остаются возможными технически;
  контракт держится ревью и тем, что UI-слой не имеет доступа к
  внутренним структурам без вызова сервиса.
- UI-чтения `active` для отображения/закрепления не считаются
  нарушением; stale-проверки выполняются по идентичности/id.

## Срок и условия выхода

- Действует до Этапа 6.
- На Этапе 6 вводится очередь/реестр операций; ADR пересматривается
  или заменяется.
- Если очередь не появится, решение остаётся постоянным для
  синхронного прикладного слоя; асинхронные сценарии всё равно требуют
  task handle.
