# ADR-25. Контракт операции в `TaskApi`

Дата: 23.11.2026
Статус: accepted

## Контекст

На Этапе 6 платформа получила общий `OperationRegistry` и `TaskService`.
Сценариям модулей нужны стабильный `operation_key`, отображаемое имя и
зависимости: без этого повторный запуск создаёт дубли, а зависимые
функции не могут дождаться построения VFS.

`TaskApi.run` до этого принимал только `fn`, `on_done` и `on_log`.
Платформа могла добавить ключи только для собственных задач, оставив
модульные сценарии вне single-flight и центра операций.

## Решение

`TaskApi.run` расширяется **обратно совместимыми** необязательными
параметрами:

- `operation_key: Optional[str]` — стабильный ключ операции;
- `title: Optional[str]` — имя для центра операций;
- `depends_on` — ключи операций, после завершения которых задача может
  начинаться.

Старое поведение без ключей сохраняется: платформа создаёт уникальный
ключ, поэтому такие задачи не дедуплицируются.

`TaskService.run` возвращает `TaskHandle` с состоянием
`queued/running/done/failed/cancelled`, прогрессом, отменой и ожиданием.
Для модулей контракт остаётся минимальным: они передают ключ и заголовок,
а отмену и состояние показывает платформа. Дополнительно
`TaskApi.operation_active(key)` позволяет проверить, идёт ли операция,
не запуская новую.

Повторный `run` с тем же активным ключом подписывает переданные
`on_done`/`on_log` на существующий handle; каждый принятый запрос получает
свой callback. Это явный контракт, а не потеря уведомления.

Ключи модулей нормализуются по owner: `items.catalog` от `base`
становится `base:items.catalog`. Глобальные ключи (`vfs.*`, `project.*`,
`platform.*`) не префиксуются. `OperationRegistry` уведомляет
`TaskService` о любом переходе в `done/failed/cancelled`, поэтому
зависимые задачи просыпаются и после внешних операций (например,
`vfs.prebuild`). Завершённые зависимости, на которые ещё ссылается
активная задача, не вытесняются из истории.

`depends_on` означает, что тело зависимости и её `on_done` уже
завершились. `TaskService` сначала вызывает `on_done`, затем уведомляет
зависимые задачи. Неизвестный ключ зависимости (никогда не
регистрировавшийся в сессии) — явная ошибка, а не «сразу стартуем».

История известных состояний ограничена 2000 ключами; при вытеснении
`done` удаляются раньше `failed`/`cancelled`, чтобы ошибка зависимости
не превращалась в «неизвестно».

Версия SDK повышается до `0.6.0`. Ломающих изменений нет: новые
параметры необязательны.

## Альтернативы

1. Оставить ключи только для платформенных задач. Отклонено: TASK-7/TASK-9
   требуют single-flight для сценариев модулей.
2. Передавать ключ через отдельный реестр capability. Отклонено:
   это второй способ запуска задач и лишний публичный контракт.
3. Строить ключ по имени функции. Отклонено: нестабильно и не выражает
   цель операции.

## Последствия

- Модульные сценарии могут участвовать в общей очереди и не создавать
  дубли.
- Публичный контракт расширен, но старые вызовы работают без изменений.
- `OperationRegistry` и `TaskHandle` остаются платформенными; модуль не
  получает доступ к внутренностям задач.
- Центр операций показывает модульные и платформенные операции одинаково.

## Срок и условия выхода

Контракт действует до `1.0`. При появлении полноценного пула потоков
сигнатура `TaskApi.run` не меняется; меняется только реализация
`TaskService`. После `1.0` изменения — по политике semver.
