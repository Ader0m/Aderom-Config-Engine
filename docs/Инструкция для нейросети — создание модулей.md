# Инструкция для нейросети: создание модулей

## 1.1. Что такое модуль

Модуль — **гость приложения**, набор возможностей с владельцем. Он не
меняет ядро, не пишет оригиналы, не управляет чужими окнами и не
полагается на порядок загрузки.

Модуль видит только **SDK**. Всё, что не описано в SDK, считается
внутренним и может измениться без предупреждения.

## 1.2. Манифест

Создай `src/modules/<id>/module.json`:

```json
{
  "manifest_version": 1,
  "id": "my_module",
  "name": "My module",
  "version": "0.1.0",
  "description": "Что делает модуль",
  "author": "author",
  "entrypoint": "module:MODULE",
  "sdk": {"min": "0.14.0"},
  "requires": [],
  "optional_requires": [],
  "needs": [],
  "optional_needs": [],
  "provides": [],
  "trust": "trusted",
  "enabled_by_default": true,
  "platforms": ["windows"]
}
```

Правила:

- `id` уникален, совпадает с каталогом и namespace команд/событий/окон.
- `version` — semver модуля.
- `requires` — только обязательный другой модуль; предпочитай
  capabilities через `needs`.
- `needs` — обязательные capabilities; `optional_needs` — необязательные.
- `provides` — capabilities, которые модуль реально предоставляет.
- `trust` не даёт разрешения; доверенные id задаёт платформа.
- `enabled_by_default` определяет первый запуск.
- Неизвестные поля игнорируются с предупреждением; не рассчитывай на них.

## 1.3. Точка входа

```python
# src/modules/my_module/module.py
from sdk import ModuleBase


class MyModule(ModuleBase):
    def init(self, ctx):
        super().init(ctx)
        self._window = None

    def register(self, ctx):
        ctx.commands.register("my_module.show", self.show)
        ctx.ui.register_menu("Модули", "My module", self.show)

    def activate(self, ctx):
        pass

    def deactivate(self, ctx):
        if self._window is not None:
            ctx.ui.close_window("my_module.window")
            self._window = None

    def show(self):
        ...


MODULE = MyModule()
```

`src/modules/my_module/__init__.py`:

```python
from .module import MODULE

__all__ = ["MODULE"]
```

## 1.4. Жизненный цикл и ответственность

- `init` — внутреннее состояние, подписки, чтение своих настроек. Не
  создавай окна и не запускай тяжёлую работу.
- `register` — меню, команды, горячие клавиши, обработчики открытия,
  типы ресурсов, настройки, contributor'ы графа, capabilities. Регистрации
  транзакционны: ошибка откатывает всё.
- `activate` — создание своих окон/вкладок и отложенной работы.
- `deactivate` — закрыть свои окна/вкладки, снять подписки, остановить
  свои задачи.
- `unload` — не оставить регистраций, окон, вкладок, задач и записей в
  `sys.modules`.

Модуль владеет только своими окнами, вкладками, задачами, регистрациями и
настройками. Чужие окна/вкладки закрывать нельзя.

## 1.5. Capabilities

- Провайдер объявляет `provides` в `module.json` и вызывает
  `ctx.capabilities.provide` только в `register`.
- Потребитель использует `ctx.capabilities.require(name, min_version)` для
  обязательной возможности и `ctx.capabilities.optional(name)` — для
  необязательной.
- `optional`-возможность должна иметь рабочий degraded-режим.
- Не заменяй capability, принадлежащую другому модулю.
- Не используй `getattr`/поиск метода по имени вместо capability-контракта.

## 1.6. Что умеет SDK

Модуль получает через `ctx`:

- `ctx.kernel` — базовые сервисы ядра;
- `ctx.events` — события;
- `ctx.commands` — команды;
- `ctx.tasks` — фоновые задачи, отмена, прогресс;
- `ctx.ui` — окна, вкладки, меню, тема, подсказки;
- `ctx.projects` — проектные настройки, asset-типы, чтение ресурсов;
- `ctx.documents` — документы и правки;
- `ctx.patches` — предложение патча (без фиксации);
- `ctx.paths` — идентичность путей;
- `ctx.capabilities` — предоставление/получение возможностей;
- `ctx.module_id` — идентификатор модуля;
- `ctx.items` — доменный feature-API, если он объявлен платформой.

Конкретные имена и уровни API — в `docs/Целевая архитектура модулей.md` и
`sdk.__all__`. Не импортируй внутренние модули `sdk.kernel`/`sdk.ui` в
обход публичного фасада, если контракт доступен через `ctx`.

## 1.7. Данные, проект и патчи

- Настройки модуля — per-project через `ctx.projects`; глобальный
  `config/modules.json` хранит только `enabled`.
- Двоичные ресурсы и новые файлы — через `ProjectAssetType`/`FileReader` и
  проектные документы.
- Не пиши в оригиналы, `Overwrite` и VFS игры.
- Не создавай `PatchPlan`/`GeneratedPatch`/`VerificationResult` вручную.
- Фиксация патча модулю недоступна: используй `ctx.patches.propose` и
  проектный путь; `CommitAuthorization` выдаёт только пользовательский
  commit-сценарий.
- Не открывай файлы напрямую; используй `ctx.documents`/`ctx.ui` и
  контекст открытия.

## 1.8. Тяжёлые операции и потоки

- Только `ctx.tasks`, с `operation_key`, `title`, owner, progress, отменой.
  Имя операции должно быть понятным пользователю; `task-N` запрещён.
- Внутри `fn(log)` сообщай измеримый прогресс:
  `ctx.tasks.progress(done, total, "сообщение")`.
- Не создавай `QThread`/`multiprocessing.Pool`.
- Не блокируй UI; не используй `processEvents`, `sleep`, `wait`.
- Задачи модуля должны быть видны в общем центре операций и отменяться
  при выгрузке.

## 1.9. Чек-лист модуля

- [ ] есть `module.json` с уникальным `id`; class-manifest не используется;
- [ ] импортируются только `sdk`, PyQt и свои зависимости;
- [ ] нет импортов `core`, `app`, `platform`, `ui`, других модулей;
- [ ] нет shim'ов и legacy-алиасов;
- [ ] команды/события/окна namespace'ированы;
- [ ] зависимости — `needs`/`provides`, а не имена модулей;
- [ ] `provide` только в `register` и только из `provides`;
- [ ] optional-возможности имеют degraded-режим;
- [ ] тяжёлая работа — через `ctx.tasks`;
- [ ] окна/вкладки создаются в `activate`/по действию;
- [ ] `deactivate`/`unload` не оставляют окон, вкладок, задач и регистраций;
- [ ] нет записи в оригиналы;
- [ ] изменения идут через `DocumentEditIntent`/`PatchRequest`;
- [ ] ошибка модуля не ломает платформу;
- [ ] README описывает capabilities и настройки;
- [ ] conformance-тесты проходят.

## 1.10. Если нужен новый API

Если модулю не хватает SDK:

1. Не лезь во внутренности `core`/`app`/`ui`.
2. Опиши, какая возможность нужна и почему существующего контракта
   недостаточно.
3. Остановись и предложи ADR: новый протокол, версия, владелец,
   совместимость.
4. После одобрения добавь контракт в `sdk` и реализацию в
   `ui/platform/sdk_bridge`; не добавляй fallback по имени метода.
