2. **«Боевой» режим с генерацией патчей пока лучше не включать**, пока не будет подтверждена не только численная, но и поимённая/источниковая идентичность.

Если коротко:

## Почему одна секция всё ещё важна

Для финального конфига важна не только общая численность секций, а совпадение по:

1. **Именам секций**
2. **Итоговому набору ключей**
3. **Значениям ключей**
4. **Источникам значений**
5. **Порядку применения модификаций**
6. **Корректной обработке `DLTX`-операторов**
7. **Корректному определению файла-победителя**

Если расхождение в одной секции кажется безобидным сейчас, оно может стать критичным позже, например:

- именно в этой секции лежит параметр предмета;
- секция создаётся движком во время загрузки, но не должна попадать в патч;
- секция удаляется через `!![section]`, но учитывается счётчиком до удаления;
- секция пустая, но движок считает её существующей;
- секция появляется из-за runtime-инициализации, а не из `system.ltx`;
- `Resolver4` теряет секцию из-за особенности `@[section]`, `![section]`, `!![section]` или override-only.

Пока причина не выяснена, я не считал бы верификацию полностью закрытой.

## Но пока не стоит включать полноценную генерацию патчей

Под полноценной генерацией патчей я понимаю режим, когда пользователь:

1. меняет значение в карточке предмета;
2. приложение само определяет файл-источник;
3. приложение создаёт `mod_*.ltx`;
4. патч автоматически становится частью VFS;
5. игра видит изменённое значение.

Для этого одного совпадения числа секций недостаточно.

Нужны дополнительные гарантии:

- точно известен файл-источник;
- точно известен корневой файл, к которому относится патч;
- точно известно, какой мод уже переопределил значение;
- корректно обрабатываются списки `>key` / `<key`;
- корректно обрабатываются `!key`, `@[section]`, `![section]`, `!![section]`;
- патч проходит round-trip проверку через тот же `Resolver4`;
- запись не идёт в оригинальные моды или `Overwrite`.

## Главная проблема сейчас: расхождение 19023 против 19024

Перед полноценным боевым режимом нужно локализовать эту одну секцию.

### Рекомендуемый порядок действий

#### 1. Выгрузить список секций из Resolver4

Из `Resolver4` нужно получить не просто количество, а список:

```python
sections = [name for name, sect in resolver.data]
```

Желательно выгрузить в файл, например:

```text
resolver_sections.txt
```

Формат:

```text
section_name<TAB>key_count
```

Пример:

```text
wpn_ak74    87
wpn_lr300   91
device_torch    14
```

---

#### 2. Выгрузить список секций из игры

Проверяющий скрипт `ace_ltx_audit.script` сейчас считает только количество:

```lua
ini:section_count()
```

Для диагностики нужно получить имена секций, если это позволяет Lua API.

Условно:

```lua
local ini = system_ini()
local count = ini:section_count()

for i = 0, count - 1 do
    local ok, name = pcall(function()
        return ini:section(i)
    end)

    if ok and name then
        printf("[ACE] section %d: %s", i, tostring(name))
    end
end
```

Если точное имя метода в вашей версии API другое, нужно использовать соответствующий биндинг, например:

```lua
ini:section_name(i)
```

или аналогичный.

Главное — получить поимённый список из игры.

---

#### 3. Сравнить множества

Нужно сравнить не количество, а именно множества:

```python
only_in_resolver = set(resolver_sections) - set(game_sections)
only_in_game = set(game_sections) - set(resolver_sections)
```

Если найдётся конкретная секция, задача резко упрощается.

## Вероятные причины одной лишней/пропавшей секции

### 1. Секция создаётся движком или скриптами уже после загрузки

Например, какая-то секция появляется во время инициализации игры, но не существует в `system.ltx` как результат статической сборки.

В этом случае `Resolver4` работает правильно, а расхождение нужно задокументировать как допустимое.

---

### 2. Секция пустая

Возможно, движок считает пустую секцию существующей, а `Resolver4` где-то её теряет или не создаёт.

Особые случаи:

```ini
[empty_section]
```

или:

```ini
[empty_section]
; только комментарии
```

---

### 3. Секция помечена на удаление через `!![section]`

Возможно, `Resolver4` уже удалил секцию после применения `!![section]`, а игровой счётчик считает состояние до полного удаления.

Нужно проверить логи:

```text
[DLTX] Found section ... to delete
```

---

### 4. Секция существует только как override

Например:

```ini
![some_section]
key = value
```

Если базовой секции нет, поведение может быть неоднозначным.

В `Resolver4` есть предупреждение:

```text
Attempted to override section '...', which doesn't exist
```

Нужно проверить, не связана ли лишняя секция с таким случаем.

---

### 5. Секция создаётся через `@[section]`

`@[section]` создаёт секцию, если её нет.

В `Resolver4` есть важное исправление:

```text
[FIX-3] Секции @[...] создаются ОДИН раз, ПОСЛЕ загрузки мод-файлов
```

Возможно, одна секция создаётся в движке, но не создаётся в `Resolver4`, или наоборот.

---

### 6. Разница в моменте снятия показаний

Важно, чтобы сравнение происходило в одинаковом состоянии:

- игра уже полностью запустилась;
- все DLTX-моды применены;
- не открыт экран, который может подгружать дополнительные конфиги;
- скрипт выполняется не слишком рано;
- скрипт выполняется не после входа в сохранение, где могут появиться временные секции.

---

### 7. В VFS попал служебный `generated/*.ltx`

Если `Main5` пишет собранные файлы в папку, которая видна игре, игра может подхватить лишний конфиг.

Например, если `generated/` оказался внутри:

```text
gamedata/configs/
```

Тогда игра может видеть больше секций, чем ожидалось.

Нужно убедиться, что:

- `generated/` не находится внутри активного `gamedata/configs`;
- игра не загружает временные ассемблы;
- `Main5` не создаёт побочные `.ltx` в VFS.

## Что нужно доработать перед полноценным боевым UI

### 1. Зафиксировать `Resolver4` как baseline

Текущий `Resolver4` уже представляет собой серьёзную реализацию. Его нужно зафиксировать как базовую версию и не менять без тестов.

Рекомендую считать его:

```text
Resolver4 = read-only engine core
```

Все дальнейшие доработки лучше делать как:

```text
Resolver5
```

или как надстройку над `Resolver4`, чтобы не сломать уже достигнутую точность.

---

### 2. Добавить поимённый дамп секций

В `Main5` нужен пункт диагностики:

```text
Экспорт списка секций Resolver4
```

Он должен выводить:

- имя секции;
- количество ключей;
- список ключей;
- источники значений;
- финальные значения.

Это необходимо для автоматического сравнения с игровым дампом.

---

### 3. Добавить источник значения

Это критично для карточки предмета и генерации патчей.

Сейчас в `Resolver4` у `Item` есть:

```python
item.filename = os.path.splitext(current_file_name[0].lower())[0]
```

Этого недостаточно для полноценного боевого режима.

Проблемы:

- хранится только имя файла без расширения;
- имя приведено к нижнему регистру;
- нет полного относительного пути;
- разные файлы с одинаковым именем могут стать неоднозначными;
- после `load()` вспомогательные карты очищаются.

Для боевого UI нужно хранить дополнительно:

```python
item.source_rel_path
item.root_file
item.depth
item.insertion_index
item.dltx_operation
```

При этом нельзя менять семантику оригинального `filename`, если он используется для совместимости. Лучше добавить отдельные служебные поля.

Пример:

```python
class Item:
    __slots__ = (
        "first",
        "second",
        "filename",
        "depth",
        "insertion_index",
        "source_rel_path",
        "root_rel_path",
    )
```

---

### 4. Научиться определять корневой файл патча

Для DLTX важно не только знать, где лежит ключ, но и к какому корневому файлу применяется патч.

Например, если секция находится где-то внутри дерева:

```text
system.ltx
  -> weapons.ltx
      -> wpn_ak74.ltx
```

Патч обычно должен быть не рядом с `wpn_ak74.ltx`, а в корне загрузки:

```text
mod_system_*.ltx
```

То есть генератор патчей должен понимать:

```text
изменяемая секция -> корневой .ltx -> имя патч-файла
```

`Main5` уже строит include-лес, поэтому эту информацию можно использовать.

---

### 5. Добавить round-trip проверку патча

Перед тем как разрешить боевую генерацию патчей, нужен механизм:

1. Пользователь меняет значение.
2. Приложение генерирует временный патч.
3. `Resolver4` собирает конфиг уже с этим патчем.
4. Приложение проверяет:
   - секция существует;
   - ключ существует;
   - значение равно ожидаемому;
   - не появились дубли;
   - не сломались `> / <` списки;
   - не появились `DLTX_DELETE`-артефакты.

Только после этого патч можно считать безопасным.
