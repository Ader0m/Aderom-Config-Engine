Спецификация программного компонента Main5.py («LTX Explorer»)
Версия документа: 1.0
Компонент: Main5.py — проводник файловой системы LTX-конфигов S.T.A.L.K.E.R. Anomaly
Статус: к реализации / приёмке
Связанные компоненты: Resolver3.py (модуль сборки, не модифицируется), Notepad++ (внешний редактор), VFS Mod Organizer 2
1. Назначение
Main5 — графический инструмент, который:
Строит аналог файловой системы из .ltx-файлов выбранного каталога конфигураций: иерархию, в которой родителем является файл, содержащий директиву #include, а детьми — включённые им файлы.
Отображает эту иерархию в виде дерева в стиле проводника Windows («Этот компьютер» → узел каталога → корни → дети).
Делегирует сборку итогового гига-конфига модулю Resolver3 (точное воспроизведение логики CInifile движка X-Ray Monolith) и открывает собранный результат в Notepad++.
Визуализирует состояние фоновой сборки анимированным индикатором (вращающийся круг) рядом с именем узла.
Main5 не вычисляет итоговые значения конфигов самостоятельно. Источник истины для значений и файлов-победителей — только Resolver3.
2. Термины и сокращения
Термин
Определение
Гига-конфиг
Итоговый объединённый конфиг, собранный резолвером из корневого файла, его #include-дерева и DLTX-модов
Корень (root)
.ltx-файл, не включённый ни в один другой файл через #include (и не ставший чьим-либо ребёнком при раскладке леса)
Include-лес (forest)
Ориентированный лес связей «родитель → ребёнок», построенный по директивам #include
DLTX-мод
Файл mod_<basename>_*.ltx, автоматически подключаемый движком к корневому файлу
Псевдо-ребёнок
DLTX-мод, присоединённый к корню в визуальном лесу (в движке он подключается не через #include, а по имени)
Спиннер
Анимированный круг (12 кадров), отображаемый рядом с именем узла во время фоновой сборки
VFS MO2
Итоговая виртуальная файловая система Mod Organizer 2, видимая игре и инструменту
Resolver3
Python-модуль, побитово воспроизводящий логику CInifile (Xr_ini.cpp) согласно референс-документу

Принципы
P-1. Main5 не модифицирует Resolver3 и не дублирует его логику слияния/приоритетов. Собственный include-сканер Main5 служит только для построения визуальной модели леса.
P-2. Все вызовы tkinter выполняются из главного потока (через root.after). Фоновые задачи — daemon-потоки.
P-3. UI не блокируется ни на одном длительном этапе (сканирование, сборка).
P-4. Детерминизм: все списки файлов, детей и корней сортируются; порядок обхода не зависит от файловой системы.
P-5. Инструмент работает только на чтение исходной VFS; единственная запись — файлы в generated/.
4. Функциональные требования
FR-1. Запуск и выбор каталога
FR-1.1. При старте каталог конфигураций определяется автоматически из констант (DEFAULT_CONFIG_DIR, производные от DEFAULT_GAME_ROOT), если существует.
FR-1.2. Текстовые поля ввода для путей отсутствуют. Выбор каталога — только кнопкой «Выбрать папку с LTX» через диалог.
FR-1.3. Единственное поле ввода в приложении — строка поиска (FR-14).
FR-1.4. Текущий каталог отображается меткой (Label), недоступной для редактирования.
FR-2. Конвейер кнопки «Получить»
Последовательность (в фоновом потоке):
Определение system.ltx: прямые кандидаты (<dir>/system.ltx, <dir>/gamedata/configs/system.ltx, <dir>/configs/system.ltx), иначе рекурсивный поиск.
Определение каталога сканирования: выбранный каталог, если в нём лежит system.ltx; иначе — каталог, содержащий найденный system.ltx.
Сканирование всех .ltx в каталоге сканирования (рекурсивно).
Построение include-леса (FR-3…FR-5).
Заполнение кэша (FR-6), перестроение дерева (FR-7).
Запуск фонового прохода Resolver3 по system.ltx (FR-17) со спиннером на узле system.ltx.
FR-2.1. Повторное нажатие «Получить» полностью перестраивает кэш и дерево.
FR-2.2. На время выполнения кнопка «Получить» блокируется.
FR-3. Построение include-графа
FR-3.1. Для каждого .ltx читается текст: UTF-8 (без BOM), при ошибке декодирования — Windows-1251 с заменой.
FR-3.2. Комментарии (;, //) вне кавычек игнорируются.
FR-3.3. Распознаются директивы #include "путь" (и без кавычек как fallback).
FR-3.4. Путь #include разрешается относительно каталога файла, содержащего директиву.
FR-3.5. Поддерживаются маски * и ? по правилам PatternMatch/file_list движка: * — ноль и более символов, ? — ровно один; сравнение регистронезависимо; рассматриваются только файлы с расширением .ltx.
FR-3.6. Родитель → ребёнок: файл, содержащий #include, является родителем каждого разрешённого файла-цели.
FR-3.7. Цели вне каталога сканирования и несуществующие цели не добавляются в граф; они учитываются в счётчике «пропавших include» и логируются (до 20 примеров).
FR-3.8. Самовключение (#include на самого себя) игнорируется.
FR-4. DLTX-псевдо-дети
FR-4.1. Для каждого предварительного корня (файл без include-родителя) в его каталоге ищутся файлы mod_<stem>_*.ltx.
FR-4.2. Применяется правило неоднозначности из Resolver3: при наличии рядом base.ltx и base_extra.ltx файл mod_base_extra_*.ltx не присоединяется к base.ltx.
FR-4.3. Мод присоединяется как ребёнок корня только если у мода нет include-родителя (include-иерархия приоритетнее визуальной).
FR-4.4. Присоединение носит визуальный характер; фактическую загрузку модов при сборке выполняет Resolver3.
FR-5. Раскладка по деревьям и циклы
FR-5.1. Каждый файл занимает ровно одно место в одном дереве.
FR-5.2. Приоритет раскладки: system.ltx первым, далее корни по относительному пути.
FR-5.3. Файл, достижимый из нескольких корней, принадлежит первому обработавшему его корню.
FR-5.4. Файлы, оставшиеся вне деревьев (циклы include), получают искусственный корень: первый необработанный файл цикла становится корнем. Зависание запрещено.
FR-5.5. Для каждого узла вычисляются: размер поддерева («Файлов в дереве», включая сам узел) и число прямых детей.
FR-6. Кэш
FR-6.1. Кэш хранится в памяти и содержит: каталог сканирования, путь system.ltx, список всех файлов, относительные пути, корни и множество корней, display_children, node_parent, subtree_counts, счётчики дерева system.ltx, число секций резолвера.
FR-6.2. Кэш инвалидируется: смена каталога, повторное «Получить».
FR-6.3. К показу готовятся узлы лениво: корни и их прямые дети — сразу; более глубокие уровни — по факту раскрытия.
FR-6.4. Кэш на диск не сохраняется (вне области действия версии).
FR-7. Отображение дерева (проводник)
FR-7.1. Виртуальные узлы верхнего уровня: «Этот компьютер» (иконка компьютера) и узел каталога сканирования с меткой <имя_каталога> (LTX VFS) (иконка диска). Оба раскрыты по умолчанию.
FR-7.2. Корни леса отображаются детьми узла каталога; их прямые дети вставляются сразу (узел раскрывается стрелкой без дозагрузки).
FR-7.3. Узлы с детьми имеют иконку папки; при раскрытии — открытой папки, при сворачивании — закрытой. Узлы без детей — иконку файла.
FR-7.4. Глубокие уровни загружаются лениво (заглушка до первого раскрытия).
FR-7.5. system.ltx после построения раскрывается автоматически.
FR-7.6. Колонки: #0 Имя (относительный путь), Файлов в дереве, Прямых детей.
FR-7.7. Отображение имён и значений не ограничивается по длине строк и числу строк.
FR-8. Спиннер (анимированный индикатор сборки)
FR-8.1. Во время любой фоновой задачи Resolver3, относящейся к узлу, рядом с именем узла отображается вращающийся круг.
FR-8.2. Прогресс загрузки не отслеживается: индикатор бинарный (есть задача / нет задачи).
FR-8.3. Параметры анимации: 12 кадров, шаг таймера 80 мс; кольцо в правой половине составной иконки 32×16 (левая половина — иконка типа узла, чтобы текст не смещался).
FR-8.4. Поддерживаются параллельные задачи на одном узле: счётчик занятостей; индикатор снимается только после завершения последней задачи.
FR-8.5. По завершении задачи иконка узла возвращается к исходной (папка/файл с учётом текущего состояния раскрытия).
FR-8.6. Задачи, включающие спиннер: первичный проход по system.ltx (FR-17); сборка корня по требованию (FR-10).
FR-9. Активация узла-родителя (сборка и открытие)
FR-9.1. Активация — двойной клик или Enter на узле из множества корней.
FR-9.2. Действия при активации: включить спиннер → в фоновом потоке создать экземпляр LtxResolver(<путь корня>), выполнить load(), сформировать собранный текст (FR-11), записать файл в generated/, открыть его в Notepad++ → выключить спиннер.
FR-9.3. Внутреннее окно предпросмотра содержимого не используется: открытие происходит сразу во внешнем редакторе.
FR-9.4. Поиск Notepad++: PATH (notepad++), затем %PROGRAMFILES%, %PROGRAMFILES(X86)%, %LOCALAPPDATA% + \Notepad++\notepad++.exe. При отсутствии — ошибка с подсказкой; автозамена другим редактором не выполняется.
FR-10. Формат собранного файла
FR-10.1. Имя файла: generated/<каталог>__<имя_без_расширения>__assembled.ltx (не-буквенно-цифровые символы заменяются _).
FR-10.2. Кодировка UTF-8.
FR-10.3. Структура:
ini

12345678
FR-10.4. Источник строки берётся из Item.filename результата Resolver3 и нормализуется к относительному пути через карту источников кэша.
FR-10.5. Многострочные значения сопровождаются комментарием источника со следующей строки.
FR-10.6. Служебные токены DLTX в итоговом выводе не встречаются; при их появлении они сериализуются как <ИМЯ_ТОКЕНА>.
FR-11. Активация узла-ребёнка
FR-11.1. Двойной клик / Enter на узле, не входящем в множество корней, выводит информационное сообщение: «Просмотр детей пока недоступен.»
FR-11.2. Раскрытие детей стрелкой при этом разрешено (структура доступна, содержимое — нет).
FR-12. Сортировка
FR-12.1. Сортируемые колонки: Имя (по умолчанию), Файлов в дереве, Прямых детей.
FR-12.2. Состояние по умолчанию: имя, по возрастанию (А→Я), регистронезависимо.
FR-12.3. Клик по заголовку активной колонки переключает направление; клик по новой колонке сбрасывает направление на «по возрастанию».
FR-12.4. Числовые колонки сортируются по значению, вторичный ключ — имя.
FR-12.5. Направление отображается стрелкой ▲/▼ в заголовке.
FR-12.6. Сортировка применяется к корням и к детям каждого раскрытого узла; состояние раскрытия и выделение по возможности восстанавливаются.
FR-13. Поиск
FR-13.1. Поиск — подстрока, регистронезависимо, по имени файла и по относительному пути.
FR-13.2. Запуск: кнопка «Найти» или Enter в поле поиска.
FR-13.3. Повторный Enter при том же запросе циклически переходит к следующему совпадению; статус показывает Найдено i/N.
FR-13.4. Найденный узел раскрывается до своей позиции: разворачивается вся цепочка родителей (включая виртуальные узлы), узел выделяется и становится видимым.
FR-13.5. Смена запроса сбрасывает индекс совпадений.
FR-13.6. При отсутствии совпадений — информационное сообщение.
FR-14. Диагностика
FR-14.1. Вкладка «Диагностика» — многострочный текстовый виджет только для вывода (ввод запрещён).
FR-14.2. Логируются: пути, число файлов, число include-связей, пропавшие include (примеры), число присоединённых модов, проходы Resolver3, трейсы ошибок.
FR-15. Сохранение и копирование отчёта
FR-15.1. Отчёт содержит: каталог сканирования, путь system.ltx, число секций резолвера, общее число файлов, размер дерева system.ltx, число корней и таблицу корней (путь; файлов в дереве; прямых детей) в текущей сортировке.
FR-15.2. «Сохранить» — запись в файл через диалог; «Копировать» — в буфер обмена.
FR-16. Первичный проход Resolver3 по system.ltx
FR-16.1. После построения дерева запускается фоновый LtxResolver(system.ltx).load().
FR-16.2. Результат (число секций) сохраняется в кэш и попадает в отчёт.
FR-16.3. Ошибка прохода не разрушает дерево: логируется трейс, спиннер снимается.

7. Потоки и синхронизация
WR-1. Сканирование и построение леса — фоновый поток; UI обновляется через root.after.
WR-2. Проход Resolver3 по system.ltx — фоновый поток; спиннер на узле.
WR-3. Сборка корня по требованию — фоновый поток; спиннер на узле; запись файла и запуск Notepad++ из потока допустимы (вне tkinter).
WR-4. Любое изменение виджетов, кэша отображения и спиннера — только из главного потока.
WR-5. Счётчик busy_count[iid] гарантирует корректный снятие индикатора при пересечении задач.

9. Нефункциональные требования
NF-1. UI не блокируется более чем на время реакции виджетов; все долгие операции фоновые.
NF-2. Детерминизм вывода при повторных запусках на той же VFS.
NF-3. Регистронезависимость имён файлов и масок (соответствие FS_FileSet движка).
NF-4. Поддержка кодировок UTF-8 (с BOM и без) и Windows-1251.
NF-5. Исходные файлы модов и Overwrite не изменяются; запись только в generated/.
NF-6. Resolver3.py не модифицируется данным компонентом.
NF-7. Типовой каталог конфигов Anomaly (несколько тысяч .ltx) сканируется и отображается без деградации UI; глубокие уровни не материализуются до раскрытия.

12. Критерии приёмки
№
Проверка
Ожидаемый результат
AT-1
Нажать «Получить»
Дерево: «Этот компьютер» → <каталог> (LTX VFS) → корни; system.ltx раскрыт с прямыми детьми; на system.ltx спиннер до завершения прохода, затем исчезает
AT-2
Сортировка
По умолчанию А→Я по имени; клик по «Файлов в дереве» — числовой порядок; повторный клик — обратный; стрелка в заголовке
AT-3
Раскрыть/свернуть корень
Дети видны; иконка папка открытая/закрытая меняется
AT-4
Двойной клик по корню
Спиннер на время сборки; создан generated/...__assembled.ltx; открыт в Notepad++; каждая строка содержит ; <= источник
AT-5
Двойной клик по ребёнку
Сообщение «Просмотр детей пока недоступен.»
AT-6
Поиск имени ребёнка
Цепочка родителей раскрыта, ребёнок выделен; повторный Enter циклически меняет совпадение; статус i/N
AT-7
«Сохранить» / «Копировать»
Отчёт с корнями и счётчиками записан/скопирован
AT-8
Повторное «Получить»
Кэш и дерево перестроены, спиннер system.ltx снова появляется
AT-9
Каталог с циклом include
Нет зависания; цикл получает искусственный корень
AT-10
Наличие mod_system_*.ltx
Мод отображается ребёнком system.ltx (если не имеет include-родителя)
AT-11
Notepad++ не установлен
Диалог с подсказкой; спиннер корректно снят
AT-12
Две сборки одного узла подряд
Спиннер не мигает между задачами, снимается после последней
