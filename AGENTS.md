# AGENTS.md — правила для AI-агента

Этот документ — **постоянный контракт** для любого AI-агента, который
меняет код ACE. Он не заменяет архитектурные документы, а фиксирует
жёсткие запреты и порядок работы.

Если правило нельзя проверить автоматически, оно всё равно обязательно.
Если правило конфликтует с указанием оператора — остановись и спроси.

---

## 1. Приоритет правил

1. Явное указание оператора.
2. Этот `AGENTS.md`.
3. `docs/Целевая архитектура приложения.md`.
4. `docs/Целевая архитектура модулей.md`.
5. `docs/План перехода к целевой архитектуре.md`.
6. `docs/Текущий режим.md`.
7. `docs/Миграционные исключения.md`.
8. ADR в `docs/adr/`.
9. Существующий код.

**Существующий код — не аргумент.** Если в проекте уже есть нарушение, это
не значит, что его можно повторить. Оно либо в legacy-карантине, либо
должно быть исправлено.

`docs/old/` — архив. Его документы не являются источником правил и не
используются как аргумент.

---

## 2. Обязательное чтение перед правкой

Перед любым изменением прочитай:

- `docs/README.md` — карта актуальных и архивных документов;
- `docs/Текущий режим.md` — текущий этап и что сейчас запрещено;
- `docs/Миграционные исключения.md` — где ещё разрешены старые нарушения;
- целевой документ того слоя, который собираешься менять;
- соответствующий раздел `docs/План перехода к целевой архитектуре.md`.

Если текущий этап не совпадает с тем, что ты собираешься делать — остановись.

---

## 3. Текущий режим

Текущий этап, разрешённые временные отклонения и состояние записи патчей
описаны только в `docs/Текущий режим.md`.

Нельзя:

- считать legacy-код примером;
- расширять список исключений без оператора;
- добавлять «временное» поведение, которого нет в исключениях;
- начинать следующий этап миграции, не закрыв критерии текущего.

---

## 4. Абсолютные запреты

### 4.1. Данные и запись

- **Не писать в оригинальные файлы модов.**
- **Не писать в `Overwrite`.**
- **Не писать в VFS-каталог игры.**
- **Не обходить `PatchWriter`.**
- **Не создавать `CommitAuthorization` вручную и не ставить
  `confirmed=True` без явного подтверждения пользователя.**
- **Не менять оригиналы «для проверки», «временно» или «потом откатим».**
- **Не добавлять второй путь сохранения** (например, прямой `open(..., "w")`
  в модуле или UI).
- **Не удалять и не перезаписывать пользовательские проекты без backup и
  one-time migration.**

### 4.2. Слои и импорты

Запрещены новые импорты:

- `modules/*` → `core`, `app`, `platform`, `ui`, другой модуль;
- `core` → `sdk`, `app`, `platform`, `ui`, `modules`;
- `sdk` → `core`, `app`, `platform`, `ui`, `modules`;
- `app` → `ui`, `platform`, `modules`;
- `ui` → `core` напрямую.

Существующие нарушения `ui → core` перечислены в
`docs/Миграционные исключения.md`. Новые не добавляются.

`ModuleLoader` — единственное место, где платформа динамически импортирует
пакет модуля. Это не статическая зависимость от конкретного модуля.

### 4.3. Публичный контракт

- **Не добавлять новое публичное API без ADR и версии.**
- **Не добавлять shim, legacy-алиас или deprecation-обёртку до `1.0`.**
- **Не оставлять два имени для одного действия.**
- **Не добавлять `getattr(..., "method", None)` вместо явного контракта.**
- **Не добавлять fallback «если метод есть — вызовем».**
- **Не расширять `sdk.__all__` и `core.__all__` без ADR.**

### 4.4. Домен и источники истины

- **Не добавлять доменные понятия предметов, звуков, карточек и т.п. в
  `core` или корень `sdk`.**
- **Не создавать второй источник истины** для текста, проекта, снимка,
  кэша или окна.
- **Не хранить полную копию большого текста в виджете, событии или
  предпросмотре без необходимости.**
- **Не использовать `id()` объекта как идентификатор.**

### 4.5. Кэш и снимок

- **Не создавать новый кэш вне `CacheService`.**
- **Не кэшировать данные без `snapshot_id` и версии правил.**
- **Не возвращать данные, посчитанные для другого снимка.**
- **Не мигрировать `generated/`.** Смена версии — удаление/пересборка.
- **Не делать кэш источником истины.**

### 4.6. Потоки и UI

- **Не выполнять тяжёлую работу в UI-потоке.**
- **Не менять виджеты из фонового потока.**
- **Не вызывать `dispatch` из фонового потока.**
- **Не использовать `sleep`, busy-wait, `processEvents`-циклы и
  `wait()` в UI-потоке для ожидания.**
- **Не блокировать всё приложение модальным ожиданием.**
- **Не создавать собственные `QThread`/`multiprocessing.Pool` в модулях;
  используй задачи платформы.**
- **Не создавать окно/вкладку/задачу без владельца.**
- **Не закрывать чужие окна и вкладки.**

### 4.7. Тесты и качество

- **Не ослаблять тест, чтобы он прошёл.**
- **Не менять `tests/main_unit_test_*` без явного одобрения оператора.**
- **Не удалять архитектурный тест, который мешает.**
- **Не добавлять зависимость без согласования.**
- **Не оставлять «TODO на потом» без ADR и срока.**
- **Не маскировать ошибку широким `except Exception`, если это скрывает
  архитектурную проблему.**

### 4.8. Движок

- **Не менять семантику `Resolver4`, LTX/DLTX, XML/DXML, порядка
  include и приоритетов без отдельного решения и паритетных тестов.**
- **Не подменять правила игры «улучшенной» логикой.**
- **Не считать совпадение количества секций достаточным паритетом.**

## 5. Слои и владение

| Слой | Владеет | Не делает |
|---|---|---|
| `core` | объективными данными, резолвом, графом, патч-движком | UI, проекты, модули, Qt |
| `app` | сценариями, снимком, проектом, черновиками, документами, предпросмотром | виджеты, меню, шины |
| `platform` | шинами, задачами, окнами, вкладками, загрузчиком, реестрами | бизнес-правила движка |
| `ui` | Qt-виджетами и рабочей средой | доменные правила, запись файлов |
| `sdk` | контрактами и моделями для модулей | реализации |
| `modules` | своими сценариями, окнами и возможностями | импорт внутренностей, чужие окна |

Состояние:

- `core` — неизменяемые данные и кэши по снимку;
- `app` — состояние сессии;
- `platform` — runtime-состояние;
- `ui` — состояние представления;
- `modules` — только своё состояние.

## 6. Тяжёлые операции и зависимости

Это обязательное правило для любой новой и изменяемой функциональности.

### 6.1. Что считается тяжёлой операцией

Любая операция, которая:

- может занять заметное время (> ~50 мс);
- читает/пишет файлы;
- запускает резолвер, XML/DXML, DDS, патч;
- строит дерево, каталог, граф, предпросмотр;
- имеет внешний процесс или сеть;
- может зависнуть или быть отменена.

### 6.2. Обязательные свойства

Каждая тяжёлая операция **обязана**:

1. Выполняться вне UI-потока через платформенный task API.
2. Иметь состояние: `queued`, `running`, `done`, `failed`, `cancelled`.
3. Иметь progress (если он измерим) и владельца.
4. Иметь кооперативную отмену.
5. Быть видимой пользователю: статус, панель или центр операций.
6. Не блокировать всё приложение.

### 6.3. Зависимости

Если функция зависит от тяжёлой операции:

- блокируется **только эта функция**, а не всё приложение;
- пользователь видит причину: «идёт построение дерева», «идёт сборка
  каталога», «операция в очереди»;
- после завершения операция сама снимает блокировку или публикует событие;
- ошибка/отмена операции не оставляет интерфейс в вечном ожидании.

Нельзя блокировать проекты, предметы, редактор и другие независимые
функции только потому, что одна операция ещё идёт. Блокировка должна быть
**по зависимости**, а не «по всему приложению».

### 6.4. Загрузочный экран и очередь

- Загрузочный экран/индикатор не должен быть модальным блокировщиком
  всего приложения.
- Допустимы: строка статуса, панель, inline-индикатор, центр операций.
- Очередь операций — платформенная возможность, а не самодельный popup
  модуля.
- Новая операция должна регистрироваться в общем реестре, чтобы будущий
  центр операций мог показать её без изменения модуля.
- Нельзя делать отдельный «загрузочный экран» на каждый модуль.

### 6.5. Запрещено

- `QApplication.processEvents()` в цикле ожидания;
- `time.sleep()` в UI-потоке;
- `thread.wait()` в UI-потоке;
- модальный `QProgressDialog` без отмены на всю рабочую среду;
- «пока идёт сборка, всё приложение недоступно»;
- скрывать очередь операций в логах.

### 6.6. Повторный запуск

У каждой операции есть стабильный `operation_key`.

Ключ включает:

- владельца;
- тип операции;
- цель (путь, корень, секция, патч);
- `snapshot_id`/ревизию проекта, если результат от них зависит.

Если пользователь повторно запускает ту же операцию:

1. Новая операция **не создаётся**.
2. UI показывает состояние «операция уже запущена».
3. Существующая операция поднимается/фокусируется в центре операций.
4. Возвращается существующий handle/результат, если это возможно.
5. Для очереди повторный запрос **объединяется** с существующим, а не
   добавляет вторую копию.

Если операция уже завершилась, повторный запуск создаёт новую — это
нормально. Если пользователь хочет перезапуск во время выполнения, нужен
явный `cancel`/`replace`, а не скрытое дублирование.

Правило:

> Одинаковый `operation_key` + активная операция = один экземпляр работы,
> одно состояние в UI и сообщение «уже запущено».

Логи недостаточно: пользователь должен видеть это в интерфейсе, а не
только в диагностике.

## 7. Правила изменения

Перед правкой:

1. Определи слой и владельца.
2. Проверь текущий этап и исключения.
3. Сформулируй план на 3–5 пунктов.
4. Проверь, не требует ли изменение нового публичного API, зависимости,
   миграции данных или записи.
5. Если требует — остановись и спроси оператора.

Во время правки:

- делай минимальное изменение;
- не переформатируй чужие файлы без необходимости;
- не смешивай рефакторинг и новую функциональность;
- не добавляй «временный» код без записи в исключения и срока удаления;
- не копируй старые нарушения.

После правки:

- добавь/обнови тест;
- прогони проверки;
- обнови документацию/ADR;
- удали временные адаптеры, если этап закрыт.

---

## 8. Стоп-условия

Остановись и задай вопрос оператору, если нужно:

- изменить публичный контракт;
- изменить `tests/main_unit_test_*`;
- ослабить или удалить тест;
- добавить зависимость;
- изменить `Resolver4` или семантику игры;
- изменить схему проекта или формат данных;
- обойти `PatchWriter`/`CommitAuthorization`;
- добавить новое исключение в legacy-карантин;
- нарушить инвариант из целевой архитектуры;
- выбрать между двумя противоречащими документами;
- объяснить падение производительности больше чем на 10%;
- сделать «быстрое решение», которое явно противоречит правилам.

Формат остановки:

```text
STOP: <причина>
Что мешает:
Варианты:
1. ...
2. ...
Рекомендация:
Что нужно от оператора:
```

## 9. Definition of Done

Изменение не готово, пока не выполнено:

- [ ] `python -m pytest -q`;
- [ ] `python -m compileall -q src`;
- [ ] `git diff --check`;
- [ ] архитектурные тесты зелёные;
- [ ] нет новых нарушений матрицы импортов;
- [ ] нет новых shim/legacy-алиасов;
- [ ] нет новых ручных `PatchPlan` вне patch engine;
- [ ] нет новых записей в оригиналы;
- [ ] нет новых синхронных тяжёлых операций в UI-потоке;
- [ ] повторный запуск операции не создаёт дубль;
- [ ] нет новых окон/вкладок без owner;
- [ ] тесты не ослаблены;
- [ ] `tests/main_unit_test_*` не изменены без одобрения;
- [ ] документация/ADR обновлены;
- [ ] исключения не расширены без оператора.

## 10. Legacy-карантин

Файлы и паттерны, где старые нарушения ещё существуют, перечислены в
`docs/Миграционные исключения.md`.

Правила:

1. Исключение действует только для указанного пути/паттерна.
2. Исключение имеет этап, на котором оно должно исчезнуть.
3. Нельзя расширять исключение на новые файлы.
4. Нельзя копировать паттерн из исключения в новый код.
5. Если ты меняешь файл из карантина — не добавляй новых нарушений;
   по возможности уменьшай.
6. Если нарушения нет в списке — считай его запрещённым.
7. Новое исключение добавляет только оператор.

---

## 11. Саморевью перед завершением

Ответь себе:

- не добавил ли я «временный» обход?
- не скопировал ли я старый плохой паттерн?
- не добавил ли я второй источник истины?
- не добавил ли я новый кэш без снимка?
- не добавил ли я новый shim?
- не блокирует ли моя операция UI?
- не сломает ли моя операция зависимые функции?
- не ослабил ли я тест?
- не добавил ли я домен в `core`/SDK?
- не нарушил ли я владельца окна/вкладки/задачи?
- обновил ли я документацию?

Если хотя бы один ответ «да» или «не уверен» — остановись.

---

## 12. Изменение самих правил

- Правила не ослабляются без оператора.
- Любое исключение оформляется ADR и записью в
  `docs/Миграционные исключения.md`.
- После закрытия этапа исключения удаляются.
- После `1.0` добавляется политика deprecation и semver, но базовые
  запреты не переписываются.
