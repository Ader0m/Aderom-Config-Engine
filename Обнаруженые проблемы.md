# Анализ архитектуры ACE

Проверил композиционный корень, `core`, `ui`, `sdk`, загрузчик модулей, `base_module`, `ogg_editor`, шины событий/команд, проектное хранилище, патч-конвейер и кэши. Ничего не исправлял.

Все 483 теста проходят (1 skipped — symlink), но архитектурные проблемы они почти не ловят: `test_architecture.py` проверяет только импорты верхнего уровня.

---

## 1. Критические проблемы

### 1.1. Resolved-черновик проекта хранится в чудовищно избыточном виде

Файл `ui/project.py` (`_write_resolved_draft`, `_serialize_line_sources`, `_deserialize_line_sources`) сохраняет:

- `original_text`, `current_text`, `saved_text` — три полные копии текста;
- `line_sources` — отдельный JSON-объект на **каждую строку**, без дедупликации.

В текущем каталоге `projects` один реальный resolved-черновик занимает:

```text
404 293 233 байта (~386 МБ)
line_sources: 1 264 411 записей
original/current/saved: ~40,6 млн символов каждый
```

Это прямо противоречит идее из `docs/modules_architecture.md` о том, что одинаковые `LineSource` должны разделяться одним объектом. При загрузке `_deserialize_line_sources` создаёт 1,26 млн объектов `LineSource` вместо ~1000 уникальных. `ProjectService.load()` читает весь JSON в память, а автосохранение раз в минуту (`MainWindow._autosave_timer`) перезаписывает его целиком.

**Последствия:** зависания UI при загрузке/автосохранении, гигантский расход RAM и диска, риск потери данных при прерывании записи.

### 1.2. Предсборка кладёт в кэш результат под чужим ключом

В `core/resolver/prebuild.py`:

- ключ кэша считается через `ResolverService.resolved_key(..., overlay=overlay)`, где `overlay` — полный `ProjectOverlay` с `source_files` **и** `resolved_edits`;
- в параллельном режиме воркеру передаётся только `dict(overlay.source_files)`:

```python
overlay_files = getattr(overlay, "source_files", None)
...
initargs=(..., dict(overlay_files)),
```

- `LtxResolverAdapter` применяет `resolved_edits` только через `_apply_resolved_overrides`, а в воркере их нет.

То есть значение сохраняется под ключом «с учётом resolved-правок», но собрано **без** этих правок.

Дополнительно `base_module/clean_run.py` при старте предсборки создаёт `ProjectOverlay` только с `source_files`, теряя `resolved_edits`.

**Последствия:** после правки resolved-документа предсборка может вернуть устаревший текст; поведение зависит от числа CPU/успешности spawn-пула (в sequential-режиме правки применяются, в parallel — нет). Это одна из самых опасных ошибок: кэш формально валиден, но содержит неверные данные.

### 1.3. Два владельца состояния resolved-документа

`ui/documents.py` объявляет `ResolvedDocument` «единственным владельцем текста, line_sources, ревизии и dirty». Фактически состояние дублируется:

- `ResolvedDocument` хранит `_text`, `_line_sources`, `_saved_text`, `_original_text`, undo/redo;
- `ResolvedView` в `ui/editor.py` хранит собственные `_line_sources`, `_baseline_text`, `_dirty` и undo/redo Scintilla;
- `ItemViewerFeature` хранит ещё одну копию: `_resolved_text`, `_original_text`, `_line_sources`, `_saved_text`;
- `ProjectResolvedDraft` в `ui/project.py` хранит `original_text`, `current_text`, `saved_text`, `line_sources`.

`ResolvedView._on_text_changed` одновременно:

- эмитит `content_changed`;
- вызывает `document.replace_text(...)`;
- сам пересчитывает dirty по `_baseline_text`.

При этом для XML-resolved вкладок `open_xml_resolved_tab` вообще не создаёт `ResolvedDocument`: используется «голый» `ResolvedView`, а изменения пишутся в проект через `on_resolved_changed`. То есть LTX-resolved и XML-resolved живут по двум разным моделям жизненного цикла.

**Последствия:** рассинхронизация `line_sources`, dirty-флагов, undo/redo и проектного черновика; баги проявляются только на больших файлах и после нескольких правок.

### 1.4. Жизненный цикл модулей небезопасен

`ui/module_loader.py`:

- если `init(ctx)` прошёл, а `register(ctx)` бросил исключение, модуль **не добавляется** в `self.loaded`, поэтому `deactivate` для него никогда не вызовется. Все подписки, команды, меню и обработчики, созданные в `init`/части `register`, остаются жить;
- зависимости проверяются только по уже загруженным именам:

```python
loaded_names = { ... self.loaded ... }
missing = [d for d in manifest.requires if d not in loaded_names]
```

Нет топологической сортировки и обнаружения циклов. Если модуль `a` требует `z`, а сортировка поставила `a` раньше `z`, модуль `a` будет молча пропущен. Принудительно первым загружается только `base_module`;
- нет проверки версий зависимостей, опциональных/мягких зависимостей и обратных зависимостей;
- нет выгрузки/перезагрузки модулей.

### 1.5. `PlatformApi` и `ProjectService` — God-object’ы, в которых смешаны слои

`ui/platform_api.py` (~2160 строк) одновременно отвечает за:

- регистрацию меню/шорткатов/действий/обработчиков;
- маршрутизацию открытия файлов;
- создание/загрузку/удаление проекта;
- сохранение и автосохранение;
- жизненный цикл resolved-документов;
- показ модульных окон и вкладок;
- диалоги;
- переключение темы Override;
- логирование, статусы, отложенную навигацию;
- публикацию событий.

`ui/project.py` (~2290 строк) содержит не только хранение черновиков, но и:

- планирование патчей;
- генерацию патчей;
- ручную сборку XML-патчей;
- построение asset/new-file патчей;
- кэш предпросмотра;
- бизнес-правила режимов Root/On-file/Override.

Это уже не «UI-слой», а прикладной/доменный сервис, живущий внутри `ui`. При этом `ui/project.py` импортирует внутренности ядра напрямую:

```python
from core.patching.ltx.merge import merge_patch_plans
from core.patching.models import ...
from core.patching.ltx.multiline import analyze_multiline_edit
from core.tools.fs import read_text_safe, read_xml_text
from core.models import LineSource
```

Публичная поверхность `core` по документации — `core/__init__.py`, `core/facade.py`, `core/models.py`; здесь она обходится.

## 2. Высокие проблемы

### 2.1. Платформа знает команды базового модуля

В `ui/editor_tabs.py` контекстное меню вкладок жёстко зашивает имена команд:

```python
"base.open_raw"
"base.assemble_open"
"base.open_xml_resolved_notepad"
"base.open_notepad"
```

`ui` не должен знать, что существует модуль `base` и какие у него команды. Это нарушает независимость модулей: переименование команды или отсутствие `base` ломает платформенное меню.

### 2.2. SDK-адаптер лезет во внутренности UI-виджета

`UiApiAdapter.sort_file_tree_by_files_desc`:

```python
window = getattr(self._platform, "window", None)
tree = getattr(window, "file_tree", None)
fn = getattr(tree, "sort_by_files_desc", None)
```

Это прямой обход SDK-контракта: адаптер зависит от `MainWindow.file_tree` и его метода. Если виджет переименуют или заменят, модуль `base` перестанет работать без ошибки.

### 2.3. `FileOpenHandler` получает сырой `PlatformApi`

Контракт:

```python
def open(self, path, api):
```

В `FileOpenRouter.open` передаётся именно `PlatformApi`:

```python
h.open(p, api)
```

Модуль-обработчик формально получает доступ к `.services`, `.commands`, `.window`, диалогам и т.д. Это обход `ctx` и декларируемой изоляции модулей. Сейчас `base_module` этот `api` игнорирует, но контракт провоцирует нарушение.

### 2.4. `UiApiAdapter.item_entry` возвращает не SDK-модель

`CoreApiAdapter.build_item_entry` аккуратно конвертирует `ItemRecord` → `sdk.ItemEntry`. А `UiApiAdapter.item_entry` просто делегирует:

```python
return self._platform.item_entry(tab_id, section)
```

`PlatformApi.item_entry` возвращает результат `CoreServices.build_item_entry...`, то есть **core-модель** `ItemRecord`, а не `sdk.ItemEntry`. Модуль получает объект ядра через `ctx.ui`, хотя соседний API через `ctx.services` возвращает SDK-модель. Это скрытая утечка типа и потенциальная поломка при изменении core-модели.

### 2.5. `SavedDraft` — payload события, которого нет в SDK

`sdk/events.py` документирует:

```python
# payload — SavedDraft
PROJECT_SAVED = "project_saved"
```

Но `SavedDraft` определён только в `ui/project.py` и не экспортируется из SDK. Модули вынуждены работать через `getattr(event, "kind", "")`, как это делает `ogg_editor`. Контракт события фактически не типизирован.

### 2.6. Запросы передаются через `publish`, хотя это не факты

`Events.ITEM_CARD_REQUESTED` — это запрос на открытие карточки, но `PlatformApi` публикует его через `self.events.publish(...)`, а `base_module` подписывается и выполняет действие. Это смешивает роли шин, которые сами же описаны в документации:

- событие — факт;
- команда — намерение;
- dispatch — перехватываемое UI-действие.

То же относится к зарезервированным `UI_WINDOW_REQUESTED`, `UI_TAB_REQUESTED`, `UI_FILE_OPEN_REQUESTED`: они объявлены, но платформа их не публикует. Стандартного механизма «модуль A просит модуль B открыть окно/вкладку» фактически нет.

### 2.7. `EventBus.dispatch` не маршалит вызов в UI-поток

`publish` умеет доставлять подписчикам через очередь главного потока. `dispatch` — нет:

```python
def dispatch(self, name, payload=None):
    for entry in self._snapshot(name):
        if self._call(entry, name, payload):
            return True
```

Если модуль вызовет `dispatch` из `ctx.tasks.run(...)` (а он может, потому что это обычный Python-метод), обработчики UI-действий выполнятся в фоновом потоке. Контракт «dispatch только из UI-потока» нигде не проверяется.

### 2.8. `CommandBus` не имеет владельца, блокировок и защиты от перехвата

- `CommandBus.register` при дубликате только пишет warning и **перезаписывает** обработчик;
- нет проверки namespace;
- `unregister` может удалить чужую команду;
- нет блокировки, в отличие от `EventBus`;
- модуль может зарегистрировать `ui.open_file` или `base.open_raw` и перехватить платформенную/чужую команду.

Это делает команды небезопасным каналом взаимодействия между независимыми модулями.

### 2.9. Регистрации модулей не имеют отписки

`ctx.ui.register_menu`, `register_tree_context_action`, `register_shortcut`, `register_mouse_binding`, `register_open_handler` не возвращают подписку и не имеют unregister-API. При `deactivate` модуль не может снять:

- пункт меню;
- действие дерева;
- горячую клавишу;
- мышиную привязку;
- обработчик открытия файлов.

`ogg_editor.deactivate` снимает asset type, setting, file reader, section contributor и подписки на события, но `SoundOpenHandler` остаётся в `FileOpenRouter`. После выгрузки модуля маршрутизатор может выполнить `api.commands.execute("ogg_editor.open", path)` для уже удалённой команды. Это прямо противоречит идее независимой выгрузки модулей.

### 2.10. `FileOpenRouter` игнорирует результат обработчика

```python
if h.can_open(p):
    h.open(p, api)
    return True
```

Если `h.open` вернул `False` (например, `LtxFileOpener.open` при отсутствии дерева), маршрутизатор всё равно сообщает «открыто». `PlatformApi.request_open_file` не покажет ошибку отсутствия обработчика, а отложенная навигация может остаться в `_pending_file_actions`.

### 2.11. Навигация применяется к текущей вкладке, а не к открытому файлу

`PlatformApi._on_file_opened`:

```python
pending = self._pending_file_actions.pop(_path_key(path), None)
...
widget = self.window.editor.currentWidget()
```

Событие несёт только путь, но не `tab_id`/виджет. Если асинхронный резолв завершился, когда пользователь уже переключился на другую вкладку, переход к строке/поиск может примениться не к тому файлу.

### 2.12. Лес (`forest`) и каталог конфигов имеют нескольких владельцев

Одновременно существуют:

- `ModuleSession.forest` в `base_module`;
- `PlatformApi._forest`;
- `MainWindow.file_tree.forest`;
- `OggEditorModule._forest`;
- `_virtual_paths` в `PlatformApi`;
- снимки `forest` в проектных черновиках и кэшах.

Плюс лес мутируется из нескольких мест:

- `TreeBuilder.add_virtual_file` / `remove_virtual_file`;
- `PlatformApi._restore_project_virtual_files`;
- `BaseModule.ItemViewerFeature._register_virtual_files`;
- `core/patching/targets.py` вешает на лес скрытые атрибуты `_ace_patch_target_index`, `_ace_xml_patch_target_index`;
- `core/tools/cache.invalidate_forest_signatures` вешает `_resolved_signature_memo`.

Это не «read-only объект ядра», как обещает документация, а разделяемое изменяемое состояние без единого владельца и без синхронизации.

### 2.13. Переключение проекта не очищает старые resolved-документы

`PlatformApi._on_project_changed` очищает `_resolved_documents` только если payload `None`. При загрузке/создании нового проекта публикуется `PROJECT_CHANGED` с объектом проекта, и старые документы остаются в реестре. `ProjectService.load/create` вызывает `close()`, но события об этом нет.

**Последствия:** после смены проекта открытые resolved-вкладки могут продолжать показывать/писать данные старого проекта, пока их не закроют вручную.

### 2.14. Дублирование патч-конвейера

`ProjectService._build_preview_per_file` вручную реализует выбор режима и вызовы:

- `services.plan_ltx_override`;
- `services.plan_xml_fork`;
- `services.patch.plan_xml_resolved_edit`;
- `services.patch.plan_xml_document_change`;
- `services.patch.plan_multiline_edit`;
- `services.patch.plan_document_change`;
- `services.generate_patch`.

При этом в `core` уже есть единые входы:

- `core/patching/ltx/service.py::LtxPatchService.plan`;
- `core/patching/xml/service.py::XmlPatchService.plan`;
- `CoreServices.plan_ltx_patch` / `plan_xml_patch`.

UI использует старые/внутренние пути и дублирует диспетчеризацию режимов. Любое изменение правил патчинга нужно вносить в двух местах.

Дополнительно `_asset_preview_item` и `_new_file_preview` вручную собирают `PatchPlan`, `GeneratedPatch`, `VerificationResult`, обходя общий конвейер.

### 2.15. UI импортирует внутренности core

Кроме `ui/project.py`, это есть в:

- `ui/platform_api.py` — `from core.tools.fs import read_text_safe, read_xml_text`;
- `ui/documents.py` — ленивый `from core.patching.ltx.document import parse_ltx_document`;
- `ui/editor.py` — собственная `_read_text` с повторением логики кодировок `core.tools.fs.read_text_safe/read_xml_text`.

Это нарушает заявленную границу «публичная поверхность core — `core/__init__.py`, `facade.py`, `models.py`».

## 3. Дублирование логики

### 3.1. Три реализации разбора LTX

1. `core/patching/ltx/document.py` — полноценная модель: `!![section]`, `![section]`, `@[section]`, `!key`, `>key`, `<key`, кавычки, многострочные значения, комментарии.
2. `ui/documents.py` — собственные `_HEADER_RE`, `field_key`, `fit_sources`, `SectionSpan`, `_build_spans`; при этом `field_line` отдельно вызывает core-парсер.
3. `modules/base_module/item_viewer.py` — собственные `_ltx_header_name`, `_ltx_section_at_line`, `_ltx_key_from_line`, `_ltx_section_bounds`, `_edit_section_text`, `_declared_sections`.

Все три по-разному обрабатывают DLTX-префиксы, кавычки, комментарии и многострочные значения. Это не только дублирование, но и риск, что карточка предмета изменит файл не так, как его понимает резолвер/ядро.

### 3.2. Две системы редактирования resolved-файлов

- LTX-resolved: `ResolvedDocument` + `ResolvedView.bind_document`.
- XML-resolved: `ResolvedView` без документа + `PlatformApi.on_resolved_changed`.

У них разные источники `baseline`, dirty, undo, сохранения и восстановления. Это уже описано в 1.3, но важно как отдельный архитектурный дубль.

### 3.3. Две системы обновления VFS

- платформенная `PlatformApi._restore_project_virtual_files`;
- модульная `ItemViewerFeature._register_virtual_files`.

Обе вызывают `add_virtual_file`/`remove_virtual_file` и публикуют `TREE_READY`. Нет единого сервиса «обновить VFS проекта».

### 3.4. Дублирование пути «открыть сырой файл»

- `LtxFileOpener.open_raw` — своя шапка, свой вызов `show_text`;
- `XmlFileOpener.open` — свой вызов `ctx.ui.open_raw`;
- `PlatformApi.open_raw` — общий маршрут;
- `FileOpenRouter.open_default` — ещё один маршрут.

Аналогично `ProjectService._asset_relative_path` повторяет логику `CoreServices.forest_game_root`, а `CoreApiAdapter.game_root` — ещё одну её копию.

### 3.5. Дублирование path-key логики

`normcase(abspath(...))` реализован минимум в:

- `core/tools/cache.py::path_key`;
- `ui/project.py::ProjectService.path_key`;
- `ui/platform_api.py::_path_key`;
- `modules/base_module/item_viewer.py::_same_path`;
- `modules/base_module/section_graph.py::_path_key`;
- `modules/ogg_editor/section_links.py::_path_key`;
- `modules/ogg_editor/explorer.py::_path_key`;
- `modules/ogg_editor/module.py`, `editor_tab.py`, `sections.py`.

Разные варианты (`fspath` vs `str`, `normpath` vs без) создают риск, что один и тот же файл в разных местах считается разным.

### 3.6. Дублирование чтения текста/кодировок

`core.tools.fs.read_text_safe` / `read_xml_text` повторяются в:

- `ui/editor.py::CodeEditor._read_text`;
- `ui/platform_api.py::document_text`;
- `ui/project.py::update_draft`.

При этом правила кодировок уже зафиксированы в core.

### 3.7. Дублирование статуса проекта и меню

`MainWindow._update_project_menu` самостоятельно считает `changed_drafts/changed_resolved_drafts/changed_asset_drafts`, а `PlatformApi._update_project_status` вызывает приватный `window._update_project_menu` и тоже пересчитывает состояние. Логика «есть ли изменения» размазана между окном и платформенным API.

### 3.8. Дублирование темы

Тема объявлена единственным источником цветов, но:

- `ui/file_tree.py` — `HL_COLOR = "#4f4f00"`;
- `ui/prebuild_panel.py` — `GREEN = "#2E7D32"`;
- `ui/project_dialogs.py` — `"#F14C4C"`, `"#FFFFFF"`;
- `modules/ogg_editor/sound_types_ui.py` — собственная fallback-палитра `#1E1F22`, `#2E3033` и т.д., отличающаяся от `Palette`;
- `modules/ogg_editor/multi_edit.py` — свои цвета;
- `modules/ogg_editor/editor_tab.py` — `"color: #F14C4C"`.

Кроме того, `editor_tab.py` запрашивает `theme_color("accent_green", "#3FA34D")`, но в `Palette` есть только `accent_teal`. Токен всегда отсутствует, и модуль всегда использует жёстко зашитый fallback.

## 4. SDK: конкретные несоответствия контракту

### 4.1. SDK смешивает платформенные и доменные интерфейсы

`CoreApi` содержит предметы, иконки, DDS, каталог:

```python
item_catalog_root
build_item_catalog
build_item_entry
read_texture_region
load_item_icons
```

`UiApi` содержит редактирование resolved-документов и карточки предметов:

```python
item_entry
open_item_card_at_cursor
apply_resolved_field_edit
rename_resolved_field
retain_resolved_document
...
```

`sdk.__init__` экспортирует `ItemCatalog`, `ItemEntry`, `ItemIcon`, `ItemSection`, `ItemCardRequest`, `ResolvedDocumentChange` и т.п.

Это делает SDK «божественным» интерфейсом и заставляет любой модуль зависеть от доменных понятий базового модуля/ядра, даже если ему нужен только логгер или меню. Для независимых модулей лучше разделять:

- платформенный SDK;
- публичный API базового модуля/предметов;
- публичный API OGG-модуля.

Сейчас граница размыта.

### 4.2. `CoreApiAdapter` хранит реестр contributor’ов в `CoreServices`

```python
registry = getattr(owner, "_sdk_section_graph_contributors", None)
if registry is None:
    registry = []
    setattr(owner, "_sdk_section_graph_contributors", registry)
```

Это скрытое состояние, приклеенное к фасаду ядра. Реестр принадлежит платформе/загрузчику модулей, а не `CoreServices`; при пересоздании фасада или в тестах поведение зависит от того, удалось ли сделать `setattr`.

### 4.3. `CoreApiAdapter.patch_target` реализован отдельно от ядра

```python
parents = forest.include_parents.get(path) or ()
return sorted(parents, ...)[0]
```

Это не использует провайдера/core-сервис и не учитывает DLTX-привязки/выбор корня. Поведение SDK-метода может отличаться от логики ядра.

### 4.4. Adapter’ы полны fallback-ов на разные имена

`run_resolver`, `assemble_text`, `open_external_editor`, `open_with_shell` ищут методы по нескольким именам (`open_notepad`, `open_in_notepad`, `open_shell`, `open_path`). Это признак того, что контракт SDK и реальные сервисы разъехались; ошибки маскируются, а не проявляются явно.

### 4.5. `ctx.paths` — сырой `SimpleNamespace`

`main.py` передаёт:

```python
paths = SimpleNamespace(app_dir=..., generated_dir=..., projects_dir=...)
```

`ModuleContext` раздаёт этот объект всем модулям без типа и защиты. Любой модуль может изменить `ctx.paths.generated_dir` или `projects_dir`, повлияв на другие модули и ядро.

### 4.6. `SectionGraphRequest` отдаёт модулям сырой лес и overlay

```python
forest: object
overlay: object
```

Модуль получает изменяемый `LtxForest` и `ProjectOverlay` без SDK-обёртки. Документация говорит «read-only», но это ничем не обеспечено. `ogg_editor` уже активно использует `forest` и `overlay`; любой модуль может начать мутировать их.

### 4.7. `ProjectOverlay` — изменяемый frozen-объект

`@dataclass(frozen=True)` защищает только поля, но `source_files` и `resolved_edits` — обычные словари. `revision` считается каждый раз и **не включает `new_files`**. Если модуль изменит overlay после вычисления ключа кэша, ключ и данные разойдутся.

### 4.8. `sdk.events` содержит нереализованные запросы

`UI_WINDOW_REQUESTED`, `UI_TAB_REQUESTED`, `UI_FILE_OPEN_REQUESTED` объявлены, но нигде не публикуются. Это мёртвые точки расширения; модули не могут рассчитывать на стандартный межмодульный запрос окна/вкладки.

### 4.9. Имена событий не соответствуют заявленному namespace

Документация: платформа — `ui.`, базовый модуль — `base.`, остальные — свой префикс.

Фактически:

- `TREE_READY`, `FILE_OPENED`, `FILE_OPEN_FAILED`;
- `CLEAN_RUN_STARTED`, `CLEAN_RUN_FINISHED`;
- `PROJECT_SAVED`, `PROJECT_CHANGED`, `PROJECT_SETTINGS_CHANGED`;
- `ITEM_CARD_REQUESTED = "item.card.requested"`;
- `RESOLVED_DOCUMENT_CHANGED = "resolved.document.changed"`.

При этом `TREE_READY` публикует и `base_module`, и `PlatformApi`; `FILE_OPEN_FAILED` публикуют модули. Владелец события неочевиден.

## 5. Модули: независимость и взаимодействие

### 5.1. Хорошее

- Модули действительно не импортируют `core` и `ui`; тест это подтверждает.
- `ogg_editor` объявляет `requires=("base",)` и использует SDK для drag-and-drop, asset type, settings, file reader, section graph contributor.
- `base_module` не импортирует внутренности UI, только SDK.
- Модули общаются через `ctx.events`/`ctx.commands`, а не через прямые ссылки.

### 5.2. Плохое

- `requires` — это только проверка «уже загружен», без топологической сортировки и версий. Для настоящих зависимостей этого мало.
- Нет понятия optional dependency/capability. Если модуль хочет «использовать OGG, если он есть», это нужно делать вручную через `commands.has`/`events.has`.
- Платформа знает `base.*` команды (см. 2.1) и доменные `ItemCardRequest`/resolved API (см. 1.5/4.1), поэтому «независимость» модулей держится на том, что `base` обязателен и его API зашит в платформу.
- Нет автоматической очистки регистраций модуля. `deactivate` — это набор ручных `try/except`, и он неполный.
- `tests/test_architecture.py` запрещает модулям импортировать `core`/`ui`, но **не запрещает** `modules.*`. Документация запрещает импорт другого модуля, тест это не проверяет.
- `ModuleLoader` не проверяет, что имя пакета совпадает с `manifest.name`, не проверяет уникальность manifest-имён и не изолирует модули на уровне файловой системы/процесса.

## 6. EventBus: отдельный разбор

### Что сделано правильно

- `publish` из фонового потока доставляется через `_EventRelay` в поток Qt-приложения.
- `dispatch` останавливается на первом truthy-обработчике.
- Ошибки подписчиков изолируются и логируются.
- `Subscription.unsubscribe()` идемпотентен.
- `CommandBus` отделён от `EventBus` концептуально.

### Проблемы

1. **`dispatch` не потокобезопасен** (см. 2.7).
2. **Нет владельца подписок**. Любой модуль может отписаться от любого события по имени, а загрузчик не ведёт реестр подписок модуля.
3. **Нет namespace-политики**. Модуль может публиковать `ui.tab.opened`, `project_changed` и т.п., провоцируя платформенные реакции.
4. **Смешение фактов и запросов** (`ITEM_CARD_REQUESTED` через `publish`, см. 2.6).
5. **Нет backpressure/coalescing**. При частом `publish` из фонового потока на каждого подписчика ставится отдельный сигнал в очередь UI; при массовых событиях очередь может расти.
6. **`CommandBus` без блокировки и без владельца** (см. 2.8).
7. **Нет проверки, что событие вообще имеет подписчиков** при `publish` (это не ошибка само по себе, но затрудняет диагностику «почему модуль не получил событие»).
8. **Системные события `ERROR` и часть `CLEAN_RUN_*` фактически не используются**; `PROJECT_SETTINGS_CHANGED` не имеет подписчиков, хотя модуль `ogg_editor` регистрирует настройку и мог бы на неё реагировать.

## 7. Хранилища, кэши и производительность

### 7.1. `generated` и `projects` лежат внутри дерева исходников

`main.py`:

```python
app_dir = Path(__file__).resolve().parent
generated_dir = app_dir / "generated"
projects_dir = app_dir.parent / "projects"
```

В текущем состоянии `src/generated` содержит **24 871 файл / ~215 МБ**. Дисковый кэш `ResolvedCache`/`ObjectCache` не имеет eviction: `max_entries`/`max_bytes` ограничивают только память, а `_save_disk` пишет файлы без удаления старых. `clear()` чистит память, но не диск.

Это приводит к неограниченному росту каталога в исходниках и потенциальным проблемам при установке в read-only каталог.

### 7.2. Сигнатура overlay пересчитывается до проверки кэша ключа

`ResolverService._resolved_key`:

```python
overlay_key = project_overlay_signature(overlay)
identity = (id(forest), kind, root_key, overlay_key)
with self._key_lock:
    cached = self._key_cache.get(identity)
```

Даже при попадании в `_key_cache` сначала полностью хешируются все `source_files` и `resolved_edits`, включая 40-МБ тексты. Комментарий «ключ кэшируется, чтобы не пересчитывать подпись» верен только для `file_subtree_signature`, но не для overlay.

### 7.3. `id(forest)` в ключе кэша

`identity` содержит `id(forest)`. Это не идентичность содержимого леса, а адрес объекта. После пересоздания леса возможен повтор `id`; `_key_cache` при этом не обязательно очищается, если лес собран без `clean=True`/инвалидации. Риск stale-ключей.

### 7.4. `ProjectOverlay` и проектные черновики копируют большие тексты

`PlatformApi.project_overlay()` собирает `source_files` и `resolved_edits` из всех черновиков. `CoreServices._prebuild_overlay`, `ResolverService._filter_overlay`, `ProjectService.build_preview` создают новые словари/срезы. Для system.ltx это несколько копий 40-МБ строк.

### 7.5. Кэш предпросмотра патча хранит `GeneratedPatch`

`ProjectService._preview_cache` (128 записей) хранит `PreviewItem` с `GeneratedPatch` и текстами файлов. Для больших патчей это может быть сотни мегабайт. Ключи включают SHA1 полного текста черновика, который считается на каждый предпросмотр.

## 8. Средние и низкие проблемы

### 8.1. `ModuleWindowManager.close_all` не используется

Метод есть, но нигде не вызывается. При завершении приложения окна модулей закрываются только их собственным `deactivate`; если модуль забыл — окно останется.

### 8.2. `TaskService` не умеет останавливать задачи

Нет `cancel`, `wait`, `shutdown`. `main.py` после `app.exec_()` останавливает только prebuild и вызывает `deactivate_all`, но не ждёт `QThread`-задачи. `on_done` может выполниться после закрытия окна/модуля.

Кроме того, `_DoneRelay.deliver` и `_LogRelay.deliver` не изолируют исключения callback’ов, в отличие от `EventBus`.

### 8.3. `ShortcutManager` / `MouseBindingManager`

- Нет unregister.
- `ShortcutManager._installed` хранит `id(registration)` и после пересоздания главного окна не переустанавливает шорткаты.
- `MouseBindingManager.handle` останавливается на первом совпавшем binding, даже если его callback вернул `False`; остальные привязки не получают шанс.

### 8.4. `OggEditorModule` регистрирует настройку, которая нигде не читается

`OGG_SAVE_SETTING` (`ogg_editor.save_mode`) регистрируется и снимается, но ни `OggEditorModule`, ни `ProjectService` её не используют. Сейчас это мёртвая настройка с единственным вариантом `override`.

### 8.5. `base_module/settings.py` содержит жёсткий путь Anomaly

```python
DEFAULT_CONFIG_DIR = r"../Anomaly 1.5.3 up/gamedata/configs"
...
app_dir.parent.parent / "Anomaly 1.5.3 up"
```

Это environment-specific хардкод в модуле, который должен быть независимым.

### 8.6. `base_module/section_graph.py` знает временный каталог core

`_is_materialized` проверяет `%TEMP%/ace_assets`, то есть модуль зашивает внутреннее соглашение `core.tools.vfs._materialize`. При изменении core модуль перестанет различать временные копии.

### 8.7. `ItemViewerFeature` содержит бизнес-логику создания предмета

`_create_item` жёстко задаёт:

```python
configs/items/mod_item_base_~ace_<tag>.ltx
configs/text/rus/st_ace_<tag>.xml
```

Модуль сам формирует LTX/XML-текст, ключи локализации, разметку секции. Это дублирует доменные правила core и привязывает модуль к конкретной раскладке `items`/`text/rus`.

### 8.8. Два пути правки предмета

`_replace_line`/`_apply_field` идут через resolved-документ, а `_new_file_for_line`/`_edit_new_item_file` — напрямую в raw-черновик нового файла. Один и тот же UI-жест может менять разные хранилища в зависимости от того, является ли файл новым.

### 8.9. `ProjectService` не является потокобезопасным

`build_preview` выполняется в `TaskService`, но работает с `self.project`, `_preview_cache` (`OrderedDict`), `changed_drafts()` и лесом, которые параллельно меняются в UI-потоке. `PlatformApi._invalidate_preview_cache`/`project_overlay` могут выполняться одновременно с фоновым предпросмотром.

### 8.10. `ProjectService` поддерживает `tab_id=""`, но ключи несимметричны

- `update_resolved_draft` сохраняет под `resolved_key(tab_id, root_path)`;
- `save_resolved_draft(tab_id)` при пустом `tab_id` ищет `resolved:<cwd>`;
- `get_resolved_draft(tab_id)` использует `str(tab_id)` напрямую;
- `remove_resolved_draft(tab_id)` тоже использует `str(tab_id)`.

Для пустого `tab_id` создание, чтение, сохранение и удаление работают с разными ключами.

### 8.11. `write_preview` автоматически подтверждает опасные планы

```python
if plan.needs_confirmation:
    plan = replace(plan, confirmed=True)
```

Пользователь видит общий предпросмотр, но отдельного подтверждения для плана, требующего `needs_confirmation`, нет. Для режима Override это потенциально опасно.

### 8.12. `ProjectService._merge_xml_generated` дублирует слияние

Ручная сборка `merged_plan`, файлов, `VerificationResult` и preview-текста дублирует логику `merge_patch_plans` и XML-патч-сервисов. Легко получить расхождение между тем, что показано в предпросмотре, и тем, что запишет `PatchWriter`.

### 8.13. `LtxResolverAdapter` monkey-patch’ит приватные методы Resolver4

`_read_lines`, `_load_file`, `_file_list`, `_load_mod_files` — внутренние методы внешнего скрипта. Любое обновление `Resolver4.py` может сломать overlay. Это не архитектурная ошибка в строгом смысле, но очень хрупкая интеграция.

### 8.14. `src/old` — мёртвый код

`src/old/core.py`, `Main5.py`, `ui.py`, `theme.py`, `main.py` (~100 КБ) не импортируются, но лежат в исходниках и создают впечатление альтернативной реализации. Аналогично есть мёртвые методы вроде `close_all`, `sync_resolved_line_edit`, `save_text`.

### 8.15. Двойной стиль импортов в UI

Часть UI-модулей использует `try: from ui.theme ... except ImportError: from .theme ...`, часть — только относительные импорты. При разных способах запуска это может привести к двум экземплярам модулей/палитры.

### 8.16. Тесты не проверяют архитектурные инварианты

`tests/test_architecture.py` проверяет только `import core/ui/modules` верхнего уровня. Не проверяются:

- импорт `modules.<other>` из модуля;
- импорт `ui` из `core`/`sdk` через динамические строки;
- обращение `ui` к внутренностям core;
- platform → base-команды;
- adapter → `window.file_tree`;
- отсутствие `dispatch` из фонового потока;
- порядок зависимостей и очистка после падения `register`;
- размер/формат проектных черновиков.

## 9. Общая оценка

### Что архитектурно сделано хорошо

- Композиционный корень в `main.py` действительно собирает зависимости явно.
- Модули не импортируют `core`/`ui`.
- Есть SDK-адаптеры, а не прямые ссылки на шины.
- `EventBus.publish` умеет безопасно доставлять события из фонового потока.
- `PatchWriter` атомарно готовит файлы и запрещает запись в Override/исходники.
- Кэши имеют версии и учитывают mtime/size зависимостей.
- Тесты покрывают много доменной логики (483 теста).

### Главные архитектурные выводы

1. **Проект и resolved-документы хранят слишком много копий одного и того же состояния.** Это самая дорогая проблема по памяти/диску и самая опасная для консистентности.
2. **Предсборка может кэшировать неверный результат** из-за потери `resolved_edits` в параллельных воркерах.
3. **`PlatformApi`/`ProjectService` — не тонкие платформенные сервисы, а God-object’ы с бизнес-логикой**, из-за чего UI напрямую зависит от внутренностей core.
4. **SDK фактически не является узким контрактом**: он знает домен предметов, resolved-документов, OGG-настроек и одновременно платформенные виджеты.
5. **Жизненный цикл модулей неполный**: зависимости не топологичны, ошибки `register` оставляют мусор, регистрации меню/обработчиков нельзя снять.
6. **EventBus концептуально смешивает факты, запросы и UI-действия**, а `CommandBus` не защищает от перехвата чужих команд.
7. **Дублирование LTX-парсеров и патч-конвейера** — главный источник будущих расхождений в поведении.

Если расставлять приоритеты по риску: сначала 1.1–1.4 (данные, кэш предсборки, владение resolved-состоянием, жизненный цикл модулей), затем 2.1–2.14 (границы SDK/UI/module), затем дублирование парсеров и патч-логики.

## 10. Пометка по 2.11 — обратная совместимость не нужна

Проект ещё не в релизе, поэтому поддержку старых форматов и старых сигнатур
удаляем, а не тащим дальше.

Для `FILE_OPENED`:

- payload — только `sdk.FileOpened(path, tab_id, request_id)`;
- строковый/`Path` payload больше не поддерживается;
- навигация применяется только к `editor.get_tab(tab_id)`, а не к
  `currentWidget()`;
- тесты и модули обновляются под новый payload, а не под старый.

То же правило применяем к другим контрактам, которые ещё будут меняться:
не добавляем `getattr`-совместимость и legacy-ветки «на всякий случай».
